# Auth Service — Full Plan

Three top-level folders, kept deliberately separate since they answer different questions:

- **`PLAN/`** (21 docs, `00`–`20`) — **how the system is built**: product scope, architecture, data model, API contract, backend/frontend architecture, public site architecture (`20-PUBLIC-SITE-ARCHITECTURE.md`), authorization (RBAC + multi-tenant delegation + ABAC), security baseline, threat model summary, testing, performance, observability, deployment, disaster recovery, roadmap, acceptance criteria, risk register, and a reusable feature-specification template (`19-FEATURE-SPECIFICATION-TEMPLATE.md`).
- **`UI-UX/`** (22 docs, `00`–`21`) — **how the system is used and felt**: design direction, personas, journeys, information architecture, user flows, design system, visual language, component specs, page specifications (summary inventory in `08`, concrete deep-dive specs in `18`), interaction/motion/micro-interaction design, responsive behavior (concrete 12/8/4-column grid), accessibility, empty/loading/error states, form UX, mobile UX, UX acceptance criteria, a frontend implementation chain (`19`), and — new — the **public-facing site** (`20-PUBLIC-SITE-SPECIFICATIONS.md`: landing page, docs, about, changelog, security/trust page) plus its **content & copy strategy** (`21-CONTENT-AND-COPY-STRATEGY.md`: voice, messaging framework, and page-by-page copy blueprints with real example copy for the landing page, about page, docs, changelog, security page, and contact page).
- **`SECURITY/`** (6 docs, `00`–`05`) — **how the system is attacked, protected, and verified**: asset & trust-boundary inventory, threat-actor profiles, a full attack-surface catalog (19 categories) each run through Asset → Trust Boundary → Threat Actor → Attack Surface → Attack Scenario → Impact → Likelihood → Mitigation → Detection → Response, detection/monitoring, incident response playbooks, and a verification/red-team plan scoped exclusively to this system's own authorized environments.

Start with `PLAN/00-PROJECT-CONTEXT.md`, then `PLAN/01-PRODUCT-SCOPE.md`. For anything console-UI-related, start with `UI-UX/00-DESIGN-DIRECTION.md`. For the public website (landing/docs/about), start with `PLAN/20-PUBLIC-SITE-ARCHITECTURE.md` and `UI-UX/20-PUBLIC-SITE-SPECIFICATIONS.md`. For security, start with `SECURITY/00-ASSET-AND-TRUST-BOUNDARY-INVENTORY.md`. Every document cross-references the others it depends on inline.

**Note on the public site vs. the console**: these are two deliberately separate frontend surfaces (different audience, tech stack, and deploy cadence) — see `PLAN/20-PUBLIC-SITE-ARCHITECTURE.md`'s comparison table. They share only the visual/brand language (`UI-UX/06-VISUAL-LANGUAGE.md`), never a codebase.

## For AI Coding Agents

**`CLAUDE.md`** and **`AGENTS.md`** at this repo's root give any coding agent (Claude Code, or any `agents.md`-compatible tool) a map of which document to read for a given task, the mandatory feature-specification workflow (`PLAN/19-FEATURE-SPECIFICATION-TEMPLATE.md`), and a set of non-negotiable constraints (server-side authorization enforcement, no console-only shortcuts, no hand-written API reference docs, no marketing copy ahead of what's shipped, etc.) pulled directly from the plan. Keep both files in sync if either is updated.
