# Audit — 2026-09-30

A full sweep of Phases 0–4, the console and public site, the backlog, and the
operational surface, run against `main` at `68d1b49` (Phase 4 through `P4-09`,
deployed to staging).

**Why it was run**: `P4-08` shipped three defects to staging that its own gate,
46 mutations and a full integration suite all passed. Each was a seam with one
caller that nothing drove. That is a class of failure no amount of care inside a
task catches, so this looks across tasks instead of within them.

**How it was run**: nine read-only agents in parallel — Phase 0–1, Phase 2–3,
the backlog and ADRs, the console and public site, operations and deployment,
plus three nested sweeps (migration columns against readers, the OpenAPI
contract against the handlers, and vacuous tests against the driver's real error
types). None of them modified anything.

## How to read this

Every finding carries a **verification** marker, because an agent's report is a
claim and not a fact:

| Marker | Meaning |
|---|---|
| **Verified** | Reproduced directly against the code or by running the thing |
| **Reported** | An agent's claim with file:line evidence, not independently reproduced |

A **Reported** finding is not lesser evidence of a problem — it is lesser
evidence that *this* is the problem. Verify before fixing.

Nothing here has been fixed. Findings that survive verification should become
task cards or `BACKLOG.md` entries and be struck from this document with a
pointer, the way `BACKLOG.md` already strikes its own resolved rows. This file
is a snapshot of one day, not a second backlog.

## Security

### AU-01 — Suspending an organization does nothing

**Verified.** `openapi/openapi.yaml:3915` publishes, as part of the contract the
public API reference is generated from:

> A suspended organization's users cannot log in. Changing this requires
> `INSTANCE_OWNER`.

No authentication path reads `organizations.status`. `authn.User.CanSignIn`
(`backend/internal/authn/user.go:72`) checks the **user's** status and the query
behind it selects from `users` alone. `LoginPolicy` (`authn/loginpolicy.go:246`)
selects `settings` and not `status`. The login flow
(`internal/login/handler.go:790-830`) never consults it. Nor do token issuance,
session lookup, or SSO cookie resumption. RLS on `organizations` filters by
`org_id` only, so suspension is not enforced as a side effect either.

**Consequence**: an `INSTANCE_OWNER` suspending a tenant — for an offboarding
customer, a compliance hold, a security incident — gets an audit event and a
flipped column, and is told by the platform's own documentation that the
tenant's users can no longer log in. In fact existing sessions keep working,
refresh tokens keep rotating, and a fresh password login against the suspended
organization succeeds. This is the "stored and enforced by nothing" shape, on a
control an operator would reach for precisely when something is wrong.

`P2-10` enforces `password_policy`, `session_lifetime_hours`,
`allowed_login_methods` and `mfa_required` at login, and never mentions
`status`. `P1-16` claims only the audit event and the soft-delete behaviour. No
backlog entry names this.

**Disposition**: task card. Either enforce it at login and on every token issue,
or delete the sentence from the contract — but the two must agree, and enforcing
is the honest reading of what an operator expects.

### AU-02 — SAML SSO skips the MFA mandate when a session already exists

**Verified.** `oauth/authorize/handler.go:234` and `oauth/token/handler.go:325`
both call `Mandate.Unmet` before reusing a live session. That is `P3-14`'s fix
for `P3-07`'s abuse case A-2: *"a live browser session went on receiving codes
silently for the session's lifetime."*

`samlapi/sso.go:131-148` has no such call. `grep` for `Mandate|Unmet` across
`internal/samlapi` returns nothing, and `samlapi.Handler` has no mandate field.
With a live session for the target organization, the fast path checks only the
requested AuthnContext class and issues.

**Consequence**: an organization that turns on `mfa_required`, or is inside its
14-day grace period, has that mandate bypassed for every user who keeps a
session alive and signs in to a SAML application — the single-sign-on case the
feature exists for. Fresh SAML logins are unaffected: they route through
`internal/login`, which does enforce it.

`P3-07`'s Definition of Done claims *"`docs/PLAN/17`'s Phase 2 criterion about
MFA-required being enforced rather than merely stored is now fully satisfied."*
That is false on current `main`.

**Disposition**: task card, and the highest priority in this document. The fix is
small — a `Mandate` field on `samlapi.Handler`, the check before the
AuthnContext check, wired in `main.go` as the OAuth handlers are. The lesson is
larger: a control added in one protocol was not carried into the next, and no
test spans the two.

### AU-03 — `manager_roles` has no RLS, past its own closure trigger

**Reported**, and consistent with the open `DV-02`. The entry's closing condition
is *"must close when `P2-05` lands"*, and `P2-05` is `DONE` (2026-09-12).
`app.current_user_id`, the mechanism the fix depended on, was never built.

Exposure, as assessed: no HTTP surface currently exploits it. The only
production writer is `projectgrant/owners.go`, restricted to
`PROJECT_GRANT_OWNER` and gated in the handler before the table is touched.
Reads are bounded by parameters rather than by RLS.

**Consequence**: latent rather than live. This is the one table in the schema
where hand-written `WHERE` clauses are the only isolation, which the Cross-Phase
Watch List's own `P0-08` row says must never be the case. The next write
endpoint against it — which `PG-31` asks for — inherits that with no database
backstop, and a reviewer who misses a scope check has no second line.

It is also **structurally invisible** to the gate: the RLS-coverage check keys
on tables having an `org_id`, and this table deliberately has none.

**Disposition**: `DV-02` needs rewriting to record that its trigger passed
unhonoured, and the missing work needs a task rather than a comment in a
migration.

### AU-04 — MFA step-up has no production caller

**Reported.** `mfa.StepUp(sessionMethods, required)` is defined in
`internal/mfa/framework.go` and called from nothing outside tests.
`oauth/authorize` has no `acr_values` handling; `prompt=login` forces a plain
fresh login rather than proof of a stronger factor. `internal/grant` and
`management/roles.go` have no recency or step-up check.

`PHASE-3:70` marks the downgrade abuse case done on the strength of unit tests
that call `StepUp` directly with hand-built slices — and `PHASE-2:118` had
already deferred step-up for sensitive grant changes to Phase 3, where it was
not delivered.

**Consequence**: an attacker holding a phished TOTP code faces no extra barrier
before a role grant, while the tracker and the test suite both read as covered.

**Disposition**: verify, then either build the step-up path or uncheck the abuse
case and say plainly that it is deferred. A checked box is a promise.

## Tests that cannot fail

### AU-05 — The audit-log index test passes with every index dropped

**Verified.** `internal/login/login_integration_test.go:1415`,
`TestTheAuditLogIsQueryableOnItsIndexes`, is `P1-14`'s DoD item *"EXPLAIN asserts
each of the three access patterns uses an index."*

`EXPLAIN (FORMAT TEXT)` returns one row per line of the plan.
`testsupport/factory.go:167` is `QueryRow(...).Scan(dest)`, which keeps the first
row and discards the rest without error. All three queries end in `LIMIT 50`, so
the first plan line is always the `Limit` node; the scan node is a child, one
level down, in a row that is thrown away.

So `plan` can contain neither `"Seq Scan"` nor `"Index"`, and the guard
`strings.Contains(plan, "Seq Scan") && !strings.Contains(plan, "Index")` is
always false. The test would pass identically with every index on `events`
dropped.

**Consequence**: the test's own comment names the risk it is blind to — *"a
sequential scan on a partitioned, append-only table that grows forever is the
shape of a query that works in a test and times out in year two."* `events` is
append-only with 24-month retention and is what an incident investigation reads.
Three index guarantees are unverified.

**Disposition**: fix the test — collect every row with `Query` and join before
matching. Then check the rest of the suite for the same `QueryRow`-against-a-
multi-row-result mistake.

### AU-06 — Eight of eleven console suites never assert a request body

**Reported.** The shared harness (`console/src/test/harness.tsx:42-44`) hands the
mock handler only `(url, {method})` and never the body, so those suites *cannot*
assert what was sent. `account`, `authorizations`, `mfa`, `pagination`,
`policies`, `roles`, `screens` and `sessions` contain no body assertions at all;
every mutation they exercise is verified only by a UI outcome driven by a canned
response.

The sharpest instance: `policies.test.tsx:265`, named *"sends the whole document,
so what is shown is what is stored"*, collects `bodies`, never populates it,
discards it with `void bodies`, and asserts only that a "Saved" toast appeared.
The regression it is named for already shipped once — `P2-14`'s `jsonb || jsonb`
shallow merge silently dropped `require_uppercase` when only `min_length`
changed.

The three newest suites (`projectgrants`, `grantedprojects`, `samlapplications`)
each wrote their own `fetch` stub that captures the body — so the limitation was
known and never backfilled.

**Disposition**: extend the shared harness to pass the body, then backfill the
suites. The three bespoke stubs should collapse into the harness.

### AU-18 — The forgot-password mail bound is never exercised as a refusal

**Verified.** `internal/login/password.go:197-204` is the anti-abuse bound on the
unauthenticated self-service reset. `issueReset` has one caller, `Forgot`
(`password.go:114`).

Precisely: `MailLimit` is not always nil in tests — `passkeys_test.go:122` sets a
`noQuota{}` that allows, and `notme_integration_test.go:550` wires a
`refusingQuota{}`. But that refusing double is wired to the **not-me** flow
(`sendReportReset`), never to `Forgot`. So across the 18 tests in
`password_integration_test.go`, the refusal branch of `issueReset` is never
taken.

**Consequence**: three regressions would pass. An inverted `verdict.Allowed`
polarity; a misconfigured limiter that refuses everything, silently breaking
every legitimate reset — and *indistinguishable from working*, because the
browser response is identical either way by design; or the limiter bypassed
entirely, leaving nothing between this endpoint and flooding a victim's inbox
with reset mail.

The test double and the wiring pattern already exist a file away. They were
never pointed at this flow.

**Disposition**: wire `refusingQuota{}` into a `Forgot` test and assert no mail
was sent and the response is byte-identical to the unknown-address answer. Cheap,
and it closes the one gap found in the four packages swept for this class.

## Operations

### AU-07 — Nothing scrapes the alerting rules

**Reported.** `deploy/observability/alerts.yml` holds 22 rules, several built on
`absent()`. No compose file defines Prometheus, Alertmanager, or any scraper, and
`deploy/observability/README.md` says so outright: *"nothing on the host scrapes
it yet."*

`backup.sh` emits no success metric, and no rule exists for backup freshness even
in the unused file.

**Consequence**: `BL-01` — a backup that silently stops — cannot be caught even
in principle, and neither can anything else the rules describe. The rules are a
design, not a control.

**Disposition**: either deploy a scraper and wire the backup freshness metric, or
move `alerts.yml` somewhere that does not read as deployed and say in `BL-01`
that monitoring is unbuilt rather than incomplete.

### AU-08 — Two systemd units describe two incompatible deployments

**Reported.** `deploy/vm/zea-auth.service` uses `/opt/zed-auth/deploy/vm` with
`/etc/zed-auth/env` and, by omitting `AUTH_COMPOSE_FILE`, starts the Caddy
variant on ports 80/443. `deploy/vm/zed-auth-backup.service` uses
`/home/infra/auth/deploy/vm` with `/home/infra/auth-state/.env` and the tunnel
variant. `deploy/vm/README.md`'s first-time setup instructs the former; the
key-rotation runbook, `secrets.sh`, and the live VM all use the latter.

**Consequence**: an operator following `README.md` verbatim stands up the wrong
stack — direct TLS on 80/443 — beside the real one, on a host already laid out
differently. The backup unit would not see its env file.

**Disposition**: one topology in the docs, with the other named as historical or
deleted. The live one is the tunnel variant.

### AU-09 — CI does not run several local gate checks

**Reported.** Absent from `.github/workflows/ci.yml`: the acceptance-harness
build and vet; `demo/`'s own tests; `brand/check.py`; the console
pattern-generation check; `scripts/check-docs.py`; the one-clock check; and the
audit-log append-only privilege check.

**Consequence**: a pull request can reintroduce `P1-28`'s clock bug or the
staging audit-write privilege drift — both of which already happened — and CI
stays green. These are caught only if a developer runs the gate locally with
Docker up.

**Disposition**: bring CI to parity, or state in the gate which checks are
deliberately local-only and why.

### AU-10 — The public site fails its own claims check, and the check is order-dependent

**Verified, with an unexplained discrepancy.** `npm run check:claims` in
`public-site/` fails on the current tree, exit code 1:

> "Roles that scale to delegation" is labelled "Phase 4" but every task it needs
> (P4-01 … P4-06) is DONE — it has shipped, and describing it as planned is now
> the inaccuracy

The landing page, `about.md:49` and `docs/index.md:23` all say delegation and
SAML are still to come; both shipped and are on staging. `CLAIMS.md` was last
audited 2026-09-15, before any Phase 4 work, and the changelog stops at Phase 3.

Two things follow, and the second matters more:

1. **`main` is currently red on its own gate.** `scripts/check.sh:768` runs this
   check, and it fails.
2. **I could not reconcile that with the last full gate run**, which reported 49
   passed, 0 failed a few hours earlier on a tree whose `PROGRESS.md` rows for
   `P4-01`–`P4-06` are identical. The check reads `public-site/build/index.html`
   — a build artifact — so its result depends on whether a build exists and how
   old it is. A gate check that can pass or fail on the staleness of a directory
   is not a check anybody can trust either way.

**Disposition**: two items. Correct the copy (governance rule, `docs/UI-UX/21`),
and make the claims check read the source rather than a build artifact — or make
the gate build first and say so.
