# 01 - Go Client SDK

> Category: **SDK** (`docs/SDK/`) &nbsp;|&nbsp; Status: Draft specification &nbsp;|&nbsp; Owner task: none — no phase in `TASKS/PROGRESS.md` schedules a Go client SDK &nbsp;|&nbsp; Verified against: `84eb9a2`

## Purpose

State what a Go integrator should do today, with no official Go client available, and specify what an official Go SDK would need to provide if the work is ever scheduled.

## Why It Is Not Built Yet

There is no `pkg/client`, no Go module published for consumers, and no code in this repository that a Go application could `go get` to talk to the Auth Service. Two things confirm this is deliberate rather than merely incomplete:

- **`backend/internal/api/oapi-codegen.yaml`** — the config that generates the server's own contract types — sets `generate: client: false` with the comment: *"No client here. The console generates a TypeScript client from the same spec; a Go client would be a third artifact with nobody to use it."* The tooling to generate one (`oapi-codegen`, already a build dependency via `backend/internal/api/generate.go`'s `go:generate` directive) is present; generating a client with it is a choice not yet made, not a missing capability.
- **`demo/internal/verify/`**, the only Go code in the repository that validates this service's tokens outside the service itself, is intentionally not a library. It lives inside `demo/go.mod`, a module separate from `backend/`, and inside an `internal/` package, which Go's compiler enforces cannot be imported from outside that module. `demo/README.md` states its purpose directly: *"the reference a consumer team copies instead of writing their own JWT handling"* — a worked example meant to be read and reproduced, not a dependency.

## What To Do Today

1. **Generate your own client from the contract.** `openapi/openapi.yaml` is the canonical, hand-written source (ADR-013). Run `oapi-codegen` (or any OpenAPI 3.1-compatible Go generator) against it with client generation turned on — the reverse of `backend/internal/api/oapi-codegen.yaml`'s `client: false` — to get typed request/response models for every documented `/v1` operation.
2. **Validate tokens locally with a standard library**, not a hand-rolled parser: fetch `/.well-known/openid-configuration` and `jwks_uri`, cache the key set, and check signature, `iss`, `aud`, `exp`, and token type on every request, exactly as `docs/DEVELOPER/03-INTEGRATION-GUIDE.md` step 3 describes. `demo/internal/verify/verify.go` is the concrete reference for every check that matters and why it is not optional (algorithm pinned rather than read from the token header, `typ` compared to reject an access token used as an ID token, exact-string `iss` comparison, `aud` containing this client's own `client_id`). Any general-purpose Go OIDC/JWT library (for example one built on `golang-jwt` or a JOSE implementation, paired with `golang.org/x/oauth2` for the authorization code exchange) can perform the same checks; the specific library is your choice; the checks themselves are not optional.
3. **Follow the integration guide end to end**: `docs/DEVELOPER/03-INTEGRATION-GUIDE.md` covers application registration, the PKCE authorization code flow, token validation, refresh rotation, and the two ways to decide what a user may do (token claims vs. live `POST /v1/authz/check`).
4. **Never treat a locally-decoded role claim as authoritative for a sensitive action.** `CLAUDE.md`'s non-negotiable constraint applies to every caller, SDK or not: the API re-checks authorization server-side regardless of what a client believes.

## Constraints Already Decided

- No Go client is currently generated by the server's own build (`client: false` in `backend/internal/api/oapi-codegen.yaml`); a future SDK's generation config would be independent of that file, not a change to it, since the server has its own reasons not to carry a client dependency.
- `demo/internal/verify/` is the proven set of checks a Go SDK's token-verification component would need to reproduce at minimum: algorithm allow-list (never read from the token), `typ` check, exact `iss` match, `aud` containment, `exp` presence and freshness, and byte-exact signature verification over the original (not re-encoded) header and payload segments (`demo/internal/verify/signature.go`).
- Refresh token rotation is mandatory server-side: every exchange returns a new refresh token and spends the old one, and presenting a spent token outside the grace window revokes the whole family (`docs/SESSION-MANAGEMENT/02-REFRESH-TOKENS-AND-ROTATION.md`, `docs/DEVELOPER/03-INTEGRATION-GUIDE.md` step 4). A Go SDK's refresh helper must store the newly issued refresh token before reporting success, or a crash between issuance and storage becomes an unrecoverable reuse-detection revocation for the caller.
- `Idempotency-Key` is required for safe automatic retries of unsafe methods (`docs/API/07-IDEMPOTENCY.md`); an SDK must not retry a `POST` on the caller's behalf without one.

## Key Topics To Specify

- Module path, versioning scheme, and how a release ties to the `openapi/openapi.yaml` version it was generated against.
- Which parts are generated (request/response models, path construction) versus hand-written (token cache, retry/backoff, refresh rotation, JWKS caching).
- Whether the SDK targets service-to-service use (client credentials, no interactive login) only, or also an interactive PKCE flow for Go CLI/desktop consumers — `docs/DEVELOPER/03-INTEGRATION-GUIDE.md` currently documents the browser-redirect flow, which does not map directly onto a headless Go process.
- `context.Context`-based cancellation and an injectable `*http.Client` for testability, consistent with idiomatic Go client design.
- How pagination (`docs/API/06-PAGINATION.md`'s opaque `page_token`) is exposed — an iterator, a manual "next page" call, or both.

## Acceptance Criteria

- [ ] Generated from `openapi/openapi.yaml` with `oapi-codegen` (or an equivalent generator) with client generation enabled; the generation command and config are committed, mirroring the documentation style of `backend/internal/api/oapi-codegen.yaml`.
- [ ] A token-verification helper, if the SDK provides one, passes tests for every negative case `demo/internal/verify/` already covers: wrong `aud`, algorithm confusion (`alg: none`, HMAC-signed token presented to an RSA-expecting verifier), expired token, wrong `typ`.
- [ ] The refresh-rotation helper writes the newly issued refresh token to the caller-supplied storage before returning success, and a fault-injection test confirms a crash between token issuance and storage cannot silently lose the session without also being visible as a reuse-detection event on the next attempt.
- [ ] No SDK method issues an unsafe (`POST`/`PATCH`/`DELETE`) retry without an `Idempotency-Key`; a test asserts the header is present on every retried call.
- [ ] Every exported method corresponds to a documented `operationId`; an SDK method with no matching entry in `openapi/openapi.yaml` fails a static check.
- [ ] A named task with an assigned roadmap phase exists in `TASKS/` before implementation begins.

## Open Questions

- Whether this work is ever scheduled at all — no phase file in `TASKS/` names it, and `backend/internal/api/oapi-codegen.yaml`'s existing reasoning ("nobody to use it") has not been revisited by any ADR.
- Service-to-service vs. interactive scope, as noted above.
