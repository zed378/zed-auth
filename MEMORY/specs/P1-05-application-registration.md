# P1-05 — Application (OIDC Client) Registration and Credentials

Feature specification, per `PLAN/19-FEATURE-SPECIFICATION-TEMPLATE.md`. `CLAUDE.md` requires one for anything touching credential handling.

---

## 1. Business Objective

Let an organization register the applications that will authenticate against this service, issue each one a credential it can prove itself with, and make the two ways that classically goes wrong impossible rather than discouraged: a client secret that can be read back after creation, and a `redirect_uri` that matches more than the one URL it was meant to.

The second is the one that turns a correct implementation of everything else into an account takeover. If `https://app.example.com/callback` also matches `https://app.example.com/callback/../../evil`, or `https://app.example.com.attacker.net/callback`, then the authorization code — the thing the entire flow exists to deliver safely — is delivered to the attacker instead. `PLAN/09` names it: exact match, never prefix match.

## 2. Actors

| Actor | Interaction |
|---|---|
| Organization administrator | Registers an application, reads its secret once, rotates it later |
| A registered application | Presents `client_id` and `client_secret` at the token endpoint (`P1-07`) |
| The authorization endpoint (`P1-06`) | Asks whether a presented `redirect_uri` is registered for this client |
| An attacker with a registered `client_id` | Tries to widen the redirect match, or to use a grant the client type should not have |
| An attacker holding a database dump | Tries to recover secrets from their hashes |

## 3. Functional Requirements

- **FR-1** Create an application per `PLAN/04` § `applications`: `id` doubles as `client_id`, `type` in {`web`, `native`, `spa`, `api`, `saml`}, plus `redirect_uris`, `grant_types`, `post_logout_redirect_uris`.
- **FR-2** Generate a client secret for confidential clients only (`web`, `api`). Public clients (`spa`, `native`) get none and rely on PKCE.
- **FR-3** The secret is **generated by this service and never supplied by a caller.** See §12 — the hash choice depends on it.
- **FR-4** Store only a hash. Return the plaintext exactly once, at creation or rotation, and never again through any code path.
- **FR-5** Validate `redirect_uris` at registration: absolute, no fragment, no wildcard, HTTPS except loopback.
- **FR-6** Match `redirect_uris` at authorization time by **exact string comparison**.
- **FR-7** Reject `grant_types` inconsistent with the client type — loudly, at registration.
- **FR-8** Rotate a secret with an overlap window: the new one works immediately, the previous one keeps working until it expires.
- **FR-9** Audit create, update, rotate and delete (`P0-12`).

## 4. Non-Functional Requirements

- **NFR-1** Secret verification is on the token endpoint's hot path and must stay cheap. See §12.
- **NFR-2** Verification is constant-time with respect to the secret value.
- **NFR-3** No secret, and no secret hash, reaches a log, a metric label, an error message, or an audit payload.
- **NFR-4** Redirect matching allocates nothing per call and does no I/O beyond the application row the caller already holds — `P1-06` runs it on every authorization request.

## 6. Database Changes

**None.** `P0-07` already created `applications` with `client_secret_hash`, `previous_client_secret_hash`, `previous_client_secret_expires_at`, both array columns, and two CHECK constraints — a public client cannot hold a secret, and a rotation window cannot exist without an expiry.

That the schema anticipated the overlap window is worth noting: it means rotation is a feature of the data model rather than something bolted onto it.

## 7. API Contract

None in this task. `P1-18` adds the endpoints. The shapes it will need are fixed here so that they cannot drift:

- Creation returns the secret **once**, in the creation response only.
- No read endpoint ever returns `client_secret`, `client_secret_hash`, or any prefix of either.
- Rotation returns the new secret once and reports when the previous one expires.

## 8. Frontend Changes

None. `UI-UX/08` § Applications tab governs the screen: "Secrets shown once at creation only, never retrievable again." The server half is what makes that true rather than a UI convention.

## 9. Backend Changes

New package `internal/oauth/client` (name settled at implementation):

```go
type Type string // web, native, spa, api, saml

func (t Type) IsPublic() bool     // spa, native
func (t Type) IsConfidential() bool

type Application struct {
    ID        string // the client_id
    OrgID     string
    ProjectID string
    Name      string
    Type      Type

    RedirectURIs           []string
    PostLogoutRedirectURIs []string
    GrantTypes             []string
}

// Secret is returned exactly once and is not a field of Application, so there
// is no struct a read path could accidentally serialise it out of.
type Secret struct{ plaintext string }

func (s Secret) String() string  // "[REDACTED]"
func (s Secret) Reveal() string  // the only way out, and it is greppable

func Generate() (Secret, string, error)  // secret, hash
func Verify(hash string, presented string) bool

func ValidateRedirectURI(raw string, t Type) error
func (a Application) MatchesRedirectURI(presented string) bool
func ValidateGrantTypes(t Type, grants []string) error
```

`Secret` is a struct wrapping an unexported string rather than a bare `string`, and that is the whole design. A `string` return value gets logged, embedded in an error, or put in a struct that later grows a JSON tag. A type whose `String()` returns `[REDACTED]` cannot be printed by accident, and `Reveal()` is a word that shows up in review.

## 10. Authorization Rules

Applications are read and written through the tenant-scoped storage API, so a caller cannot register an application in another organization's project, and `applications.org_id` is denormalised precisely so RLS can filter without a join (`P0-08`).

Who may register an application is `P2-05`'s manager-role check, applied by `P1-18` at the endpoint. This task provides no authorization of its own and must not appear to: a domain package that looks like it enforces permissions is one an endpoint author trusts to.

## 11. Validation

### Redirect URIs

| Rule | Reason |
|---|---|
| Absolute, with scheme and host | A relative URI resolves against whatever the browser was on |
| No fragment (`#...`) | The fragment never reaches the server, so it cannot be part of a match; a registered one is a misunderstanding worth correcting at registration |
| No wildcard characters (`*`) | There is no wildcard matching, so a wildcard in a registered URI is silently literal — worse than an error |
| Scheme `https`, or `http` only for loopback | `PLAN/09` § Transport. An authorization code over cleartext is a code an observer keeps |
| Loopback means `127.0.0.1`, `[::1]`, or `localhost` | Native clients need it (RFC 8252). Nothing else gets an `http` exemption |
| Custom schemes (`com.example.app:/cb`) allowed for `native` only | RFC 8252's private-use scheme redirect, which has no meaning for a browser client |
| Not a link-local address | `169.254.0.0/16` includes `169.254.169.254`. No legitimate redirect target lives there, and a code delivered there is a code delivered to a cloud metadata service |
| At least one URI for any client using `authorization_code` | A client that can start a flow it cannot finish is a configuration error |
| Normalised at registration: scheme and host lowercased | So that later exact comparison is predictable. See §13 |

**On SSRF.** The task card cites `SECURITY/02` §7 for the internal-address case. That mapping is not quite right and the difference matters: a `redirect_uri` is never fetched by this server, it is handed to the user's browser. So there is no server-side request to forge. What an internal redirect target actually risks is an authorization code delivered to a host the *user's* machine can reach and its owner cannot see. Link-local is refused for that reason. Private ranges (`10/8`, `192.168/16`) are **allowed**, because a self-hosted deployment redirecting to an intranet application is a legitimate and expected configuration, and registration is already an authenticated, audited, admin-only action.

### Grant types

| Client type | Allowed | Reason |
|---|---|---|
| `web` | `authorization_code`, `refresh_token`, `client_credentials` | Confidential; can hold a secret |
| `api` | `client_credentials`, `refresh_token` | No user is present, so no authorization code |
| `spa` | `authorization_code`, `refresh_token` | Public; PKCE instead of a secret |
| `native` | `authorization_code`, `refresh_token` | Same |
| `saml` | none of the OIDC grants | SAML is Phase 4; an OIDC grant on a SAML client is a category error |

`implicit` and `password` are refused for every type, matching `P1-04`'s discovery document and `PLAN/05`. The refusal lives in one place shared by both, so the document and the enforcement cannot disagree.

**The rule that carries the abuse case**: `client_credentials` requires the client to authenticate, and a public client has nothing to authenticate with. So a `spa` requesting it is rejected — not because a table says so, but because the grant is meaningless without a secret.

## 12. Error Handling and the Hashing Decision

**Client secrets are hashed with SHA-256, not Argon2id.** Recorded as an ADR. The reasoning, and the constraint it depends on:

A password is chosen by a human, has perhaps 30 bits of entropy, and needs a deliberately slow KDF so that a leaked hash is not a leaked password. A client secret here is 256 bits from `crypto/rand`. Brute-forcing it behind even an infinitely fast hash takes on the order of 10^52 years. The hash's speed is not what protects it; the entropy already did.

What a slow KDF *would* buy is a denial-of-service vector pointed at ourselves. Client secrets are verified on every `client_credentials` token request. At `P1-01`'s measured Argon2id parameters — 90ms and 64 MiB on the staging VM — 50 token requests per second is 4.5 cores and 288 MiB of resident memory, and an attacker sending deliberately **wrong** secrets pays nothing while we pay all of it. That is an unauthenticated amplification vector bought for no security benefit.

This holds **only while the secret is high-entropy and generated by us**. If a future change ever lets an administrator choose a client secret, SHA-256 becomes the wrong answer that afternoon. So it is not left as a convention: `Generate()` is the only way to produce one, no function accepts a caller-supplied secret, and a test asserts the generated length and alphabet. FR-3 exists to protect this decision, not for its own sake.

Verification is `crypto/subtle.ConstantTimeCompare` over the hex digests.

Other errors:

| Condition | Behaviour |
|---|---|
| Secret presented for a public client | Rejected. A public client has no secret, so presenting one means the caller is confused about which client it is |
| Rotation when a previous secret is still live | Allowed; the window restarts. Refusing would leave an operator unable to respond to a leak during a planned rotation |
| Previous secret presented after expiry | Rejected exactly as an unknown secret. No hint that it was once valid |
| Redirect URI presented that is not registered | Rejected. **How much is said depends on who is asking**, the same asymmetry as `P1-02` §12: at the authorization endpoint nothing is disclosed, because anyone can craft that request with a known `client_id` and an error listing the registered URIs would enumerate them for free — and OAuth requires not redirecting at all in that case. On an authenticated management call (`P1-18`) the registered value is named, because the admin already owns it and is trying to fix a typo |

## 13. Edge Cases

| Case | Handling |
|---|---|
| Registered `https://a.example/cb`, presented `https://a.example/cb/` | **Rejected.** A trailing slash is a different string |
| Presented with an extra query parameter | **Rejected.** Exact comparison over the whole URI |
| Presented `HTTPS://A.EXAMPLE/cb` for registered `https://a.example/cb` | **Rejected.** Registration lowercases scheme and host, so the registered form is canonical and the client must send it. RFC 3986 makes scheme and host case-insensitive, but OAuth 2.1 specifies simple string comparison, and every deviation from "compare the strings" is where prefix bugs get in |
| Path case differs | Rejected. Paths are case-sensitive anyway |
| Percent-encoding differs (`%2F` vs `/`) | Rejected. Not normalised — normalisation is decoding, and decoding is where a matcher starts accepting things it did not mean to |
| Two applications registering the same redirect URI | Allowed. It is not a unique key; the `client_id` identifies which one is in play |
| Empty `redirect_uris` on an `api` client | Allowed. `client_credentials` involves no redirect |
| `saml` client created | Allowed as a record, with no OIDC grants. Its flows are Phase 4 |
| Rotation on a public client | Rejected. There is no secret to rotate |

## 14. Abuse Cases

| # | Abuse case | Source | Control |
|---|---|---|---|
| A-1 | Open redirect by registering a URI sharing a prefix with the target | `SECURITY/02` §1 | Exact comparison; a prefix match is not implemented at all |
| A-2 | `https://app.example.com.attacker.net/cb` accepted for `https://app.example.com/cb` | `SECURITY/02` §1 | Same — suffix confusion needs prefix or pattern matching to exist |
| A-3 | Public client requesting `client_credentials` | Task card | Grant/type consistency, refused at registration |
| A-4 | Public client created with a secret | Task card | Refused in code and by a database CHECK |
| A-5 | Secret read back after creation | `UI-UX/08`, `SECURITY/02` §16 | Only a hash is stored; `Secret` is not a field of `Application` |
| A-6 | Secret recovered from a database dump | `SECURITY/02` §16 | 256-bit entropy; see §12 |
| A-7 | Secret leaked through a log or an audit payload | `SECURITY/02` §16, §19 | `Secret.String()` returns `[REDACTED]`; audit payloads carry ids only |
| A-8 | Timing oracle on secret comparison | `SECURITY/02` §1 | Constant-time comparison |
| A-9 | Expired previous secret still accepted | — | Expiry checked against the caller's clock on every verification |
| A-10 | Code delivered to a link-local address | §11 | Link-local refused at registration |
| A-11 | Cross-tenant application read or write | `SECURITY/02` §2 | RLS-scoped storage API |
| A-12 | CPU/memory exhaustion via wrong secrets | `SECURITY/02` §10 | The hash choice in §12 is what prevents it |

## 15. Logging / Audit Requirements

| Event | Payload | Never |
|---|---|---|
| `application.created` | app id, org id, project id, type, whether a secret was issued | the secret, its hash, any prefix |
| `application.updated` | app id, which fields changed | the values of `redirect_uris` are recorded; they are not secret and a change to them is exactly what an investigator needs |
| `application.secret_rotated` | app id, when the previous secret expires | either secret |
| `application.deleted` | app id | — |

`application.updated` is new; the other three exist in `internal/audit` already.

Redirect URI changes are audited **with their values** deliberately. If an attacker with admin access widens a redirect URI, the audit log is the only place that shows it, and an entry saying "redirect_uris changed" without saying to what is an entry that cannot answer the question it exists for.

## 16. Security Controls

- Secrets from `crypto/rand`, 256 bits, base64url, never caller-supplied.
- Only hashes stored; plaintext returned once and held in a type that will not print itself.
- Constant-time verification.
- Exact redirect matching, with no normalisation at comparison time.
- Registration-time URI validation: absolute, no fragment, no wildcard, HTTPS-or-loopback, no link-local.
- Grant/type consistency, refusing meaningless combinations rather than accepting them.
- Rotation with a bounded overlap that cannot be unbounded (database CHECK).
- Tenant scoping through RLS.

## 17. Testing Strategy

| Layer | Coverage |
|---|---|
| Unit | Redirect validation across absolute/relative, fragment, wildcard, http vs https, each loopback form, custom schemes per type, link-local, empty |
| Unit | Redirect **matching**: the trailing slash, the extra query parameter, the fragment, the case difference, the percent-encoding difference, the prefix, the suffix-confusion host — each asserted rejected, and the exact registered string asserted accepted so the matcher is not simply refusing everything |
| Unit | Grant/type consistency for all five types, including every forbidden combination and `implicit`/`password` for each |
| Unit | Secret generation: length, alphabet, and that two calls differ. Verification: correct, wrong, empty, and the hash never equal to the plaintext |
| Unit | `Secret.String()` does not contain the secret — asserted by generating one and searching the formatted output |
| Integration | An application round-trips through a real tenant-scoped transaction; `SELECT client_secret_hash` proves the plaintext is absent from the row |
| Integration | Rotation: new secret verifies, previous verifies until expiry, previous fails after it |
| Integration | Cross-tenant read returns not-found, with a control proving the row is readable in its own scope |
| Security | Every abuse case A-1…A-12 |

A **control test** for the matcher: a table of URIs that must all be rejected is worthless if the matcher rejects everything, so the same table asserts the registered URI itself matches.

## 18. Acceptance Criteria

1. A secret is returned at creation and by no other code path; the database holds only a hash.
2. `https://a.example/cb ` variants differing by a trailing slash, a query parameter, or a fragment are all rejected while the exact string is accepted.
3. A `spa` cannot be created with a secret, and cannot be granted `client_credentials`.
4. A rotated secret and its predecessor both verify until the overlap expires; afterwards only the new one does.
5. Create, update, rotate and delete each write an audit event carrying no secret material.

## 19. Definition of Done

The task's five items plus the global DoD in `TASKS/00-TASK-CONVENTIONS.md`. Item 3 of the task's DoD ("rejected at authorization time") is satisfied here by the matcher and its tests; `P1-06` wires it to the endpoint.

## 20. Implementation Sequence

1. `Type`, `ValidateGrantTypes` — pure, with the full table of combinations.
2. `ValidateRedirectURI` and `MatchesRedirectURI` — pure, with the rejection table and its control.
3. `Secret`, `Generate`, `Verify` — and the ADR.
4. The store: create, read, update, rotate, delete through the scoped transaction.
5. `application.updated` audit event, and audit writes on each path.
6. Integration tests, including the direct row inspection and the cross-tenant control.

Steps 1–3 are pure and cover most of the abuse cases; they can be reviewed before any database code exists.

## 21. Rollback Strategy

No schema change, so there is nothing to roll back in the database. Rolling back the code removes the ability to register applications; existing rows keep their hashes and stay verifiable by the previous version, because the hash format does not change.

The one-way door is the hashing choice: secrets issued under SHA-256 cannot be re-hashed under a different scheme without reissuing them, since we never hold the plaintext. That is inherent to storing hashes and is the reason §12 is an ADR rather than a comment.

## 22. Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Someone later accepts an admin-supplied client secret, invalidating §12 | Medium | High | No function accepts one; `Generate` is the only producer. The ADR states the dependency explicitly so the connection is findable |
| A future "convenience" adds prefix or wildcard redirect matching | Medium | Critical | The rejection table is the guard, and it names the attack in each case so the tests read as reasons rather than as fixtures |
| The `Secret` type is unwrapped early and passed as a `string` | Medium | High | `Reveal()` is deliberately conspicuous; the test asserting `String()` hides the value fails if the type is replaced |
| Exact matching frustrates an integrator whose framework normalises URIs | High | Low | Real and intended. The remedy is the management API's error, which names the registered string to an authenticated admin; the authorization endpoint stays silent. Documenting the rule in the API reference is what keeps this a five-minute confusion rather than an afternoon |
