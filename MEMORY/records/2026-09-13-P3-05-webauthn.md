## The conflict this task was always going to hit

`P1-12` made "no JavaScript" a load-bearing property of the hosted login flow —
it is what makes `default-src 'none'` achievable rather than aspirational.
WebAuthn is `navigator.credentials`, a browser API with no form-only
equivalent. **There is no version of this feature without script.**

`P3-03` saw it and deferred it here rather than resolving it quietly.

The resolution is containment, and the boundary is tested rather than asserted:
`/login` is untouched, `/login/mfa` offering only TOTP is untouched, and only a
challenge that actually renders a passkey form carries `script-src` — one
source, a **hash** of one inline script. A nonce would have authorised whatever
the server put it on; a hash authorises that exact text and nothing else, and
it is computed from the source so the two cannot drift.

The residual is real and `PG-40` says so plainly: this is the one page in the
estate where a content-injection bug could reach a script context.

## A library, against P3-02's own argument

`P3-02` argued against new dependencies in the authentication path and wrote
TOTP into the repository. This vendors one, and the difference is not
inconsistency:

| | TOTP | WebAuthn |
|---|---|---|
| Size | ~30 lines | CBOR + COSE + attestation + three signature algorithms |
| Stability | RFC 6238, frozen since 2011 | An evolving W3C spec |
| Getting it wrong | Codes nobody's app agrees with — **visible within a day** | A signature check that accepts forgeries — **invisible** |

The last row decides it, and `docs/PLAN/07` asks for exactly this call.

It forced `golang.org/x/crypto` from v0.56.0 to v0.57.0, which matters because
Argon2 lives there. Checked before going further: the password suite and the
whole unit suite pass unchanged.

## A bug the test caught that only a browser would otherwise have shown

`showChallenge` emitted the embedded `Page`'s policy rather than the
`ChallengePage`'s. They differ by exactly one directive — the script source.

So the page would have rendered the script and then forbidden it. In every
browser, the passkey button would simply never appear, with one console line
nobody is watching, and the natural conclusion would have been "my security key
is broken". Curl-driven tests would have passed, which is the same shape as
`P1-27`'s `form-action` bug.

## Two more, found while writing the store

- `public_key` is a **`text`** column (`docs/PLAN/04` names it that way) and a
  COSE key is CBOR — bytes, never valid UTF-8. Writing it raw would have been
  rejected by Postgres or mangled by a driver that tried. Both text columns now
  hold base64url, which is also what the browser uses for `credential_id`, so a
  log line and a devtools panel compare directly.
- Nothing made "one credential belongs to one account" a property of the
  database. The ceremony enforces it, but `docs/SECURITY/02` §2 names
  registering to another user's account as an attack, and a guarantee resting
  on one code path staying correct is thinner than one the database holds.
  Migration `20260913000031` adds the partial unique index.

## The software authenticator

Every claim in this task — that a relayed assertion fails, that a challenge
cannot be replayed, that a regressed counter is caught — is a claim about what
happens when a **real** signature arrives with one thing wrong. A fake verifier
cannot test any of it, because the fake would be the thing deciding.

So `softauthenticator_test.go` produces genuine ES256 assertions: COSE keys in
CBOR, authenticator data with the right flags, ECDSA over
`authData || SHA256(clientData)`. Each test breaks exactly one property.

The origin test is the one worth reading. The authenticator holds the right
key, signs the right challenge, and produces a signature that verifies
cryptographically — the **only** thing wrong is the origin the browser
reported, which is precisely what a relayed phishing attempt looks like. It has
a positive control beside it: the same authenticator and the same challenge
with the right origin is accepted, so the refusal is the origin check rather
than a verifier that refuses everything.

## The mutation run

Fifteen controls. Thirteen red immediately; **two were redundant rather than
untested**, and both were resolved the way `P3-02` established:

| Guard | Resolution |
|---|---|
| `FinishLogin`'s "credential this service did not load" | **Kept, documented.** Unreachable — the library resolves against the list this function just loaded. It stays because without it `stored` would be a zero value and the counter write would go to an empty factor id: a silent write rather than a refusal. The mutation was retargeted to the query that loads the candidates, which is what actually enforces "another user's credential does not work" |
| `FinishLogin`'s active-status filter | **Kept, documented.** `BeginLogin` applies the same test and the session's allow-list comes from it, so this one is unreachable today. It stays for the discoverable-login path, which carries no allow-list and would make this the only status check between a half-finished registration and a session |

The second one also exposed a genuine gap: **nothing tested that a pending
credential cannot authenticate**, because `FinishRegistration` activates in the
same transaction and no pending WebAuthn row exists on any path. That test now
exists, inserting the row directly, with a positive control. All fifteen red.

## What this does not deliver

**DoD item 1 — "registration and authentication work across at least two
browser and platform combinations" — is NOT met, and is not claimed.**

Playwright drives a virtual authenticator through the Chrome DevTools Protocol,
which covers Chromium. Firefox and WebKit expose no equivalent, and a platform
authenticator (Touch ID, Windows Hello) needs real hardware. What ships is the
ceremony verified against a software authenticator and the page verified for
the script and policy it emits.

**The item stays open on the card** with what would close it: two real devices,
or a hosted browser lab. Marking it done on the strength of one engine would be
the kind of claim this project's `docs/PLAN/17` exists to prevent.

Also deferred:

- **Self-service registration** of a passkey — `P3-12`, with the account screen
  and its "requires recent authentication". `BeginRegistration` and
  `FinishRegistration` are built and tested; nothing calls them from outside.
- **WebAuthn as the sole factor** (passwordless). `docs/PLAN/05` calls it a
  later phase.

Not yet on staging: the VM at 10.1.200.13 has been unreachable since the deploy
key was lost with a session scratchpad.
