## A passkey never protected anybody in the running service

The most important thing this task found is not in its own code.

`P3-05` built passkeys, and its tests passed. The framework's `Required` decides
whether to challenge a user by asking the **code-verifier registry** whether it
can answer each enrolled factor type. The service wires the registry with TOTP
only, and wires the passkey ceremony separately as `Framework.WebAuthn`, because
an assertion is not a code and the real verifier does not implement the code
interface. So `Required` skipped every passkey: **a user whose only factor was a
passkey signed in with a password alone**, and a user with both was never offered
the passkey.

Every framework test that involved a passkey had put a *fake* WebAuthn verifier
into the registry — a wiring nothing runs — which is why nothing noticed. It was
found by this task's end-to-end test, the first thing that ever registered a
passkey and then signed in with it in a real browser: the sign-in went straight
through.

Fixed in the framework (a passkey is answerable when the ceremony is
configured), with tests that build the framework exactly as `cmd/authservice`
does, and the old test rewired to match. `P3-05`'s record claimed the challenge
worked; for the deployed wiring it did not, and this record is where that is
corrected.

## A lockout in the forced enrolment

`P3-07` routes a user past the mandate's grace into enrolment, which creates a
pending TOTP factor. The one-TOTP-per-user index covers **pending** rows, and
nothing removed an abandoned one. A user who closed that tab could never begin
again: every later sign-in hit the unique index and answered 500, until an
administrator reset them — a lockout of exactly the people the forced flow exists
to get through. `TOTP.Begin` now replaces an abandoned pending enrolment and
refuses by name when an active one exists. Proven at the login level and in the
store, and each test fails with the fix removed.

## The API nobody's card assigned (PG-42)

`P3-02`, `P3-04` and `P3-05` each deferred "the endpoint" to `P3-12`'s screen.
This tab needed it first, and FR-14 forbids a console-only capability, so it is
built here:

```
GET    /v1/me/mfa                                      the caller's factors
POST   /v1/me/mfa/totp                                 begin (recent sign-in)
POST   /v1/me/mfa/totp/{factor_id}/confirm             confirm (attempt-bounded)
DELETE /v1/me/mfa/factors/{factor_id}                  remove (recent sign-in)
POST   /v1/me/mfa/recovery-codes                       replace (recent sign-in)
GET    /v1/organizations/{org_id}/users/{user_id}/mfa  read-only, ORG_ADMIN
```

The three requirements the earlier tasks carried forward are met here:

- **Recent authentication.** The token's session must have authenticated within
  ten minutes. Past that the API answers a new code, `REAUTHENTICATION_REQUIRED`,
  and the console sends the user through the ordinary sign-in with
  `prompt=login` — which re-checks the password *and the existing factor*, and
  keeps passwords off the Management API. The session is read together with the
  token's user, so a token cannot borrow a colleague's fresh session (tested).
- **Audit.** `user.mfa.enrolment_started`, `user.mfa.enrolled`,
  `user.mfa.removed`, `user.mfa.codes_generated`, through `management.Audit`.
- **Recovery codes with the first factor**, shown once — and never re-issued over
  codes a user already holds.

An administrator has no write here. Being able to add a factor to someone else's
account would be being able to sign in as them; `mfa-reset` (`P3-04`) is the only
administrator write, and it only removes.

## A passkey is registered on the service's origin (PG-43)

WebAuthn binds a credential to the relying party, and `P3-05` made that the
issuer's origin on purpose. The console is a separate deployment on a separate
origin, so a ceremony run in its page is refused by the browser. Registration is
therefore a hosted page, `/account/passkeys`: the SSO session cookie, a recent
sign-in, CSRF, the ceremony state in Redis under a hashed handle and bound to the
session that began it, and a `return_to` accepted only for an origin the named
application registered — otherwise it would be an open redirect on the most
trusted origin in the estate. It is the second scripted page in the hosted flow,
under `PG-40`'s rules.

## The E2E suite had been broken since P3-06

The E2E fixture minted access tokens by presenting the bootstrap refresh token
from `.e2e.env` every time. `P3-06` made refresh tokens rotate, so the first mint
spent it and any later mint was reuse — which revokes the whole family. Every
test after the first mint failed with "the bootstrap refresh token was refused".
Nothing had run the full suite since. The fixture now keeps the current token in
a shared file under a lock, so workers rotate it in turn. All 26 tests pass.

## Smaller findings

- **The generated server ignores `required: false` on a request body**, so
  `POST /v1/me/mfa/totp` with no body was a 400 before the handler. The contract
  now requires `{}` rather than promising what the server refuses.
- **The QR code crosses the API as a module grid**, not an image or SVG markup,
  so nothing that could be read as HTML is inserted into the console and it
  needs no QR library. The secret is always shown beside it as text — the
  accessible alternative, and what a person who cannot scan types.
- **The e2e stack had no MFA seal key**, so nothing in it could enrol. It is
  written into the secrets volume before the service starts.

## What this does not deliver

- **Recovery codes at forced enrolment** (`P3-07`'s flow issues none). Handing
  them over needs an interstitial in the hosted sign-in; `P3-12`'s card carries
  it. The tab shows a user with a factor and no codes a plain warning and the
  generate action.
- **Cross-browser passkey verification** — Chromium's virtual authenticator only,
  as `P3-05` stated for itself.
- **The personal settings screen** — `P3-12`; a user without an administrator
  role reaches this tab through User detail today, where the Profile tab is
  refused to them.

Not yet on staging: the VM at 10.1.200.13 has been unreachable since the deploy
key was lost with a session scratchpad.
