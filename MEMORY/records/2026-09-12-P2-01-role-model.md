## The table already existed

`P0-07` created the full Phase 0/1 schema on 2026-09-08, and `roles` has been in it ever since — `project_id`, `org_id`, `key`, `display_name`, `permission_keys text[]`, `is_builtin`, the unique index on `(project_id, key)`, an `updated_at` trigger and row-level security.

Finding that before writing a migration is the difference between this task and a second, conflicting definition of a role. The spec's first draft proposed a table, a different key shape and a different set of columns; all of it was wrong in the specific way that only shows up as a migration conflict weeks later.

So the work here is the part Phase 0 could not know. The table said what a role *is*. Nothing said what may go in it.

## What the schema gained

**Permission keys have a shape.** `resource:action`, optionally dotted — `user:read`, `billing.invoice:write`. Before this, a role could carry `{""}` or `{"'; DROP TABLE"}`.

**No wildcards**, deliberately. A `*` in a stored permission key is an authorization decision hiding inside a string: every consumer application would have to reimplement the same matching rule and they would not agree on it. If wildcards are ever wanted they belong in `P2-06`'s decision engine, where the matching is written once. The asymmetry decides it — widening the pattern later is harmless, and narrowing it breaks deployed consumer code that cannot be seen from here.

**`org_id` and `project_id` must agree**, as a trigger. The table carried both and nothing made them consistent. A caller inside organization A naming organization B's project would write a role with A's `org_id` and B's `project_id` — and RLS then **hides** that row from B, the organization that actually owns the project. A silently misfiled permission is worse than a rejected write.

The trigger deliberately does *not* use `SECURITY DEFINER`. It runs as the caller, under RLS, so the project lookup can only see the caller's own tenant: a project in another organization is simply not found, and the refusal follows from that rather than from comparing two values we were handed.

**Built-in roles are immutable in the database**, not only in the store — `P1-20` already found `events` writable on staging while the code meant to prevent it read perfectly. Re-keying, deleting, and *clearing the flag* are all refused; the last one because unset-then-delete is a two-step deletion. `display_name` stays editable: what a grant references is `key`, and freezing the label would mean a typo in a built-in role's name could never be corrected.

**The same mistake, twice, five days apart.** The distinctness constraint was first written as `array_length(...) = (SELECT count(DISTINCT k) FROM unnest(...))` — a subquery in a `CHECK`, which PostgreSQL refuses outright. `P1-29` hit this exact wall on `applications.allowed_origins`, and the migration's own comment three lines above says so. Writing the rule down did not stop me repeating it; the integration test did, on the first run.

## One definition of the pattern, not two

`P2-01` step 2 asks for the format to be "documented and shared with the console's form validation". Shared, for a regular expression, usually means copied — and a copied regex diverges the first time somebody widens one side to accept a customer's role name. The divergence is silent in the worst direction: the console accepts what the API then refuses.

So the pattern lives in `openapi/openapi.yaml`, which is already the contract's source of truth (ADR-013), as `PermissionKey` and `RoleKey` schemas. `console/scripts/gen-patterns.mjs` writes `backend/internal/role/pattern.gen.go` and `console/src/lib/api/patterns.gen.ts` from it. `check.sh` regenerates and diffs, exactly as it already does for the generated server interface and API client.

The generator lives under `console/` because that is where `js-yaml` is installed, not because it is a console concern.

**The gate is mutation-tested.** Widening `RoleKey` to accept upper case in the spec turns it red and prints the drifted line. That test caught my own mistake in the process: the first mutation attempt used a string replacement that silently matched nothing, so the gate "passed" against an unchanged file — the same shape of error as the vacuous gate `P1-28` found. An assertion on the replacement is what made the second attempt meaningful.

## Two things the plan says that cannot both be true

`docs/PLAN/08` Part A: *"Roles can be built-in (`org_owner`, `org_admin`) or custom."* Three lines earlier, the same section establishes that roles are per-project.

`ORG_OWNER` and `ORG_ADMIN` are not project-scoped roles. Part C of the same document says they are `manager_roles` — "administrative roles … distinct from application-level roles" — and `docs/PLAN/04` gives them a different table with a different shape. They have been implemented that way since `P1-15`; the `ORG_ADMIN` the console holds today is a `manager_roles` row.

Read literally, Part A asks this task to seed every project with an `org_owner` role carrying permission keys — a second, parallel definition of an identity the service already has elsewhere, and the first place a permission check would consult the wrong one.

**`is_builtin` ships as a mechanism with nothing built in.** `PG-30` records the contradiction; the plan edit goes through the deliberate process rather than through this task. The mechanism is not speculative — `P2-05` and `P4-01` both have reasons to want a role an organization cannot remove — and the immutability test keeps it honest by exercising it on a row the test marks itself.

## Decisions worth naming

**`admin` is not reserved.** It is the single most natural name a consumer application will reach for, and reserving it to prevent a confusion nobody has yet would trade a real need for a theoretical one. What *is* reserved is the five `manager_roles` values in lower case: a project role keyed `org_admin` would arrive in a token beside a manager role of the same name meaning something else entirely, and the consumer reading it would have no way to tell which it got. There is a test asserting `admin` stays allowed, because the absence of a rule is the kind of decision that gets quietly reversed.

**Duplicate permission keys are refused, not folded.** Silently de-duplicating means the stored row does not match what the caller sent, and they find out from a later read instead of from the write that was wrong. The error names the index of the second occurrence *and* where the first one was.

**The key is not updatable by anyone** — not merely for built-in roles. Grants reference roles by key with no foreign key to cascade, so re-keying would silently orphan every grant holding the old one. That is a rename that removes access, which is precisely the failure the card's step 5 is about.

**Roles list ordered by key**, unlike every other list in this API. A role list is read as a reference table, and somebody looking for `billing-admin` should not need to know when it was created.

The mutations, because a suite that has only ever been green has not been shown to test anything:

| Reverted | Went red |
|---|---|
| The org/project trigger | `TestARoleCannotBeWrittenIntoAnotherOrganizationsProject` |
| Built-in immutability | `TestABuiltinRoleCannotBeDeletedOrReKeyed` |
| The permission-key constraint | `TestTheConstraintIsAttachedToTheTable` |
| The delete refusal | `TestDeletingAReferencedRoleIsRefused` |

And one test exists only to keep two implementations honest: `TestTheDatabaseAgreesWithTheValidator` feeds nineteen cases to the Go validator and to the SQL function and fails if they disagree. Without it the pair drifts silently, and the drift produces a 500 for input the API said was fine.
