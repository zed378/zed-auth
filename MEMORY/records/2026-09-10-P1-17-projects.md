# P1-17 — Management API: Projects

**Date**: 2026-09-10
**Branch**: `feat/P1-17-projects`
**Spec**: none — the card is `Spec required: No`, and nothing here touches authentication, credentials or the data model. The schema `projects` needs already shipped in `P0-07`.

---

## What this is

Five operations on projects, under the organization that owns them:

```
GET    /v1/organizations/{org_id}/projects
POST   /v1/organizations/{org_id}/projects
GET    /v1/organizations/{org_id}/projects/{project_id}
PATCH  /v1/organizations/{org_id}/projects/{project_id}
DELETE /v1/organizations/{org_id}/projects/{project_id}
```

No migration. `projects` has existed since `P0-07` with its RLS policy, its per-tenant unique index and its `ON DELETE RESTRICT` references from `applications` and `roles`. This task is the API in front of a table that was already correct — which is why the whole thing is 352 lines of handler, 264 of store, and 669 of test.

## The tenant is a shape, not a check

The card's step 2 says "never trust an `org_id` supplied in the body". The usual way to satisfy that is a comparison: read the body's `org_id`, compare it to the path's, refuse a mismatch. That is a check somebody can forget to write on the sixth endpoint.

**`store.go` has no `org_id` parameter in it anywhere.** `Create` reads the organization from the transaction's own scope (`tx.OrgID()`); every other query is a plain statement with no tenant predicate at all, because `WithTenant` has already confined the transaction and `org_id = current_org_id()` does the filtering in the database. There is nothing to trust because there is nowhere to put it.

That also makes the RLS test honest. `TestAnotherOrganizationsProjectIsUnreachableEvenWithTheRightRole` asks for another tenant's project id *through the caller's own organization's path* — so `Authorize` allows the request, and the only thing between it and the row is the policy. Had the store carried its own `org_id = $1` predicate, that test would pass whether or not RLS existed, which is the vacuous shape again.

This is the difference from `P1-16`: `organizations` is the one table whose policy is keyed on `id`, so listing and creating needed `SECURITY DEFINER` functions. `projects` is an ordinary org-scoped table and needs none.

## Cross-organization access, refused twice

The card asks for it "verified at both the RLS and application layers", and the two are tested separately because each one alone would pass against a broken system:

| | The claim | What would break it |
|---|---|---|
| Application layer | A caller with no role over the organization in the path is refused | `TestACallerWithNoRoleOverTheTargetIsRefusedBeforeAnyQuery` — 404, not 403, so an id cannot be probed |
| RLS | A caller *with* the right role still cannot reach another tenant's row | `TestAnotherOrganizationsProjectIsUnreachableEvenWithTheRightRole`, and `TestTheStoreCannotReadAcrossTenants` with no HTTP layer at all |

Each carries its control: the same request for a project that *is* the caller's succeeds, and the owning tenant can read the row the other one could not. Without those, both tests pass against a service that refuses everything.

## Deletion refuses, and says what blocks it

A project with applications or roles attached gets a `409` whose `details` carry the counts: `applications: "2 still belong to this project"`. Not cascaded, and not the database's error message.

- **Not cascaded** because deleting a project would take every OIDC client in it, and every consumer application configured against those client ids would stop authenticating. That is a far larger consequence than `DELETE /projects/{id}` appears to ask for.
- **Not the foreign key's error** because "violates foreign key constraint applications_project_id_fkey" is not something to put in front of an administrator, and it cannot say *how many*. The count runs first and the refusal is explicit. The FK is still there and still `RESTRICT` — it is the guarantee; the count is the explanation.
- **The counts disclose nothing** the caller could not already list, since reading them requires `ORG_ADMIN` over the same organization.

`Delete` still handles the constraint violation, for the case where something is attached between the count and the delete. Same refusal rather than a 500, with a detail saying so.

`TestOnceEmptiedAProjectDeletes` is what stops "delete is refused" from meaning "delete is broken": the same project deletes as soon as its application is gone.

**Hard delete, not soft.** `organizations` got a `deleted_at` in `P1-16` because an organization *is* a tenant boundary and owns audit history that must outlive it. A project owns neither: its audit events carry `org_id`, and `events` has no foreign key on any of this by `P0-12`'s decision, so the trail survives the row without a tombstone.

## `PROJECT_OWNER` is reserved and grants nothing

Card step 4. The role already existed in `management.Role` from `P1-15` and in the manager-role schema from `P0-07`. What this task adds is the test: a caller holding `PROJECT_OWNER` gets `403` on every project endpoint, and the same caller with `ORG_ADMIN` gets through — so the refusal is about the role rather than about the fixture.

Reserving it now means Phase 2 grants an existing role rather than introducing one, and nothing between now and then can accidentally make it mean something.

## The permission table

Five new rows in `management.Policy`, all `ScopeOrganization`:

| Route | Role |
|---|---|
| `GET`, `POST` `.../projects` | `ORG_ADMIN` |
| `GET`, `PATCH` `.../projects/{project_id}` | `ORG_ADMIN` |
| `DELETE .../projects/{project_id}` | `ORG_OWNER` |

`DELETE` is the only destructive one and the only one raised. An `ORG_ADMIN` refused a delete gets `403` rather than `404` — they can plainly see the project, so hiding it would be a lie rather than a control.

`TestEveryV1RouteHasADeclaredPermission` (from `P1-16`) covers the five new routes without being told about them: it walks what the router actually registers, so an endpoint added without a permission fails before anybody notices it is unreachable.

## Audit

Three event types, written inside the same transaction as the change: `project.created`, `project.updated`, `project.deleted`. The rename event records the previous name, or the log cannot answer "what was this project called last week".

**A rename to the same name writes nothing.** An audit log full of "renamed Billing to Billing" is one nobody reads, and a log nobody reads is not a control. Tested in both directions — the three lifecycle events are asserted present, and the no-op rename asserted absent.

`P1-15`'s `auth_management_unaudited_mutations_total` covers the inverse: a mutating handler that writes no event increments a counter that should be permanently zero.

## Small decisions worth keeping

- **A `PATCH` with no `name` is a `200`, not a `400`.** It changed nothing, and a request that changes nothing is not malformed.
- **Name uniqueness is per organization and case-insensitive** — `projects_org_name_key` is on `(org_id, lower(name))`. "Billing" and "billing" in one tenant is a support ticket waiting to be filed; the same name in two tenants is ordinary, and making it global would leak which names other customers use.
- **Names are trimmed before they are stored,** so `"   "` is a blank name at the handler rather than a `CHECK` violation at the database. The `CHECK` stays as the backstop, and `wrapConstraint` translates it if it is ever reached.

## Found while building it

**A required dependency that only one caller knew about.** `httpserver.New` now panics if `V1` is configured without a `ProjectAPI` — the same guard `P1-16` added for `Organizations`, and right for the same reason: `apiRoutes` embeds both interfaces, so a nil one is a panic on the first request to a route that is already registered. Failing at boot beats failing at 3am.

The cost is that it made `P1-16`'s integration harness panic on every test. That harness builds a real server with a real `/v1` chain, and it had no reason to know projects exist. `check.sh` caught it; `go build` could not, because the harness is behind a build tag and the failure is at runtime.

So the guard is kept and the harness now names the project handler, with a comment saying why. **This is friction that grows**: `P1-18`'s applications and `P1-19`'s users each add a required field that every existing endpoint package's harness has to name. Worth watching — if it becomes four packages naming five handlers, the shape is wrong, and the fix is a shared constructor for `Deps` rather than a weaker guard.

## Verification

- **Integration, 20 tests** against real PostgreSQL and real Redis, through the generated router and the real `/v1` chain, with tokens from `P1-07`'s own claim builder: every permission boundary and its control, cross-organization refusal at both layers, an `org_id` in the body having nowhere to land, deletion refused with counts and then succeeding once emptied, per-tenant case-insensitive naming, the three audit events and the one that is deliberately absent, and a full walk of the paginated list seeing each project exactly once.
- **Unit**: the route-coverage tests in `internal/httpserver` walk what the router actually registers and check both directions against `management.Policy` — every route has a permission, and no permission names a route nobody serves.
- **Six mutations, all killed.** Row-level security disabled on `projects` (three tests), the dependents check removed from `Delete`, the no-op-rename short circuit removed, and `DELETE` lowered to `ORG_ADMIN`. Each run asserts the named test actually ran, because `go test -run` prints `ok` when its pattern matches nothing — which is how a mutation harness reports a survivor for a test that never executed.

## What this does not do

- **No console screen.** `PF-*`/`P1-22` owns that; this is the API only.
- **`projects` carries no settings of its own,** deliberately. An application already has its own configuration and an organization's policy already applies to everything inside it — a third home for settings would be a third place to look.
