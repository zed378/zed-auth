## What this was supposed to be

Fill in `docs/PLAN/11`'s pyramid for Phase 1: unit, integration, end-to-end, security; add fuzz tests for JWT parsing; wire it all into CI; confirm the coverage floors.

## What it actually was

**An end-to-end environment, and the four production bugs it found in its first hour.**

Every one of those bugs had passed every other layer of testing. Not because the other layers were careless — the unit tests are thorough, the integration tests run against real PostgreSQL and Redis, and the coverage floors are enforced — but because **they all drive the service with `curl`, and `curl` enforces no browser rules.**

A harness that cannot enforce browser rules cannot find browser bugs. A suite made entirely of such harnesses reports a green login flow that no person can use. That is the sentence this task is about.

## The environment

`scripts/e2e-up.sh`, one command: the stack, migrations, a signing key, the bootstrap, a management token obtained through the real hosted login page, both demo applications registered **through the Management API**, both running, and the console built against the client it just created. `scripts/e2e-down.sh` takes it away and verifies that it did.

Nothing reaches into the database except the bootstrap — the instance, the organization, the first administrator and the console's own client, which no published endpoint can create (`PG-26`). Everything after that goes through the API, because a suite seeded past its own API proves nothing about the API.

The same script runs in CI, in a job of its own. The E2E step used to live in the console job, where it had no service to talk to and failed every time — which is how it came to be ignored.

## The four bugs

**1. The hosted login page could not log anyone in, in any Chromium browser.**

`form-action 'self'`. Chrome enforces `form-action` against the **redirect chain** a submission produces, not just the action URL — so the POST to `/login` was permitted, the service answered `302` to the application's registered redirect URI, and the browser refused to follow it. The page sat there with the fields still filled and one console message.

The policy now names the registered redirect origin alongside `'self'`. The logout interstitial had the identical bug for the identical reason.

**2. No public client could complete a login at all, and the console could not call the API.**

No CORS. The code exchange is a `fetch` from the application's own origin and the browser refuses it before the request is sent. `PG-17` had forecast this in Phase 0 and written a rule — *no endpoint may add CORS headers to unblock a caller* — which made it a decision to raise rather than make. Raised, authorized, and built as [`P1-29`](./2026-09-11-P1-29-cors.md).

**3. Every role-gated console screen refused everybody, including an organization owner.**

The console gates on a `roles` claim. The service does not issue one until `P2-04` — the claim namespace is reserved and served empty — so `hasRole` was always false, and `/users`, `/projects` and `/audit-log` were unreachable for every account that has ever existed.

The bug was reading "absent" as "none". Those are different answers and the code now says so: `Claims.roles` is `string[] | null`, and `null` means the token told us nothing. `hasRole` then defers to the API.

Deferring is also the right default beyond this window. `CLAUDE.md` puts enforcement server-side and permits the console to hide controls "for UX purposes" only. The failure modes are not symmetric: showing a screen the API refuses costs one clear message that every screen already renders; hiding a screen the API would have allowed removes a capability from someone entitled to it, silently, with nothing anywhere saying so.

**4. Every preflight answered `405`.**

CORS was registered as route-level middleware. The generated router registers `GET`, `POST`, `PATCH` and `DELETE` and never `OPTIONS`, and chi's method-not-allowed path does not run route-level middleware — so every browser request carrying an `Authorization` header failed at the preflight, before the real call was attempted. It is on the main router now, ahead of routing.

## Proving the suite can fail

`P1-27`'s fourth DoD item asks for "a deliberately-reverted security control causes a red build, demonstrated once". Once is not enough, so `scratchpad/mutate-p127.sh` reverts six in turn:

| Reverted control | Build |
|---|---|
| The algorithm allowlist admits `none` and HMAC | red |
| Redirect URIs matched by prefix instead of exactly | red |
| Every origin may read personal data | red |
| The public wildcard applied to every path | red |
| The login form may post a password to any origin | red |
| A token minted for another audience may administer the platform | red |

**Six for six — after one stayed green and taught something.**

Reverting `allowedAlgorithms` to include `none` and `HS256` left every test passing. go-jose refuses an unsigned JWS on its own, refuses an HMAC algorithm against an RSA key set, and reports both in a way this package maps to `ErrAlgorithmNotAllowed` either way. **The protection is real, doubly held, and completely invisible through `Verify`** — so no black-box test could ever have covered it, and the one named `TestAlgNoneIsRejected` was passing for a reason other than its name.

The allowlist is now asserted directly, which is the only thing that makes widening it a reviewed edit rather than a line somebody adds to make a third-party token work.

## Fuzzing

`FuzzVerify` over the token parser, seeded with the shapes that have historically broken JWT parsers: `alg: none`, algorithm confusion, 200-deep nested JSON, a 100KB token, a 10KB `kid`, invalid base64url, and a multi-signature JWS.

Two properties, for every input: it never panics, and it never returns a payload for a token this service did not sign.

**944,501 executions, 169 new interesting inputs, no crash and nothing forged accepted.**

## Found while building the environment

Each of these is a state nothing reported:

- **A fresh database has no `instances` row**, and `organizations.instance_id` is `NOT NULL` with no default. Nothing creates the first one.
- **`docker compose up` against an existing volume starts a service on a schema of any age.** This stack was ten migrations behind; the only symptom was "this application is not registered" from an endpoint whose lookup function did not exist yet, and `/readyz` was green throughout.
- **The local stack had no signing key and nowhere to put one.** The service starts, reports healthy, and fails only when something asks it to sign — which is the token endpoint, which is the first thing any consumer touches. `keyctl` now ships in the image, so the tool and the service agree on where the private half lives by construction; the rotation runbook's hand-built binary and bind mount is what that replaces, and it had already gone wrong once.
- **`go run` cannot be stopped by pid.** It compiles to a temporary binary and execs it as a child, so the recorded pid is the wrapper's. Killing it left the servers holding their ports, and the next run started a demo that could not bind, exited, and left the *previous* one answering with a `client_id` the wiped database no longer had. The demos are built first now, and `e2e-down.sh` verifies the ports are free rather than reporting success.
- **`127.0.0.1` and `localhost` are different sites.** The console's silent renewal is a `prompt=none` iframe against the issuer, and a third-party iframe receives no `SameSite=Lax` cookie — so a console at `127.0.0.1:4173` against an issuer at `localhost:8080` could never renew. ADR-019 assumed same-site and did not say so; deployed, both live under one registrable domain.
- **Post-logout URIs are exact-matched too**, and `window.location.origin` carries no trailing slash. Registering only the slashed form produces a sign-out that refuses with "an address it has not registered".

## Tests that were wrong, not code that was wrong

Three, and all three had never run:

- `login.spec.ts` asserted the console redirects to the hosted page on a deep link. It shows its own sign-in page with an explicit button — which is better: a deep link that silently throws the browser at another origin is a navigation nobody asked for, and indistinguishable from a redirect loop when it goes wrong.
- `shell.spec.ts` clicked into screens that had no authentication when it was written at `P0-17`.
- My own SSO assertion looked for `/oauth/authorize` in the navigation events. A `302` is never committed as a document, so it appears in none — the trip through the provider has to be asserted on requests. It reported that single sign-on had not happened while the page behind it was plainly signed in.

## Where it stands

Twelve end-to-end tests, all passing in a real browser: sign-in, silent renewal, sign-out genuinely ending the session, a deep link, an API-driven permission refusal, single sign-on across two applications, sign-out of A ending B's session, and application B refusing a token minted for another application.
