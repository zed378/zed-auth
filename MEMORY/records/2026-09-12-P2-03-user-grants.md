## The row that actually grants access

`P2-01` defined what a role is. This is what hands one out, and until now nothing in the system gave anybody access to anything.

## Least privilege is an absence, so the test asserts one

`docs/PLAN/08` § Least Privilege, and `docs/PLAN/17`'s Phase 2 criterion verbatim: a new user has no access until explicitly granted, with no implicit or default role.

There is no code implementing that. It is true because nothing writes a grant except these four endpoints, and a user with no row has no roles. Which is precisely why it needs a test: a future "give new users a default role" convenience would break it and no existing assertion would notice. `TestAUserWithNoGrantHasNoRoles` checks the store and the API, and both answer *empty* rather than *error* — having no access is an ordinary state for a new account, and making it exceptional pushes every caller into treating the normal case as a failure.

## A grant that names a role which does not exist

The failure this prevents is quiet in the way that matters. The row looks like access. The token carries a key nothing defines. Every consumer checking for it denies. And nothing anywhere explains why — there is no error, just a permission that does not work.

Refused by a trigger as well as by the application, because the application is not the only writer, and the trigger **names the offending key**. "One of your role keys is invalid" sends an administrator to guess, and a script usually sent several at once.

Pulling that key back out means parsing the trigger's message, which is unpleasant. The alternative is a second round trip asking which key was missing, which can disagree with the write that just failed.

## The Phase 4 slot, closed rather than absent

`user_grants.project_grant_id` distinguishes a delegated grant from a direct one, and `docs/PLAN/08` Part C requires a delegated grant's role keys to be a **subset** of the delegation's `granted_role_keys`, revalidated on every request. That is the most security-critical check in the system, and it belongs to `P4-01`.

The card asked for the hook point to exist now so Phase 4 fills a designed slot rather than retrofitting. So the refusal is a **trigger whose body Phase 4 replaces**, not a `CHECK (project_grant_id IS NULL)` that Phase 4 would have to drop. The difference is a window: dropping a constraint before adding the real check leaves a period where any delegated grant is accepted. Replacing a function body does not.

`TestADelegatedGrantIsRefusedUntilPhaseFour` is written to be **inverted** in Phase 4, not deleted, so the diff shows a rule changing rather than a guard disappearing. It writes directly to the table, because no API accepts the column at all — that is the first line of defence and the test has to reach past it.

## Self-service escalation, which no scope can express

An `ORG_ADMIN` administers every user in their organization. They are one of those users. So the permission model says yes to an administrator granting themselves another role, and the answer should be no — `docs/SECURITY/02` §3's vertical escalation is exactly the administrator who gives themselves one more role than they were given.

Refused in the handler, because there is no role requirement that says "not this one user". **Revocation is deliberately not covered**: it can only reduce what somebody holds, and refusing it would mean an administrator who wants to drop a privilege has to find a colleague.

## Two decisions recorded rather than assumed

**These routes are `ORG_ADMIN` over the organization, not `PROJECT_OWNER` over the project** — despite `P2-02` setting the project-scoped precedent one task earlier. The path is `/users/{user_id}/grants`, so the route is about a *user*: a project-scoped caller who could reach it would be able to enumerate the organization's users one grant request at a time. A narrower role buying a wider read. When `P2-12`'s console needs the project side of the same data, it gets a route that lists a project's grants.

**Re-authentication for sensitive grant changes is Phase 3**, which the card explicitly asked to decide. MFA itself is `P3-01`, and a re-authentication prompt with no second factor behind it is a password re-entry: friction without assurance. The `amr` claim `P1-11` already emits is what Phase 3 will read.

**The fourth mutation was green at first, and the reason is worth keeping.** Removing the application's empty-set check changed nothing, because the table's own `CHECK` refuses an empty `role_keys` too — defence in depth working exactly as intended, and a test that could not tell the two layers apart. What the application layer actually adds is the sentence telling the caller what to do instead ("to remove access, delete the grant"), so that is what the test now asserts. A status code alone could not have distinguished them.
