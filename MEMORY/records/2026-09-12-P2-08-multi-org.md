## Mostly a verification task, and it found a real hole

The schema has carried multi-tenancy since Phase 0 and `docs/PLAN/02` promised a second organization would need no migration. Step 1 asks for that promise to be *verified* rather than assumed, which is the right instinct — and verifying it turned up something the promise did not cover.

## `applications` had no rule saying its organization owns its project

Four tables carry both an `org_id` and a `project_id`. `P2-01` added the agreement trigger for `roles`; `P2-03` added a near-identical one for `user_grants`. **`applications` and `project_grants` had nothing.**

`applications` is the one that matters. It holds every OIDC client, it has been writable since Phase 0, and the failure is the quiet kind: both ids are real, so nothing rejects the write, and row-level security then **hides** the row from the organization that actually owns the project. An application nobody can see. A login nobody can account for.

Confirmed by mutation rather than asserted: dropping the new trigger makes `TestNoRowCanReferenceAnotherOrganizationsProject` report *"applications accepted a row pointing at another organization's project"* — which is the state the table was in this morning.

`project_grants` gets the rule before it has any rows, because a delegation filed under the wrong organization is the worst instance of this bug: crossing an organization boundary is what the row is **for**, so a mistake looks like the feature working.

## One function, and the no-op it nearly became

Two copies of an invariant is a coincidence; four is a pattern that drifts. So the three per-table functions collapse into one `org_must_match_project()` that reads `NEW` through `to_jsonb`.

The first version read only `org_id` — and `project_grants` names its columns `granting_org_id` and `granted_org_id`. Attached to that table it would have found no organization, returned `NEW`, and enforced **nothing**: a trigger that looks present and is a no-op, which is worse than an absent one because it answers "is this checked?" wrongly.

It now reads both names, and **raises** if it finds a `project_id` with no organization column it recognises. Silence there is exactly how the no-op would have gone unnoticed.

## The architecture test, and what it can honestly claim

Step 3 asks for a test that "fails if a repository method can execute without tenant context". It cannot forbid the bypass outright: six reads genuinely happen *before* a tenant is known — resolving a client id, a refresh token, a session cookie. Each is the read that **decides** which tenant the request belongs to, so requiring a tenant first would be circular.

What it can do is make every one deliberate. `postgres.DB.SQL()` is the unscoped handle, and the test pins the list of files that use it with a reason for each. A seventh appears in a diff with a justification beside it rather than as a convenience somebody reached for at 5pm.

It fails in **both directions**, which is the part worth having: a new bypass, and an exception listed for a file that no longer bypasses anything — an unchecked exception is just as much rot as an unchecked bypass. Both proven by planting them.

## Every filter combination on the audit log

A filter is a `WHERE` clause, and a `WHERE` clause is where tenant scoping gets lost. The test generates the combinations from a list of clauses rather than writing them out, because a hand-written list covers the ones somebody thought of.

It only combines **distinct** parameters. Repeating a non-repeatable one is correctly a `400`, and folding that into the test would mean tolerating a status that might one day hide a real error.

And it asserts the caller can still read their **own** history, because every isolation assertion above is satisfied by an endpoint that returns nothing at all.

## The deferral, kept

`docs/PLAN/01` puts one user belonging to multiple organizations out of scope, and step 5 says to keep it that way. Nothing here builds workspace switching for a single identity. `P2-13`'s switcher is for an administrator holding manager roles in more than one organization, which is a different thing — `manager_roles` has no `org_id` and is read outside any tenant precisely so that works.
