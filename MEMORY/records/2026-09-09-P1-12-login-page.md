# P1-12 — The hosted login page

**Date**: 2026-09-09
**Branch**: `feat/P1-12-login-page`
**Spec**: [`MEMORY/specs/P1-12-login-page.md`](../specs/P1-12-login-page.md)

---

## What this is

The page a human types a password into. `P1-06` issues codes, `P1-07` exchanges them, and until now neither was reachable by a person — the authorization endpoint redirected to `/login`, and `/login` was a 404. With this the protocol loop closes: a person can complete a login end to end. The capability audit still says single sign-on has not shipped, and it is right — see below.

Three routes, all HTML, all served by the auth service itself:

```
GET  /login?request=<id>   the form
POST /login                verify, create a session, resume the authorization
GET  /login/forgot         FR-9's entry point
```

No console change. That is step 1 of the card and it is load-bearing rather than incidental: signing in must not depend on the console being deployed, reachable, or working.

## The property everything else is arranged around

**A wrong password and an address with no account must be the same answer** — in the body, the status, every header, and the time taken.

It is easy to satisfy by accident and just as easy to lose by accident, so it is not left to discipline:

- The message is a named constant, `MsgCredentials`, used for a wrong password, an unknown address, a locked account, a deactivated one, and an account with no password set. Five conditions, one constant, so a future edit that wants to be more helpful about one of them has to change the thing all five share.
- The equal-cost path lives inside `authn.UserStore.Authenticate` rather than at the call site. A caller that looked a user up and then decided whether to verify would be a caller that returns early on the not-found path, and the early return is the disclosure.
- The status is `200` for every credential failure — the form, re-rendered. A `401` would be fine too; what matters is that it does not differ *between* the failures.

### How it is tested, and why the obvious test would not have done

The integration test submits **the same address twice** with the same wrong password, and deletes the account in between:

```
POST alice@example.test + wrong  →  response A   (account exists)
DELETE FROM users …
POST alice@example.test + wrong  →  response B   (account does not)
assert A == B   status, every header, body, byte for byte
```

The obvious version — submit a known address and an unknown one, compare — cannot work, because the page echoes the address back into the form so a typo need not be retyped. The two bodies would differ for a reason that discloses nothing, and the comparison would have to be loosened, and a loosened comparison of two error pages passes against almost anything. Holding the address fixed and varying only the account's existence makes any difference a difference the account caused.

Two consequences fell out of wanting that test to be strict:

- **The stylesheet is whitelisted by its SHA-256 hash, not a nonce.** A nonce changes every response, which would make "byte-identical" impossible to state, let alone assert. The hash is also the stricter policy — it authorises one exact block of CSS rather than whatever the server put a nonce on.
- **A failed submission does not re-issue the CSRF cookie.** It reuses the one the request carried, so no `Set-Cookie` header appears on either response. Re-issuing would have been harmless and would have made the two responses differ in a header, which is exactly the kind of difference a hand-written list of headers to compare would have skipped.

The header comparison dumps *every* header in sorted order rather than checking a list. `Content-Length` is in there, and it is the one a list would have forgotten.

## The seam back into the OAuth flow

`P1-06`'s handler gained two exported methods and its store gained one:

```go
func (h *Handler) Peek(ctx, id) (Pending, error)                    // read, no consume
func (h *Handler) Resume(w, r, id string, current session.Session)  // consume, issue, redirect
func (s *Store) PeekPending(ctx, id) (Request, error)               // GET, not GETDEL
```

`Resume` deliberately does **not** re-parse parameters, re-check the client's grant types, or re-match the redirect URI. All of that happened in `ServeHTTP` before the request was stored, on the values that were stored. Doing it twice would put the exact-match rule in two places, and two places is how one of them ends up subtly different.

What it does do is consume — this is the single-use point — and check that the session's organization is the client's. That check is unreachable through the login page, which authenticates against the organization it read from the same client; it is there because it costs one comparison and the failure it prevents is a code issued across tenants.

### The `PeekPending` / `LoadPending` split, which was nearly a bug

`LoadPending` is a `GETDEL`, and that is correct: a resumable-twice request would let one login satisfy two authorization flows. The first version of the login handler called it on every POST.

That would have given **every account exactly one attempt at its password**. Type it wrong once and the pending request is gone; the retry gets "this sign-in has expired", and the user is at a dead end with no way back to the application, because the whole point of the opaque reference is that the destination is not in the URL. It would also have broken a page refresh and the back button.

So the read is free and the *success* consumes. Single-use still holds where it matters — exactly one code per pending request, still atomic, since `LoadPending` is called once immediately before `IssueCode`. Two concurrent successful submissions race on the `GETDEL` and exactly one wins.

Both halves are covered by tests that fail when the other implementation is substituted: turning `PeekPending` into a `GETDEL` breaks the retry test; turning `Resume`'s `LoadPending` into a `PeekPending` breaks the single-use test.

## PG-16 — branding was specified, designed, half-built, and had nowhere to live

`PLAN/01` puts per-organization branding in scope. `UI-UX/05` bounds it precisely — the accent and a logo, never `color-danger` or `color-warning`, so that red keeps meaning "irreversible" in every tenant. `UI-UX/08` gives it a settings screen. `P0-17` already implemented the applying half in `console/src/branding/branding.ts`, carefully, as a closed union of overridable tokens.

And `PLAN/04` § `organizations` has `settings jsonb` whose four documented keys are `password_policy`, `mfa_required`, `session_lifetime_hours` and `allowed_login_methods`. Branding is not among them, and no other column or table holds it.

Closed with **no schema change**, by specifying `settings.branding`:

```json
"branding": { "logo_url": "https://…", "accent_color": "#1d4ed8" }
```

A separate `organization_branding` table was considered and rejected: one row per organization holding two nullable strings, joined on every login page render, for data that is by definition per-organization configuration. The gap was never a missing column — it was a missing specification, and each reader inventing a shape is what the entry prevents. `PLAN/08` Part B should be amended.

`ParseBranding` is exported and pure so that `P2-14` validates on write with the same rules that apply on read. A value the settings screen accepts and the login page silently discards would be a control that appears to work.

Two validators do real work rather than decorative work:

- **The accent must be `#rgb` or `#rrggbb`.** Named colours, `rgb()` and `hsl()` are all valid CSS and are refused, because the value is interpolated into a stylesheet and the set of strings that are *safe* there is far easier to state than the set that is valid. `#1d4ed8;}body{display:none` is refused by the same rule, and `renderStyle` re-checks before interpolating because it is the last point before the value becomes CSS.
- **The accent must reach 4.5:1 against white.** It is a button background with white label text on it. A pale brand colour produces a primary action nobody can read, on the page where not finding the button means not signing in.

**Nothing writes it yet.** `P2-14` makes it editable; today every organization renders unbranded. Stated here rather than left to be discovered when a logo does not appear.

## Abuse case A-7, answered structurally

Reflected XSS through `error` or `state` is on the card. `html/template` would escape them correctly, and the page still renders **no query parameter at all** — there is no field on the `Page` struct that could carry one. An error is selected from a fixed table by a known key, so the worst a crafted URL can do is choose a message we wrote.

The test submits `error`, `error_description`, `state`, `redirect_uri` and `next` with distinctive markers and asserts none appears, with a control assertion that the form actually rendered — without which it would pass against an error page.

## What else this task produced

- **`authn.UserStore`**. The credential lookup, with the stored hash never leaving the file: `Authenticate` takes the password and returns a decision, because a hash on an exported struct is a hash that eventually gets logged. It is where `P1-01`'s `VerifyDummy` and `NeedsRehash` finally acquired callers — `NeedsRehash` because login is the only moment the plaintext and the stored hash are both available.
- **Rehash-on-login does not touch `password_changed_at`.** The password did not change, only the cost of storing it did, and moving that column would silently reset every user's expiry clock on the day the parameters were raised.
- **`prompt=login` revokes the session this browser was carrying**, with `session.ReasonReauth` — a constant `P1-11` defined and nothing called. The cookie is about to be overwritten, so what it pointed at becomes unreachable, and an unreachable *live* session still appears on the sessions screen and still authorises a refresh token. Every other session the user has is untouched, which is what `/oauth/authorize` already says `prompt=login` means. A session belonging to a *different* user in the same browser is also untouched — two accounts, one of which asked for nothing.
- **A coverage floor for `internal/login`**, plus the tests needed to keep `internal/authn` and `internal/oauth/authorize` above theirs once this task's code landed. Both dropped below 80% the moment the new files appeared; both were closed with tests rather than by lowering the floor.

## The capability audit fired, and was right twice

`check-claims.mjs` failed the moment `P1-12` was marked done:

> "Single sign-on" is labelled "Phase 1" but every task it needs (P1-06, P1-07, P1-12) is DONE — it has shipped, and describing it as planned is now the inaccuracy

It had not shipped. The **protocol** is complete; the **capability** is not. A visitor cannot register an application (`P1-18`) or create a user with a password (`P1-19`), so there is nothing to sign in to and nobody to sign in as. "A consumer can complete a login" was being measured against a database somebody had populated by hand.

That is the same lesson the audit already carries in a comment — it was written when `P1-06` alone made it declare SSO shipped — arriving a second time, one layer out. The list has to encode *usable by a visitor*, not *implemented*, because that is what a capability card promises. Fixed by extending the task list to `P1-06, P1-07, P1-12, P1-18, P1-19`, not by relabelling the card.

Fixing it exposed a second, quieter problem. The check asked whether the string `"Phase 1"` appeared **anywhere on the page**, and two cards carry that label — so deleting the label from one of them would have passed. It now extracts each capability card and looks for the label inside the card it belongs to. Demonstrated by removing the label from the Single sign-on card alone and watching it fail, which the previous version did not.

## Decisions worth disagreeing with

**The routes are not in `openapi/openapi.yaml`.** The spec's first draft said they should join it "for the same reason `/oauth/authorize` did", and that reason does not carry. `/oauth/authorize` is in the contract because an integrator builds its URL and reads its redirect. Nobody ever calls `/login`; a browser is its only client, it is reached only by a redirect this service issues, and its form fields are an implementation detail. `PLAN/20` renders `/docs/api-reference` straight from the spec, so putting it there would publish an endpoint to integrators that has no stable contract and that no integrator should touch. Nothing checks the reverse direction, so this is a decision rather than a rule being evaded, and it should be revisited if a served-surface audit is ever added.

**A failed login does not record the address that was tried.** Including it would make credential-stuffing forensics much easier. It would also write every mistyped and every probed address into an append-only table with 24-month retention — turning the audit log into a list of addresses somebody tried, which is the artefact an attacker who reaches the log most wants, and one the people in it never consented to. `P1-13`'s rate limiting keys on the address in Redis with a short TTL, which is where that data belongs. The audit log *does* record a reason class (`wrong_password`, `account_locked`, `credentials`), because the audit log is not the response body and an operator investigating an account needs it.

**The metric label is coarse.** `auth_login_attempts_total{outcome="failed"}` covers a wrong password, an unknown address and a locked account alike. Separating them would move the enumeration disclosure from the response body into `/metrics`, which is scraped, retained, and usually more widely readable than the audit log.

## Verification

Nine mutations, each reverted, each confirming a test fails when its control is removed:

| Control removed | Test that failed |
|---|---|
| `frame-ancestors 'none'` from the CSP | `TestTheLoginPageCannotBeFramed` |
| a locked account gets its own message | `TestEveryCredentialFailureLooksTheSame` |
| the same, against a real database | `TestALockedAccountIsIndistinguishableFromAWrongPassword` |
| an unknown address answered differently | `TestAWrongPasswordAndAnUnknownAccountAreByteIdentical` |
| the CSRF check skipped | `TestSubmissionRequiresACSRFToken` |
| `VerifyDummy` skipped on the not-found path | `TestTheUnknownAddressPathCostsTheSame` |
| `Resume` peeks instead of consuming | `TestASuccessConsumesThePendingRequest` |
| `PeekPending` implemented as `GETDEL` | `TestAFailedAttemptCanBeRetried` |
| a query parameter rendered onto the page | control assertion inside `TestNothingFromTheQueryStringIsRendered` |

Keyboard-only completion was checked in Chromium against the bytes the handler serves: focus lands on the error summary (`autofocus` on a `tabindex="-1"` element, which is how focus moves without script), Tab reaches email → password → Sign in → "Forgot your password?" in that order, and Enter from the password field submits. `document.scripts.length` is 0.

That last check needs the rendered page in a browser, so `dump_test.go` writes it to a path given in `AUTH_DUMP_PAGE` and skips otherwise. It is not a test; it is the fixture that makes the accessibility claim re-checkable rather than a thing somebody asserted once.

**Automated checks do not establish accessibility.** Labels, contrast and focus order are the parts that can be asserted; `PF-50`'s audit still owns the claim.

## What is still missing

- **Nothing can create a user with a password.** `P1-19` owns user management, so on a fresh deployment this page is complete and has nobody to let in. The same "package with no caller" shape flagged in earlier records, one layer up: the flow is now end-to-end except for its first step.
- **The forgotten-password entry point is an honest dead end.** `P1-19.4` owns the reset flow. The page says a reset is not available and to ask an administrator, rather than offering a form that appears to work — the person waiting for an email that will never arrive never asks anybody for help.
- **An expired password is also a dead end**, for the same reason and with the same wording.
- **Branding has no writer** until `P2-14`.
- **`clientIP` reads `RemoteAddr` and ignores `X-Forwarded-For`.** A header a client can set is not an address, and honouring it would let anybody write any IP into the audit log and, once `P1-13` lands, evade a rate limit by inventing a new one per request. A proxy-aware version belongs with that task, which needs the same value and has to decide which hop to trust.
