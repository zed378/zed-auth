# P1-08 — `GET /oauth/userinfo`

**Date**: 2026-09-10
**Branch**: `feat/P1-08-userinfo`
**Spec**: [`MEMORY/specs/P1-08-userinfo.md`](../specs/P1-08-userinfo.md)

---

## What this is

The endpoint a consumer calls to find out who is holding an access token. It completes the OIDC core surface: discovery now advertises `authorization_endpoint`, `token_endpoint`, `jwks_uri` and `userinfo_endpoint`, which is everything a conforming client configures itself from.

Its job is to hand personal data to a caller, so every decision in it is about how much. The rule is a negative — **return exactly what the granted scopes authorise and nothing else** — and every extra field would leak through every consumer that stores the response.

## The mapping is tested for absence, not presence

```
openid   →  sub
profile  →  name, preferred_username, updated_at
email    →  email
```

The tests assert the **exact key set**, not a subset:

```go
want: []string{"email", "sub"}          // openid + email
got  := keys(Build(subject(), email, scope))
if !slices.Equal(got, want) { … }
```

That distinction is the whole test. A handler that returned every claim regardless of scope passes every "is `email` there when `email` was granted" assertion anybody will ever write. Only an exact comparison catches it, and only `slices.Equal` rather than "contains" makes the comparison exact.

There is a second line behind it. `userinfo.Subject` deliberately is **not** `authn.User`: that type carries `Status`, `MFAEnabled` and `PasswordChangedAt`, none of which any scope authorises, and a struct that holds them is a struct somebody eventually ranges over. What cannot be in the struct cannot be in the response. `Allowed` enumerates every claim name that may ever appear, and a test walks every scope combination against it — which is what catches a claim added later without a gate, the failure that is invisible in review because adding a key to a map looks harmless.

## The one control that costs something

**Session liveness is checked, and `docs/PLAN/04` can be read as arguing against it.**

That document says access tokens are not stored because "storing them would add a lookup to the hottest path in the system for no security gain". The reasoning is about the token endpoint and about *storing tokens*. Neither changes here: nothing is stored, and this is not the hottest path.

What changes without the check is real. A user clicks "log out", the session is revoked, and this endpoint keeps describing them for up to ten minutes — the access token's remaining life. For a call an SPA makes on every page load, that is the difference between logging out and appearing to.

It costs nothing, and that is why it is defensible rather than merely desirable: the user's row has to be read anyway, so the liveness test is a predicate in the same statement, in the same tenant-scoped transaction, in one round trip.

```sql
SELECT u.id, u.email, u.display_name, u.username, u.updated_at
  FROM users u
 WHERE u.id = $1
   AND u.status = 'active'
   AND EXISTS (SELECT 1 FROM sessions s
                WHERE s.id = $2 AND s.user_id = u.id
                  AND s.revoked_at IS NULL AND s.expires_at > $3)
```

If it had needed a second round trip the trade would have been worth arguing about. It did not.

## One answer for every unusable token

Expired, forged, wrong audience, unknown key, revoked session, deactivated user, `client_credentials`: all `401`, all `error="invalid_token"`, all the same body. The specific reason goes to the log.

The alternative — a helpful `error_description` per case — turns the endpoint into a probe, and the most useful thing it would tell an attacker holding a captured token is **whether the user has logged out since**.

Tested by comparing eight failure classes as whole recorded responses: status, every header in sorted order, and body. With a control assertion that the shared response is actually a `401 invalid_token`, without which the comparison would pass against a handler that answered everything with an empty 500 — and a second control proving a *successful* request is distinguishable, without which it would pass against a handler that refused everything.

`insufficient_scope` is the deliberate exception: `403`, naming the scope. Not a disclosure — the caller already knows what it asked for — and conflating it with `invalid_token` sends a working client into a re-authentication loop that cannot help it. It is checked **last**, so a token that is both invalid and unscoped is reported as invalid; the other order would answer the more informative code to a forged token. That ordering has its own test.

## `signing.Verifier.Verify` gained a mandatory parameter

```go
func (v *Verifier) Verify(compact, wantType string) ([]byte, error)
```

Not a strict `VerifyTyped` beside a permissive `Verify`. That is a pair where the shorter, more obvious name is the unsafe one, and the unsafe one is what gets called. As a required parameter the check cannot be forgotten, only got wrong — and got wrong is visible in review. It also refuses an empty `wantType`, so the permissive behaviour cannot be recovered by passing `""`.

Changing the signature was cheap because **the verifier had no caller at all**. This service could sign tokens and had never once verified one of its own — a verifier nothing had ever verified with, which is exactly the kind of code that turns out not to work when something finally needs it. It worked.

## What the mutation testing found

Seven mutations, each reverted:

| Control removed | Test that failed |
|---|---|
| the handler verifies with `typ: JWT` | `TestTheHandlerAsksForAnAccessToken` |
| the session-liveness predicate | `TestRevokingTheSessionInvalidatesTheTokenImmediately` |
| `u.status = 'active'` | `TestADeactivatedUserStopsBeingDescribed` |
| the email scope gate | `TestTheEmailNeverAppearsWithoutTheEmailScope` |
| a distinct description for a revoked session | `TestEveryRefusalIsIndistinguishable` |
| the `client_credentials` refusal | `TestClaimValidation` |
| the handler verifies with `typ: JWT` | `TestAnIDTokenIsRefusedAsABearerCredential` — **passed** |

The last row is the interesting one. The end-to-end test presents a real id_token signed by this service and asserts it gets nothing — and it kept passing with the `typ` check removed, because an id_token's `aud` is the client rather than the issuer, so the audience check caught it.

That is the layered design working, not a bug. But the test looked sharper than it was, so it now **says** so: it documents that two independent controls refuse an id_token, names the test that proves the `typ` half sharply, and adds assertions that the two distinguishing properties are still true **of the token** — because if `P1-07` ever typed an id_token `at+jwt` or addressed it to the issuer, this endpoint's defence would quietly rest on one control instead of two and nothing else in the suite would notice.

The response to a test that turns out not to isolate what it claimed is to correct the claim, not to weaken the design so that one test can carry it alone.

## The `sid` claim had never been exercised by anything

This endpoint looks the session up by the access token's `sid`, so a token without one is refused. Writing a test for that turned up something:

```go
// internal/oauth/token/token_integration_test.go, the fixture
code := authorize.Code{
    …
    SessionID:     "",   // ← every token the token endpoint's tests ever issued
```

The production path was correct all along — `/oauth/authorize` puts `current.ID` in the code and the token handler copies `code.SessionID` into the `Subject`. But **no test had ever put a session behind a code**, so `sid` had never appeared in an issued token, and a regression that dropped `SessionID` from either grant's `Subject` would have broken nothing in the suite while making every real token fail at userinfo with `invalid_token` — which reads like a signature problem and is very hard to trace back.

Worse, **this endpoint's own integration test would not have caught it**, because it builds its `Subject` by hand and hands it to `token.AccessTokenClaims` directly. It proves userinfo consumes what that builder produces; it says nothing about what the token *endpoint* puts into the builder. Two tests that each look end-to-end, with the actual seam falling between them.

Closed on both sides:

- The token fixture now creates a **real session** through `P1-11`'s manager and wires `Sessions` into the handler — which also means the refresh grant's session-liveness check is exercised for the first time, having been skipped by a `h.Sessions != nil` guard against a nil field.
- Two new tests in the token package: `sid` survives a refresh (the risky path, because the refresh builds its own `Subject`), and a `client_credentials` token carries **no** `sid` — which is the other half of what userinfo relies on when it refuses one.

The general shape is worth keeping: a fixture that pins a field to its zero value is a fixture that quietly removes that field from every test built on it.

## Gaps raised

**`PG-17` — there is no CORS policy anywhere in the plan.** `docs/PLAN/12` says SPAs call this endpoint on every page load; that means a browser, which means cross-origin, and no plan document specifies an origin policy. `docs/SECURITY/02` §12 names "overly permissive CORS" as a token-leak path — a warning with no rule behind it.

This endpoint sends **no CORS headers**, which is the safe default and also the one that does not work from a browser. That is the honest state: the alternative is inventing an origin policy for an endpoint that returns email addresses. Doing it properly needs a per-application allowed-origins list, and `docs/PLAN/04` § `applications` has nowhere to put one — a single instance-wide allowlist would let any tenant's application read any other tenant's user data from a browser.

**`PG-18` — `email_verified` has no column behind it.** The claim is **omitted** rather than returned as `false`. Absent means "not asserted", which is true; `false` means "we checked and it is not verified", which we did not. A consumer gating on a verified address would otherwise refuse every user this service has, on the strength of a value the service made up.

## Also deliberately not done

**Step 4 of the card — "serve from a read replica or a short-TTL cache".** There is no replica, and a cache is the wrong instinct here: an entry that outlives a profile change or a session revocation serves a stale identity, on the endpoint whose entire job is to say who somebody currently is. One indexed query already fits the budget. Measure before adding a cache that comes with an invalidation problem.

**The query parameter form of the credential.** RFC 6750 §2.3 defines `?access_token=` and calls it NOT RECOMMENDED. It is refused, and has a test: a query parameter is written to the access log of every proxy in the path, to the browser's history, and to the `Referer` of whatever loads next. `P1-06` takes some trouble to keep credentials out of URLs; accepting one here would undo that on the endpoint that returns the email address.

## Verification

- Unit and integration tests, `internal/oauth/userinfo` at 98.3% with a floor added at 80%.
- The integration tests run the real chain: a key generated and rotated through `P1-03`'s store, a session created through `P1-11`'s manager, a token built by `P1-07`'s own claim builder and signer. Nothing is a hand-built approximation of what the service issues.
- Tenant isolation tested by signing a token that names **another** organization and confirming it reads nothing — RLS confining the query rather than a predicate somebody remembered to write.
- `go vet -tags=integration ./...`, which the restructure earlier the same day proved is not implied by plain `go vet`.

## What is still missing

- **Nothing gives a consumer an access token without an application and a user**, and neither can be created through the product yet (`P1-18`, `P1-19`). The capability audit records exactly this and is right to.
- **No consumer can call this from a browser** until `PG-17` is decided.
- `email_verified` stays absent until `PG-18` is decided and `P1-19.5` sets it.
