# P4-10.3 - Hosted social login

**Date**: 2026-11-25. **Status**: REVIEW; parent P4-10 remains WIP.

Implements steps 5-7 of [the feature spec](../../TASKS/specs/P4-10-social-login-federation.md), following ADR-028 (GitHub OAuth) and ADR-030 (existing local accounts only). References: `docs/PLAN/05-API-CONTRACT.md` social login and rate limiting; `docs/PLAN/08-AUTHORIZATION.md` Part B; `docs/PLAN/11-TESTING.md`; `docs/SECURITY/02-ATTACK-SURFACE-AND-SCENARIOS.md` tenant isolation and secret exposure. Reference documentation is unchanged.

## Implemented

- `GET /login/social/{provider}` and its `/callback` route are registered only when social providers are configured. Google, Microsoft and GitHub each have an independent Secure, HttpOnly, host-only, SameSite=Lax browser cookie containing a pending-request reference and a random browser binding. Callback request parameters cannot choose the organization or pending authorization. State consumption precedes provider exchange and identity lookup; a callback clears its binding cookie.
- Organization policy is read before starting, before callback exchange, during tenant-scoped linked-subject resolution, and immediately before session issuance. Unknown/unlinked subjects, inactive accounts, cross-tenant accounts, provider failures and browser/state mismatches fail generically. No email matching, account creation or linking was introduced.
- Reuses session creation, session replacement, audit, anomaly observation and OIDC/SAML authorization resumption. Provider identity checks run outside database transactions. Known local-user failures include the internal user ID in the audit event; unknown-user events omit it. Neither success nor failure audit payloads contain provider codes, tokens, subjects or raw responses.
- MFA challenge and forced-enrollment state retain the verified primary method. TOTP, WebAuthn and recovery outcomes propagate it through session creation. Social sessions record the provider instead of `pwd`; a local factor adds its actual method and `mfa`. Social login refuses a required enrollment when enrollment is unavailable. After MFA, account status and current organization provider policy are rechecked before issuance.
- Hosted login exposes only configured and policy-permitted providers. Organization settings accept the three individual provider names; the REST schema, generated Go/TypeScript artifacts and console policy controls use that same enum. Generic `social` and primary `passkey` remain rejected.
- Uses the existing Redis quota machinery: 20 route requests per minute per provider/client IP, counting starts and callbacks together. It inherits the existing quota fail-open behavior; the mandatory state store independently fails closed during Redis outages.
- OpenAPI documents both hosted HTML routes. Like OAuth protocol routes, these are excluded from generated server routing because raw cookies and duplicate-query validation belong to the handler. The public reference continues to derive from OpenAPI.

## Remaining work and rollback

P4-10.3 is REVIEW, not deployment acceptance. Provider credentials and real staging registrations still need acceptance. P4-11 must provide authenticated identity linking/unlinking and account settings; these routes can sign in only an already-linked local account. Do not enable a social-only organization policy until members have linked identities and an outage recovery path.

To disable, remove provider configuration or disallow provider methods in organization policy. Keep password access available. Before reverting to a build without social primary-method state support, stop social starts and allow pending social state, MFA challenges and forced enrollment to expire (at least 15 minutes). The additive identity table may remain. No commit, deployment, external message or reference-plan edit was performed.
