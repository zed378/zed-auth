## The claim shape is a one-way door, so it is asserted literally

A consumer application parses this claim and branches on it. Changing the shape later breaks every one of them at the same moment, and they are not all deployed by us.

So `TestTheRoleClaimMatchesThePlansJSONExactly` compares against the literal JSON `docs/PLAN/08` Part A prints, rather than against a Go structure that happens to marshal into something similar. The difference matters: a struct test passes when a field is renamed in both places at once.

**`org_id` inside each role value is the part somebody will want to remove.** In Phase 2 it is genuinely redundant — a role can only come from one organizational context, so the value is the same for every key in the claim. `docs/PLAN/08` says why it is there anyway: once Phase 4's delegation makes the same role name reachable from two contexts, a consumer needs to tell them apart, and adding a field to a claim consumers already parse is a breaking change for all of them.

It costs nothing now and cannot be added cheaply later, so it is emitted now, with a test that names it specifically.

## Scoped to one project, which is the real bound

A token carries the roles held **in the requesting client's project** and no other. That is not a size optimisation bolted on; it is what `docs/PLAN/08` Part A's per-project claim key means, and it is what keeps a token's size a function of one application's role model rather than of how many projects the organization has.

The test that matters asserts the **absence**: a role granted in project A does not appear in a token issued for project B, and a token does not carry a claim for a project it was not issued for. A test checking only that the granted role appears would pass against a service that puts every role in every token.

## ADR-021, which the card asked for before it becomes an incident

An access token travels in an `Authorization` header, and most proxies cap headers near 8 KB. An unbounded claim fails **at the consumer**, **in production**, **for one user** — whoever accumulated the most grants — and reads as "the application is broken for Priya" rather than as a token problem.

Bounded at 64, matching `grant.MaxRoleKeys` so a grant cannot be written that a token cannot represent. Over the bound the claim **truncates rather than drops**, because a truncated claim is a true subset: a consumer denies access it should have granted, which somebody reports and an administrator fixes. A dropped claim is indistinguishable from "no roles", with no signal at all, and failing issuance takes down every login for that user.

The asymmetry decides it: denying access that should have been granted is recoverable; granting access that should have been denied is not.

A reference token was considered and not taken — it has no size limit, and it turns every authorization decision into a round trip to this service, which `docs/PLAN/12` names as the single biggest latency win to avoid giving up. The 64 bound is where that gets re-examined.

## Reading the roles without slowing down the token endpoint

`P1-28`'s load test found `/oauth/token` to be the first endpoint that saturates, and the ceiling was **Postgres CPU**. So the claim read is one query, not two: project roles and manager roles come back in a single statement.

The two halves are scoped differently on purpose. Project roles are read inside the user's tenant, because `user_grants` is org-scoped and RLS is what confines it. Manager roles are read outside any tenant — `manager_roles` has no `org_id`, only a `scope_id` whose meaning depends on the role, and an `INSTANCE_OWNER`'s scope is the instance. The same reasoning `management.RoleStore` already documents.

**A failure reading them does not fail the token.** A token with no roles grants less, which every consumer already handles; refusing to issue one takes down every login in the deployment because one query failed. It is logged at `ERROR`, because a service quietly issuing role-less tokens is an outage that looks like a permissions bug to everybody downstream.

## Snapshot semantics, documented where consumers will read them

`docs/PLAN/08` says claims are a point-in-time snapshot and that sensitive decisions belong at a real-time check. The public authorization page now says it in the second person, with the reason rather than the rule: a revocation cannot reach back into a token already in somebody's hands, so keep lifetimes short and ask at the time of the action for anything destructive.

`TestARoleGrantedAfterLoginReachesTheNextToken` pins the half that is deliverable today — claims are read at issuance, not carried forward from the session, so a role granted mid-session reaches the next token. The inverse, a revocation not reaching an issued token, is the snapshot's cost and is `P2-06`'s to demonstrate.

The claim-injection abuse case is answered by construction rather than by escaping: the claim is built as a Go map and marshalled, never assembled as a string, so a role key containing `","admin":{"org_id":"` becomes one escaped key rather than two roles. The test asserts the property holds rather than that the code looks like it should.
