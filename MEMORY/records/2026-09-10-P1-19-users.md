## What this is

The task that makes the product usable by somebody who is not a database administrator. Until it landed, every user in every environment was inserted by hand.

Seven `/v1` operations, two hosted pages, one new package for email, and the column that closes `PG-18`.

```
GET/POST   /v1/organizations/{org_id}/users
GET/PATCH  /v1/organizations/{org_id}/users/{user_id}
POST       .../users/{user_id}/deactivate
POST       .../users/{user_id}/reactivate
POST       .../users/{user_id}/password-reset

GET/POST   /login/forgot        ← unauthenticated, hosted HTML
GET/POST   /password/set        ← unauthenticated, hosted HTML
```

## The rule the whole package is shaped around

**No password crosses this API in either direction.** There is no password field on create, none on update, none in any response, and no store method that accepts a hash. `password` and `password_hash` are both in the refused-fields list, and the test asserts a `400` for each.

That is not squeamishness about a convenience. An account whose first password was chosen by an administrator is an account its owner cannot be held responsible for — and an administrator who can set one can take over any account in the organization while leaving an audit trail that says only "user updated". The password comes from the person it belongs to, through a link sent to their own address, which is also the only thing that proves the address is theirs.

Same reasoning for the reset link: **it is not in the response** to the administrator-triggered reset. Only the mailbox holder sees it. An administrator needing to set a password directly does not have that capability, deliberately.

## Two answers that must be identical, asserted on bytes

`/login/forgot` is the endpoint whose entire security property is that it says nothing. The test compares the **full response body and the status** for a real address and an unknown one — not "both return 200", which passes against a service whose two pages differ by a sentence.

Three ways that could pass for the wrong reason, all closed:

- **The control**: exactly one message was sent across the two requests, so the identical answers are not identical because nothing happened in either case.
- **A deactivated account** is compared too, and matches.
- **Timing**: the two paths are measured over six rounds each, warmed first, with a 0.2×–5× tolerance. Wide, because it measures a real database in a container — what it rules out is the order-of-magnitude difference a short-circuit produces.

**No audit event is written for an unknown address.** One per probe would put every attempted address into the log, durably and searchably — the enumeration list the endpoint exists to withhold. Asserted in both directions: zero for an unknown address, one for a real one.

## Deactivation is three revocations, not a status change

The card asks for it "within one request cycle", and the reason is that a status alone stops only the *next* login. It does nothing about a session cookie already in a browser or a refresh token already in a consumer application's store.

So `DeactivateUser` does all of it inside the request: revokes every session, tombstones the session cache, revokes every refresh token, and retires any live invitation or reset link. **Any one left out leaves the user working**, and the cache is the subtle one — the table would say revoked while the cache still said valid, and the cache is what the next request reads. A tombstone failure is an error here rather than a warning, for that reason.

The test creates a **real session through the real manager** and a **real refresh token through the real store**, checks both work, deactivates, and checks both stopped — through their own interfaces rather than by reading a column, which would pass against a service that set the status and revoked nothing.

`Handler` refuses to deactivate at all if either revoker is missing, with a message naming the missing one. A nil dereference there would be a panic; a `204` that left the user working would be worse.

## Single use is the database's decision

`ConsumeToken` is one conditional `UPDATE`:

```sql
UPDATE user_tokens SET used_at = $2
 WHERE token_hash = $1 AND purpose = $3 AND used_at IS NULL AND expires_at > $2
RETURNING user_id, org_id, purpose
```

Not a read followed by a write. Two requests arriving with the same token at the same moment would both pass a read-then-check, and both would set a password — the second silently overwriting the first, on an account neither party fully controls.

**A sixteen-goroutine race was not enough, and a mutation proved it.** Replacing the conditional `UPDATE` with a read-then-write **survived** that test — because under serial execution a read-then-write is correct: the second reader sees `used_at` already set. The bug only appears when two transactions genuinely overlap, and goroutine scheduling plus connection acquisition kept them from doing so. The test was hoping for a race rather than causing one.

The replacement **forces the overlap**: one transaction consumes the token and stays open, a second consumes the same token while the first is uncommitted, and only then does the first commit. The real implementation blocks the second on the row lock, re-evaluates `used_at IS NULL` after the commit, matches nothing and refuses. A read-then-write would have read `NULL` before the commit and written anyway. Deterministic, and it kills the mutation.

The sixteen-way race stays as well — it is cheap and it exercises a different thing — but it is no longer what the claim rests on.

**Issuing a token retires every unused one of the same purpose**, so an account never holds two live credentials at once — and the one the user did not ask for is the one nobody is watching.

**A password the policy refuses does not burn the token.** The policy runs before consumption; consuming first and then refusing would leave the person holding a dead link and no account, which is the worst combination available and is easy to write by accident.

## The page sets a password and does not sign anybody in

Deliberate, and tested: no session cookie, and no row in `sessions`.

A page that both consumes an emailed link and issues a session is a second authentication path with none of the login page's rate limiting, and it turns a stolen link into a live session in one step rather than two.

Every way a link can fail — used, expired, never existed, malformed — renders the **same page**, asserted by comparing the three bodies against each other. Distinguishing them would let a holder of an expired token learn it was once real.

A stale CSRF token is the one thing that does *not* condemn the link: the form re-renders and the link still works afterwards. The form is stale; the credential is not.

## `PG-18` closed, narrowly

`users.email_verified_at`, a timestamp for the reason `password_changed_at` is one: "when" answers questions "whether" cannot.

Set when an **invitation** is accepted through a link sent to that address — which is exactly what verification means. **A password reset does not set it.** A reset proves reachability too, and widening the claim there would be a security statement made by accident rather than by decision; `PG-18` names `P1-19.5` and that is what this implements. Both halves are tested.

Changing the address clears it, because a verification is a statement about one address and not about the user who holds it.

`docs/PLAN/04` should be amended to describe the column — that is the deliberate plan-change process and is **not** done here.

## ADR-018, and what it cost

`OQ-04` had been open since the backlog was written and blocked this task outright. Decided rather than deferred, because the instruction was to finish Phase 1 without stopping: **plain SMTP by URL, no provider SDK, and nothing waits on delivery.**

Consequences visible in the code:

- An invitation whose email fails still returns `201`, with `invite_email_sent: false`. Rolling a user back because a mail server was busy is the worse outcome, and the flag says what actually happened rather than what was asked for.
- A reset answers identically whether the send succeeded — it has to, since it already answers identically whether the address exists.
- `auth_mail_send_failures_total` is the metric that makes both safe. Without it, an invitation nobody received and an invitation nobody sent look identical from outside, and for a password reset the person who notices is somebody locked out.
- The config refuses to boot on `smtp://` outside local development, because an invitation link is a bearer credential and a cleartext hop hands it to anything on the path. It also refuses a URL with no `From`: half-configured is worse than unconfigured, since it looks set up and fails per message rather than at startup.

## Found while building it

**The fourth handler, and my own prediction was wrong.** `P1-18`'s record said that at four sub-interfaces the answer was a shared constructor for `httpserver.Deps`. It is not. Such a constructor would have to import every handler package, and each of those has an **in-package** integration test that would then import it back — an import cycle in tests. The only escape is making four large test files external, which costs more than the one line per harness this actually costs. Recorded where the interface is declared, so the next person does not re-derive it.

**Three test bugs, each of which would have hidden something.**

- `RefreshStore.Issue` returns `(RefreshToken, familyID, error)`. Taking the second value as the plaintext produced a token that never existed — and the test failed at its *setup* assertion rather than passing vacuously, which is why the shape of that assertion matters.
- `user_tokens_expires_after_creation` refuses a row whose expiry precedes its creation, so the expiry test could not backdate a row. It asks from the future instead, with a control proving the same token resolves before its expiry — a test that fights a `CHECK` is testing the wrong thing.
- The audit test originally asserted `user.invite_accepted`, which the **hosted page** writes and the test's helper does not. Asserting it there would have asserted that the helper wrote it. It is covered in `internal/login`, where it happens.

**Every hosted-page test failed on the password policy, and that was the policy working.** The test passwords were lowercase and the default policy requires an uppercase letter. Worth keeping because it is the shape a real integration is supposed to have: the page does not have rules of its own, it uses `P1-02`'s evaluator over the organization's own settings, and a set-password page with a second policy would be the one nobody remembers to update.

## The amplification bound is keyed on the recipient

Card step 4 asks for invite sending and reset requests to be rate limited, and the interesting part is *what the counter is keyed on*.

**The recipient, not the caller.** The abuse in `docs/SECURITY/02` §10 is flooding a third party: an administrator with a perfectly legitimate account sending twenty invitations to somebody who never asked for one. A per-caller bound does not touch that — the caller is entitled to be there, and it is the mailbox that suffers. `ratelimit.MailKey` lowercases the address for the same reason `AddressKey` does: two spellings of one mailbox sharing one counter, or the bound is a formality.

It sits in **one place per surface**: inside `deliver`, which every message the Management API sends passes through, and inside the forgot flow's send. One place the bound can be missing rather than three.

A refused message does not change what the caller is told. The create still returns `201` with `invite_email_sent: false`; the reset still returns `202`. **A `429` here would be a signal about somebody else's mailbox** — and on the unauthenticated forgot page it would be an enumeration oracle outright, since "you are being rate limited" confirms the account exists.

The test installs a bound of two rather than depending on the deployment's number, and pairs the refusal with a control: a different address is unaffected, so the bound is per recipient rather than a global stop.

## The permission table

Seven routes, all `ORG_ADMIN`, and **nothing raised to `ORG_OWNER`** — a deliberate departure from `P1-17` and `P1-18`. Those raised delete because it is irreversible. There is no irreversible operation here: deactivation is the reversible thing the card asks for *instead* of deletion, and raising it would make the safe action harder than the unsafe one it replaced. Administrators route around that.

## Verification

- **Integration, 31 tests** in `internal/user`: the documented create response asserted against raw JSON rather than a struct — a struct tolerates a missing key by leaving a zero value; the invited user having no hash; a failed send still returning the account and its token; `send_invite_email: false`; per-organization uniqueness and its cross-tenant control; seven privilege fields refused with the stored row unchanged; verification cleared by an address change; deactivation killing a real session and a real refresh token; live links retired; reactivation returning a never-accepted invitation to `invited` rather than `active`; the sixteen-way token race and the deterministic overlapping-transaction race; hashed-at-rest with the plaintext absent from the whole row; expiry with its control; reissue retiring the previous token; the reset link absent from the response and sent to the user; both tenant boundaries; search across three fields with `%` and `_` treated literally; pagination; the audit events with no payload carrying a token or a password; and the per-recipient mail bound with its control.
- **Five mutations, all killed**: single use as a read-then-write, deactivation without refresh-token revocation, a forgot page that says whether the address exists, a reset that claims verification, and consumption before the policy check. The first of those **survived its original test**, which is how the weak concurrency test was found.
- **Integration, 15 tests** in `internal/login` for the hosted pages: the byte-identical forgot responses with their control, a deactivated account matching an unknown one, the timing comparison, no audit event for an unknown address (with its control), invitation acceptance setting the password and verifying the address, no session issued, single use, every invalid link rendering the same page, a refused password leaving the link usable, the form naming no user, a reset not verifying the address (with a control that the password did change), the stale-form path, mismatched confirmation, and the message's contents.
