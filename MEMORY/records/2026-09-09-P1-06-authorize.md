## What Changed

`internal/oauth/authorize` implements the authorization endpoint: two-phase parameter validation, PKCE required for every client type, silent SSO from a session cookie, `prompt` handling, and single-use codes in Redis with a 30-second TTL and atomic redemption.

The endpoint is served, documented, and now advertised — `P1-04`'s discovery document says `authorization_endpoint` for the first time, and with it `code_challenge_methods_supported`, because both are true.

This is the first task that connects the previous three. `P1-02`, `P1-05` and `P1-11` were each a package with no caller; this one uses `P1-05`'s redirect matching and `P1-11`'s session lookup on a real request path.

## Why

`PLAN/03`'s data flow made visible: a user with a session reaches the second application without seeing anything. It is also the endpoint with the most ways to be wrong — it takes seven parameters from an untrusted redirect, decides whether to authenticate somebody, and ends by sending a browser somewhere with a credential in the URL.

## How

**The ordering of validation is the security property, and the code is arranged so it reads that way.** Phase 1 resolves `client_id` and matches `redirect_uri`; a failure there renders an error page with **no redirect at all**. Phase 2 is everything else, and its failures redirect to the now-validated URI.

The reason is the one that is easy to state and easy to get wrong in an afternoon of refactoring: reporting an error by redirecting to an unvalidated `redirect_uri` *is* the open-redirect vulnerability, delivered by the code written to prevent it. The attacker supplies a `redirect_uri` they control and something else invalid, and the service obligingly sends the browser to them.

`renderError` and `redirectError` are separate methods rather than one function with a boolean, because the boolean is the thing that gets passed wrongly.

**PKCE is required for every client type**, which `PLAN/05` demands and OAuth 2.1's baseline does not. A confidential client's secret protects the token request, not the code in transit: a code intercepted from a browser redirect — a referrer leak, a malicious app claiming the same custom scheme, a URL bar over somebody's shoulder — is useless without the verifier regardless of what the client can prove afterwards.

**Codes redeem atomically**, by `GETDEL`. `PLAN/04` states the requirement plainly — "two concurrent redemptions of one code must yield exactly one success" — and the obvious `GET`, check, `DEL` passes every sequential test and loses the race. That is demonstrated below rather than asserted.

**On `state`:** required and echoed, never checked. It is opaque to us and only the client knows what it sent; mismatch is detected by the consumer, which is the entire mechanism. Requiring presence is real hardening — a client that forgot its CSRF defence learns at integration time — but claiming to verify it would be a false claim about who protects whom. The task card's abuse case says "missing or mismatched"; only the first half is ours.

## Decisions Made

| Decision | Rationale |
|---|---|
| Two-phase validation, separate render/redirect methods | Reporting a phase-1 error by redirect is the vulnerability itself |
| PKCE mandatory for all client types | A secret protects the token request, not the code in transit |
| `GETDEL` for redemption | `PLAN/04` requires atomicity; the two-call version passes sequential tests |
| `CodeTTL` 30s, not the permitted 60 | The code travels a redirect to a backend — milliseconds. Halving the ceiling halves the window a glimpsed code is worth anything |
| `state` required, never validated | Presence is ours to enforce; matching is the client's, and pretending otherwise would misattribute the protection |
| `redirect_uri` not defaulted when omitted | Defaulting makes exact matching conditional on how many URIs happen to be registered |
| Duplicate parameters rejected outright | Taking the first or last is how parameter-pollution bypasses get in |
| Only the opaque request id travels to the login page | Carrying the original parameters would put a `redirect_uri` in a URL the user can edit and need re-validating on the way back |
| `authorize` excluded from code generation | **See below** — the one exception to ADR-013 |
| Discovery now advertises `authorization_endpoint` | It is true. `token_endpoint` is still absent, which is also true |

### The one exception to ADR-013

The generated router binds and validates every parameter before the handler runs, and that is incompatible with two properties this endpoint rests on. A missing `state` would be rejected before `redirect_uri` had been validated, sending the error down the wrong channel; and the wrapper reads `r.URL.Query().Get()`, which silently takes the first of a duplicated parameter — the exact bypass the handler refuses.

So the operation is excluded from generation and registered by hand. It stays in `openapi.yaml`, so it is documented, generates into the public API reference, and is still checked by `openapi-shipped-paths.py`. Only the code generation is skipped, and the reason lives in `oapi-codegen.yaml` where somebody re-enabling it will read it.

This is a deviation from ADR-013's mechanism, not from its goal — served paths still equal documented paths.

## Deviations from the Plan

The ADR-013 exception above. `redocly`'s `operation-2xx-response` was downgraded from `error` to `warn`: this endpoint genuinely never returns 2xx — it redirects on success, redirects on most errors, and renders a 400 when it must not redirect. Documenting a 200 to satisfy the rule would be inventing a response the endpoint cannot produce, which is the failure the rule exists to catch, reached from the other side.

## What Did Not Work

**The generated router could not serve this endpoint.** The first wiring implemented the generated strict interface, and it does not work: `AuthorizeRequestObject` carries only the bound `AuthorizeParams`, not the request, so the handler cannot see the raw query — and by then the wrapper has already rejected a missing `state` (before `redirect_uri` was validated) and collapsed any duplicated parameter to its first value. Both are exactly what the handler exists to prevent.

Several arrangements were tried before excluding the operation: overriding at the non-strict `ServerInterface` layer (the binding still runs first), and marking parameters optional in the spec so binding cannot fail (which makes the `required` flags describe something other than the endpoint's semantics). Exclusion is the honest one, and it keeps the endpoint documented.

**`operation-2xx-response` failed the spec lint**, correctly by its own logic and wrongly here. Downgraded to `warn` rather than exempted by hand, with a note that a second exception should turn it into a per-operation exemption instead.

**The capability audit declared single sign-on shipped, and it was wrong.** `P0-19`'s check maps each landing-page capability to the roadmap task that ships it, one task per capability. `P1-06` going DONE made it demand that the "Single sign-on" card stop saying "Phase 1" — but a consumer still could not complete a login, because there is no token endpoint to exchange a code at and no page to log in on.

Marking the card available would have been exactly the false claim the check exists to prevent, produced by the check itself. Fixed by letting a capability list every task it needs: single sign-on now requires `P1-06`, `P1-07` and `P1-12`, and the audit reports which are outstanding. Proven both ways — it passes now and fails if all three are marked done.

**`internal/oauth/client` fell below its coverage floor** when `ByClientID` arrived with no test. Caught by the floor rather than noticed — which is the floor doing its job, on a method that resolves a client before any tenant scope exists and therefore deserved a test more than most.

## Follow-Ups and Open Questions

- `P1-07` redeems the code: it must check `client_id`, `redirect_uri` and the PKCE verifier against what the code bound, and treat a second redemption as a reuse signal. Everything it needs is on the `Code` struct.
- `P1-12` serves `/login` and resumes a pending request. Until it lands, a user without a session is redirected to a path that 404s — visible and honest, but the flow is incomplete.
- `P1-27` owns the load test for the p95 target.
- Discovery advertises `authorization_endpoint` and not `token_endpoint`. That is accurate and it means a conforming client still cannot configure — `P1-07` closes it, and only then can `P1-04`'s first DoD item be ticked.
- Session policy is the instance default; nothing yet reads `session_lifetime_hours` from the organization row. Same gap `P1-11` noted.

## What to Watch

**Anything that makes phase 1 report by redirect.** The test asserts the absence of a `Location` header. If that assertion is ever softened to "returns 400", the open-redirect protection can be removed without a test failing.

**`auth_authorize_total{outcome="denied"}` by error code.** A spike in `invalid_request` after a consumer deploy is that consumer's integration breaking; a spike in `unauthorized_client` is a client misconfiguration; a rise in `login_required` means sessions are being lost. The label is what separates them.

**`GETDEL`.** If a refactor splits it, every sequential test still passes. The concurrency test is the only thing standing between that and duplicate code redemption in production.

**The login redirect target.** `LoginPath` is `/login` and nothing serves it yet. When `P1-12` lands, the resume path has to re-validate nothing — the pending request was validated before it was stored, which is why only an opaque id travels.
