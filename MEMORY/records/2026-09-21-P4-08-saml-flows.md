## What is built

`docs/PLAN/17`'s Phase 4 criterion — "a SAML-only legacy application completes a full
SP-initiated login" — passes on both bindings, verified by verifying the assertion.

| Piece | Constraint |
|---|---|
| `request.go` | The **inflated** document is bounded, not the query string (C-4) |
| `metadata.go` | Persistent NameID, never email; no SLO endpoint advertised (C-5) |
| `authncontext.go` | The assertion describes the session, never the request (C-6) |
| `pending.go` + migration 042 | One AuthnRequest, one answer (C-3) — on the login path; see below |
| `response.go` | The **assertion** is signed, not the envelope (C-2); the form is `html/template` |
| `providers.go` + migration 043 | The registration decides the destination, not the request (C-1) |
| `nameid.go` + migration 044 | A user is a different subject to every service provider |
| `internal/samlapi` | The endpoints, the dispatcher, the subject, the audit |

**46 mutations, all caught** — after six of them exposed tests that could not fail.

## Decisions worth keeping

### Single Logout is refused, in the protocol's own vocabulary

The card allowed implementing it or documenting its absence. Front-channel SLO iterates
every service provider in a session through the user's browser, and any one of them being
slow, unreachable or wrong leaves a **partial logout** — a user told they are signed out
of applications they are not. That failure is silent and users act on it.

So `/saml/metadata` advertises no `SingleLogoutService`, and `/saml/slo` answers
`RequestDenied` with a readable reason rather than 404. A 404 reads as a misconfiguration
to retry; a refusal reads as a decision. Advertising the endpoint would be worse than
either, because a service provider would build a logout button on it.

### One seam, not two

`internal/login` hands a finished sign-in back through a single interface. The tempting
change was a second seam and an `if`, and it is wrong twice over: the login page would
learn which protocols exist, and every future protocol would edit the most
security-critical path in the service — a branch that has to be right for password, for
the factor step, for a refresh, and for the forced-enrolment detour.

The request id carries a `saml:` namespace and a dispatcher routes it. `internal/login` is
not edited at all.

### A SAML login is `token.issued`

F-8 asks that SAML logins appear "identically to OIDC logins". A new
`saml.assertion.issued` type would be invisible to every query that exists — the console's
audit screen, an operator asking what was issued to whom, a detection rule. So it is the
same event with `protocol: saml` in the payload.

### The NameID is stored, not derived

`HMAC(secret, user || entity_id)` needs no table and creates a secret that **can never be
rotated**: rotating it re-identifies every user at every service provider as a stranger.
"We can never change this key" is a worse property than a table.

## What the mutations found

Twenty-seven died immediately. Four survived, and each was a test that could not fail.

**The bomb defence was untested as a memory property.** Removing the `LimitReader` still
produced `ErrBomb` — after inflating everything. An error-only test cannot tell a bounded
reader from an unbounded one, so the test now measures allocation.

**"The parsed request carries no ACS URL" named one field.** The real property is that
*no* field carries it. It walks the struct by reflection now, so adding a field that reads
the request's own ACS URL fails rather than quietly becoming a redirect nobody approved.

**"The database refuses an email NameID" was satisfied by a primary-key collision.** It
reused a user that already had a row, so the insert was refused before the CHECK was
consulted. Removing the constraint left it green. It uses a different user now.

**The routing predicate had no test at all** until the dispatcher got one — a wrong answer
there is invisible: the login page renders, the user signs in, and the flow completes
against the wrong protocol.

**"IdP-initiated needs a service provider" could not fail.** With the empty-`entity_id`
guard removed, the lookup of the empty string refuses the request anyway, so the status
alone proves nothing. It asserts on the reason now — the only thing separating "you named
nobody" from "you named somebody unknown".

## Two bugs found while wiring, either of which would have failed silently

**The `RequestedAuthnContext` was being dropped across the login page.** `Pending` did not
carry it, so a service provider's requirement survived only for a user who *already had a
session* — and the login path is exactly the one an attacker with no session takes. That
is the "never ignored" half of C-6 defeated by a round trip. It is a stored column now,
checked on both paths.

**`ByID` read an RLS-protected table with no tenant set.** Every policy evaluates false, so
it would have returned nothing: a login refused for a reason invisible in the logs. It goes
through a bounded `SECURITY DEFINER` function now, and a test asserts the direct read
genuinely sees nothing — so the function is demonstrably necessary rather than decorative.

## The gosec finding, answered rather than silenced

G705 — XSS via taint analysis, HIGH confidence — on writing the self-submitting form. The
taint is **real**: `RelayState` and the destination are attacker-influenced and do reach
that buffer. They are also already neutralised by `html/template`'s contextual escaping,
which tests assert and which a mutation rebuilding the form by concatenation turns red.
gosec cannot see through the call, so it flags the write rather than the construction.

Silenced at that one line, with the reasoning and the test named — not by excluding the
rule, which would hide the next one.

## An operational note

The gate and a full integration run must not execute concurrently. Both drive
testcontainers, and running them together produced three failures in packages that pass
standalone — the same shape as the earlier "never run the mutation script and the gate at
once", and equally misleading to read.

## Two gaps found while writing this record, and closed

Both were the same shape: something stored and not enforced, which is worse than not
offering it — an administrator who ticks a box believes it does something.

### Signed AuthnRequests

`want_signed_requests` and `certificate` were stored by migration 040 and consulted by
nothing. Now: verified on the **HTTP-POST** binding through the same `saml.Verify` every
assertion goes through, so the signed element must be the element consumed.

**Refused on HTTP-Redirect.** That binding does not sign the XML — it signs a query string
as an octet sequence, with the signature in a separate parameter, which is a different
construction with its own canonicalisation rules and its own history of implementations
verifying the wrong bytes. It is not implemented, so a registration that requires signing
is refused there rather than accepted unverified. A visible failure an administrator can
act on beats a flag that silently verifies nothing.

### IdP-initiated sign-on

`GET /saml/init?entity_id=…`, **opt-in per registration and off by default** — the card
said "consider making it opt-in", and that is the answer rather than a suggestion.

The risk is stated in the endpoint's own documentation rather than implied. An
SP-initiated login is correlated: the service provider made the request, remembers its id,
and checks `InResponseTo`. An IdP-initiated assertion answers nothing, so anyone who can
cause a browser to visit that URL can have an assertion delivered — the same shape as a
CSRF. Some service providers handle it; many log the user in.

Three properties make it as safe as it can be:

- A registration that has not opted in receives **nothing at all**, not even a SAML
  failure, which would still be delivering something it never asked for.
- A live session is required. The endpoint never drives an authentication of its own for a
  service provider chosen by whoever sent the link.
- The assertion carries **no `InResponseTo`**. Signing in through the hosted login needs an
  id to find the browser again, so one is minted — and `idp_initiated` on the row is what
  stops that bookkeeping id being echoed back, which would invent the correlation this
  flow does not have.

It reuses the pending-request table and the resume seam rather than teaching the login
page a `next` parameter. A `next` is a URL the page redirects to after authentication,
which is an open redirect unless every path through that page validates it — a new hole in
the most security-critical surface in the service, opened for one flow.

## What "one answer per request" actually covers

C-3 holds on the path that goes through the hosted login: the request is recorded, and
consumed once, by a conditional `UPDATE … WHERE consumed_at IS NULL … RETURNING`. A second
arrival of the same id is refused to the registered address.

It does **not** hold on the live-session path, which records nothing and answers
immediately. That is a deliberate limit rather than an oversight, and the reasoning is
worth keeping because the flat claim reads stronger than the code:

- Replaying an AuthnRequest against a live session needs the victim's session cookie, and
  anyone holding that can start a fresh sign-on of their own. The replay buys nothing the
  cookie did not already give.
- An attacker who merely knows a registered entity ID can **forge** an AuthnRequest — they
  are unsigned unless the registration says otherwise — so bounding *replays* of one
  particular id would not bound issuance at all. What stops the forgery being useful is
  the service provider checking `InResponseTo` against a request it generated, which a
  forged id fails. The correlation defence belongs there and works there.
- Recording on the fast path would put a primary key on a string the service provider
  chooses, and an SP that retries legitimately — a user pressing back — would meet a
  refusal instead of a login. That is a real cost for a property somebody else already
  enforces better.

Stated here so the next person reading `pending.go` does not assume a guarantee the fast
path never made.

## A third table with the same shape, found while looking for the first two — `BL-08`

`saml.Replay.Prune` and `saml.Requests.Prune` are written, tested, and called by nothing.
So is `management.IdempotencyStore.Sweep`. `Prune`'s own comment states the property it
does not deliver: *"the table would otherwise grow without bound … an unbounded table on
the login path is a slow outage scheduled for whenever it stops fitting in memory."*

`saml_authn_requests` takes a row per SAML login and `Consume` only sets `consumed_at`.

The part that makes it more than wiring: all three tables are under RLS, a sweeper has no
organization to be, and under instance scope `current_org_id()` is NULL — so a plain
`DELETE` **succeeds having removed nothing**. `sweep_idempotency_records` already solved
this with a bounded `SECURITY DEFINER` function and says so in its own comment; the two
`saml` Prunes are plain `DELETE`s. A test asserting "no error" would pass.

Recorded as `BL-08` rather than fixed inside `P4-08`, because the fix spans a migration, a
janitor, and two packages this task does not own — and because a test that proves the
function is *necessary* is the only thing that stops the fix re-creating the bug.

## Two operational things this task had to build

**`keyctl -purpose saml`.** The binary hard-coded `PurposeOIDC`, so the staging deployment
had no way to create the key the endpoints look for. `generate` now produces the
self-signed certificate too, in the same step as the row, because migration 041's CHECK
says a SAML key without one is not a key. `keyctl -purpose saml jwks` refuses rather than
improvising: SAML has no JWKS, and printing something would suggest an endpoint that does
not exist.

**The rotation runbook gained a SAML section, and it inverts the OIDC procedure.** The
thing that makes an OIDC rotation safe — publish the key, let consumers fetch it, then
sign — has no counterpart here. A service provider pins a certificate out of band and
`/saml/metadata` advertises only the current one, so the moment `rotate` runs, every
service provider still pinning the old certificate rejects every assertion. `previous`
buys nothing: this service is the issuer, not the consumer. So the wait happens *before*
the rotation and it is a wait on people, not on caches.

That is a worse property than it needs to be, and the fix belongs to `P4-09`: SAML
metadata can advertise more than one signing `KeyDescriptor`, which is how the overlap is
supposed to be automatic instead of a round of emails. It is a DoD item there now.

## The acceptance harness is a badly-behaved service provider

`scripts/acceptance-saml.sh` plus `scripts/acceptance/saml`. It sends requests naming its
own Assertion Consumer Service URL, replays a request id, asks for an assertion it never
requested, and presents an entity ID nobody registered — then asserts every one of those
was refused, against a real deployment rather than a fixture.

Two details are the whole point of it.

**It verifies the signature with `goxmldsig` directly, not through `internal/saml.Verify`.**
A check calling the same function would agree with the service by construction: a `Verify`
that validated the wrong element would still say yes here, and the one property this
protocol rests on would go unchecked by the only test that runs against a deployment. It
builds its own validation context from the certificate published in `/saml/metadata` —
which is where a real service provider would get it — and its module deliberately does not
pin the same library versions the backend does.

**The IdP-initiated opt-in is tested with two registrations, not one toggled between
passes.** A refusal before a flip and a delivery after it is also what a fixed unrelated
problem looks like. Two rows differing in exactly one column, exercised in one run against
the same key and the same user, leave the flag as the only thing that can account for the
difference.

It seeds by SQL because there is no API for registering a service provider yet — the
table, the flags and the enforcement exist and the administrator does not. That is `P4-09`,
and needing raw SQL to run the acceptance suite is the argument for it.

## Three defects the acceptance suite found that the integration suite could not

Both were in `Requests.Peek`, and both broke **every** SAML login on the deployment —
through the hosted login page, which is the path a user without a session takes.

The integration suite passed throughout. It drives `Resume` directly with a session it
constructs, so `Peek` — the call the login PAGE makes, with no tenant, before anyone has
signed in — had **no test at all**. Thirty-eight mutations, five vacuous tests found and
fixed, and the one function nothing called was invisible to all of it.

**It read the RLS-protected table directly.** `Peek` runs under `WithInstanceScope`
because the browser arrives with a request id and no session. Instance scope sets
`current_org_id()` to NULL, every policy on `saml_authn_requests` then evaluates false, and
the read returned nothing while reporting no error. The page answered "Nothing to sign in
to". Exactly the shape `ByID` had, fixed in migration 043 — and missed one function away.

**It scanned a nullable column into a string.** `requested_authn_context` is NULL whenever
a service provider asks for no context, which is most of them. `Consume` reads it as a
`sql.NullString`; `Peek` did not. This one was hiding *behind* the first: the RLS blindness
meant the scan never ran, so fixing one exposed the other.

Both are migration 045 and a `sql.NullString`. What matters more is the third finding:

**The test proving the fix necessary was itself vacuous.** A mutation widening the new
`SECURITY DEFINER` function to `WHERE lookup_id IS NOT NULL` — making it return *any*
pending request, across every tenant — left the new tests green. Boundedness is the entire
reason that function is safe to be `SECURITY DEFINER` at all, and nothing tested it. The
fix is to ask for an id that was never recorded, with a real row present so an unbounded
version has something to wrongly return.

### The third: the login page refused the id before the dispatcher could route it

The first two fixes did not fix the flow, and the second acceptance run failed identically.
`validPendingID` — a shape check the login page runs *before* calling the seam — accepts
exactly 43 base64url characters, which is what `authorize.SavePending` mints. A `saml:`
prefixed id is neither, so it was refused one step before the dispatcher that exists to
route it.

That is the "one seam, not two" design's blind spot, and it is worth naming precisely: the
dispatcher kept `internal/login` from learning which protocols exist, and the id *validator*
in the same file still only knew one. The seam was tested and the page was tested; the line
between them was not.

`validPendingID` now accepts `<name>:<id>` as a **convention about ids**, not as knowledge
of SAML — a bounded lowercase namespace and a bounded, character-restricted body. The
unnamespaced form keeps its exact 43.

The body is bounded rather than exact because it is **not this service's to mint**: a
service provider chooses its own request id, and an unsigned AuthnRequest can be sent by
anyone. So it is also refused at the parser now — `ValidRequestID` enforces the ASCII form
of the xsd:ID the schema already requires, with a length bound, because that value becomes
a primary key, a query parameter on the login URL, and an `InResponseTo` the service
provider reads back. Three places an attacker-chosen string would otherwise arrive
unbounded, none of which had a check.

## What this cost, and what it is worth

Three defects, all in the same flow, none visible to 38 mutations or a full integration
suite. The pattern is the same each time: **a seam only one caller uses gets tested only if
something drives that caller.** Here the only thing that does is a browser hitting the real
login page.

Two of the three were also invisible to the acceptance suite's first run — the RLS failure
masked the NULL scan, and both masked the id-shape refusal — so each fix revealed the next.
A check that stops at the first failure finds one bug per run, and that is fine: it found
three bugs in three runs that nothing else was ever going to find.

`scripts/acceptance-saml.sh` earned its place before it finished its first execution.

### Four changes so this costs less next time

**The suite reports every section rather than the first failure.** `die` abandoned the
process, so each run surfaced one defect and the next was visible only after the first was
fixed and redeployed — three bugs, three round trips, with the metadata and Single Logout
sections passing pointlessly each time. The sections are independent, so `die` now abandons
only its own; a section that needs an earlier one's result names the result it is missing.
A panic that is *not* a section abandoning itself is re-raised, because a bug in the harness
must never be reported as a finding about the service.

**The gate builds the acceptance modules.** It did not. They are separate modules, so
neither the backend nor the demo section reaches them — `go build ./...` does not cross a
module boundary. The thing that catches what the gate cannot was not itself compile-checked,
and a harness that does not build is discovered during a rollout by whoever is holding the
release.

**A contract test pins the join that broke.** `validPendingID` and `RequestPrefix` were two
rules written independently, each correct alone. Changing the prefix to something the
namespace rule rejects now fails at the moment of the change.

**A test drives the login page with a namespaced id at all**, which nothing did.

## Staging (2026-09-21)

Migrations 040–045 applied. The SAML key set created with `keyctl -purpose saml generate`
and promoted with `rotate` — the first key of a purpose this instance had never had — and
the service rolled to `zed-auth:p4-08c` after two intermediate builds, each replaced
because it could not complete a single SAML login.

`scripts/acceptance-saml.sh` reports **39 passed, 0 failed**, and its two throwaway
registrations remove themselves. `docs/PLAN/17`'s Phase 4 criterion — "a SAML-only legacy
application completes a full SP-initiated login" — is met on a real deployment, on both
bindings, verified by verifying the assertion against the certificate `/saml/metadata`
publishes rather than by observing that a form came back.

Three deployments to get there, and each one was a defect this suite found and nothing
else could. That is the number worth remembering: the feature passed its own gate, was
merged, and was deployed, and it had never once completed a login.

### One operational note

`keyctl generate` writes the private key **before** inserting the row, deliberately — a row
pointing at a missing file stops the service from starting, while a file with no row is
inert. The first attempt failed between the two because the schema was a release behind, so
a key file with no row was left behind. Harmless, and removed, but worth knowing the order
so the orphan is recognised rather than puzzled over.

The runbook's build step is also now unnecessary: `backend/Dockerfile` copies `/keyctl`
into the runtime image, so the tool can be run from the image being deployed instead of
built separately — which makes it impossible for the tool and the service to be different
builds. The rollout used it that way.
