## Decisions worth keeping

### Single Logout is refused, in the protocol's own vocabulary

The card allowed implementing it or documenting its absence. Front-channel SLO iterates
every service provider in a session through the user's browser, and any one of them being
slow, unreachable or wrong leaves a **partial logout** — a user told they are signed out
of applications they are not. That failure is silent and users act on it.

So `/saml/metadata` advertises no `SingleLogoutService`, and `/saml/slo` answers
`RequestDenied` with a readable reason rather than 404. A 404 reads as a misconfiguration
to retry; a refusal reads as a decision. Advertising the endpoint would be worse than
either, because a service provider would build a logout button on it.

### One seam, not two

`internal/login` hands a finished sign-in back through a single interface. The tempting
change was a second seam and an `if`, and it is wrong twice over: the login page would
learn which protocols exist, and every future protocol would edit the most
security-critical path in the service — a branch that has to be right for password, for
the factor step, for a refresh, and for the forced-enrolment detour.

The request id carries a `saml:` namespace and a dispatcher routes it. `internal/login` is
not edited at all.

### A SAML login is `token.issued`

F-8 asks that SAML logins appear "identically to OIDC logins". A new
`saml.assertion.issued` type would be invisible to every query that exists — the console's
audit screen, an operator asking what was issued to whom, a detection rule. So it is the
same event with `protocol: saml` in the payload.

### The NameID is stored, not derived

`HMAC(secret, user || entity_id)` needs no table and creates a secret that **can never be
rotated**: rotating it re-identifies every user at every service provider as a stranger.
"We can never change this key" is a worse property than a table.

## What the mutations found

Twenty-seven died immediately. Four survived, and each was a test that could not fail.

**The bomb defence was untested as a memory property.** Removing the `LimitReader` still
produced `ErrBomb` — after inflating everything. An error-only test cannot tell a bounded
reader from an unbounded one, so the test now measures allocation.

**"The parsed request carries no ACS URL" named one field.** The real property is that
*no* field carries it. It walks the struct by reflection now, so adding a field that reads
the request's own ACS URL fails rather than quietly becoming a redirect nobody approved.

**"The database refuses an email NameID" was satisfied by a primary-key collision.** It
reused a user that already had a row, so the insert was refused before the CHECK was
consulted. Removing the constraint left it green. It uses a different user now.

**The routing predicate had no test at all** until the dispatcher got one — a wrong answer
there is invisible: the login page renders, the user signs in, and the flow completes
against the wrong protocol.

## Two bugs found while wiring, either of which would have failed silently

**The `RequestedAuthnContext` was being dropped across the login page.** `Pending` did not
carry it, so a service provider's requirement survived only for a user who *already had a
session* — and the login path is exactly the one an attacker with no session takes. That
is the "never ignored" half of C-6 defeated by a round trip. It is a stored column now,
checked on both paths.

**`ByID` read an RLS-protected table with no tenant set.** Every policy evaluates false, so
it would have returned nothing: a login refused for a reason invisible in the logs. It goes
through a bounded `SECURITY DEFINER` function now, and a test asserts the direct read
genuinely sees nothing — so the function is demonstrably necessary rather than decorative.

## The gosec finding, answered rather than silenced

G705 — XSS via taint analysis, HIGH confidence — on writing the self-submitting form. The
taint is **real**: `RelayState` and the destination are attacker-influenced and do reach
that buffer. They are also already neutralised by `html/template`'s contextual escaping,
which tests assert and which a mutation rebuilding the form by concatenation turns red.
gosec cannot see through the call, so it flags the write rather than the construction.

Silenced at that one line, with the reasoning and the test named — not by excluding the
rule, which would hide the next one.

## An operational note

The gate and a full integration run must not execute concurrently. Both drive
testcontainers, and running them together produced three failures in packages that pass
standalone — the same shape as the earlier "never run the mutation script and the gate at
once", and equally misleading to read.

## Two gaps found while writing this record, and closed

Both were the same shape: something stored and not enforced, which is worse than not
offering it — an administrator who ticks a box believes it does something.

### Signed AuthnRequests

`want_signed_requests` and `certificate` were stored by migration 040 and consulted by
nothing. Now: verified on the **HTTP-POST** binding through the same `saml.Verify` every
assertion goes through, so the signed element must be the element consumed.

**Refused on HTTP-Redirect.** That binding does not sign the XML — it signs a query string
as an octet sequence, with the signature in a separate parameter, which is a different
construction with its own canonicalisation rules and its own history of implementations
verifying the wrong bytes. It is not implemented, so a registration that requires signing
is refused there rather than accepted unverified. A visible failure an administrator can
act on beats a flag that silently verifies nothing.

### IdP-initiated sign-on

`GET /saml/init?entity_id=…`, **opt-in per registration and off by default** — the card
said "consider making it opt-in", and that is the answer rather than a suggestion.

The risk is stated in the endpoint's own documentation rather than implied. An
SP-initiated login is correlated: the service provider made the request, remembers its id,
and checks `InResponseTo`. An IdP-initiated assertion answers nothing, so anyone who can
cause a browser to visit that URL can have an assertion delivered — the same shape as a
CSRF. Some service providers handle it; many log the user in.

Three properties make it as safe as it can be:

- A registration that has not opted in receives **nothing at all**, not even a SAML
  failure, which would still be delivering something it never asked for.
- A live session is required. The endpoint never drives an authentication of its own for a
  service provider chosen by whoever sent the link.
- The assertion carries **no `InResponseTo`**. Signing in through the hosted login needs an
  id to find the browser again, so one is minted — and `idp_initiated` on the row is what
  stops that bookkeeping id being echoed back, which would invent the correlation this
  flow does not have.

It reuses the pending-request table and the resume seam rather than teaching the login
page a `next` parameter. A `next` is a URL the page redirects to after authentication,
which is an open redirect unless every path through that page validates it — a new hole in
the most security-critical surface in the service, opened for one flow.
