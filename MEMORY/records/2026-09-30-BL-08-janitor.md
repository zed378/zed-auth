# BL-08 — the tables whose cleanup nothing could reach

**Date**: 2026-09-30
**Backlog entry**: `TASKS/BACKLOG.md` § BL-08 (rewritten and closed here)
**Branch**: `fix/BL-08-janitor`
**Found by**: the cross-phase audit of 2026-09-30 (`TASKS/AUDIT-2026-09-30.md` AU-15)

## What was wrong

Five tables written on a request path had no reachable cleanup. Three had
functions or methods nobody called; two had nothing at all.

| Table | State |
|---|---|
| `saml_authn_requests` | Plain `DELETE`, uncalled — and it would have removed nothing if called |
| `saml_assertion_ids` | Plain `DELETE`, uncalled, same |
| `idempotency_records` | Correct `SECURITY DEFINER` function, **also uncalled** |
| `user_tokens` | No sweeper at all |
| `refresh_tokens` | No sweeper at all, and `session_id` is `ON DELETE SET NULL`, so the hourly session sweep nulled the link and left the row — one per login *and* one per rotation |

Two of the plain `DELETE`s could not have worked. Under `WithInstanceScope`,
`app.current_org_id` is the empty string, `current_org_id()` is NULL, every
tenant policy evaluates false, and the statement **succeeds having removed
nothing**. No error. A sweeper in that state logs a cheerful zero forever.

## The three-part fix, and why any two of them is not a fix

**Migration 046** adds `sweep_saml_authn_requests`, `sweep_saml_assertion_ids`,
`sweep_user_tokens` and `sweep_refresh_tokens` — `SECURITY DEFINER`, pinned
`search_path`, `EXECUTE` to `auth_app` alone, each bounded per call and narrowed
to rows already past their cutoff. None takes an organization, none returns row
contents, and none can reach a live row, so none becomes a way to erase a
credential or a pending login.

**`internal/maintenance`** owns one janitor over six tables, `sessions`
included. Not a goroutine per table, and that is the point: the defect was never
a forgotten line in `main.go`, it was that **nothing owned the question "is
everything with an expiry actually being swept?"**. A table added next year is a
`Task` in that list or it is not swept, and the list is short enough to read in
one screen.

**A test that runs the broken version.**
`TestABareDeleteUnderInstanceScopeRemovesNothingAndSaysNothing` performs the
plain `DELETE` under instance scope and asserts it returns no error, zero rows,
and leaves the row in place. Without it the fix is indistinguishable from the
bug — every other test in the package passes either way.

## Decisions worth keeping

### The session sweeper was folded in, not left beside

`runSessionSweep` worked, so leaving it would have been the smaller diff. It was
deleted anyway, for two reasons. Two sweepers on two schedules put the question
above back into two places. And it logged only when it had removed something,
which made it **silent when idle and silent when stopped** — precisely `BL-01`'s
shape, in the one sweeper that did run.

The janitor logs one line per pass with every table's count, always.

### Retention is per table, and each margin is an argument

- The two SAML tables: deleted at expiry, no margin. Both are refused by two
  independent checks once expired, so a kept row protects nothing and costs a
  page of memory on the login path.
- `user_tokens`: a week. "The link you sent me does not work" is asked days
  later and the row is the answer.
- `refresh_tokens`: thirty days, the longest. The row is the lineage `P3-06`'s
  reuse detection walks. An expired token needs none of it — expiry refuses the
  credential first — but deleting the family history at expiry would remove it
  at exactly the moment a stolen token surfaces.
- `sessions`: a week, unchanged, for the reason `P1-11` already gave.

`Task.Before` is a function per task rather than one duration for the janitor,
so each table states its own window against a single reading of the clock.

### `session.Manager.SweepBefore`

One new method, expressing the same work as a cutoff rather than a retention
plus a clock. The janitor owns retention for every table it sweeps; without this
it would have subtracted a duration from a clock and `Sweep` would have added it
back.

## What I got wrong on the way

**The tests were behind the wrong build tag.** I first put all of them in
`janitor_integration_test.go`, so proving that the janitor isolates a failing
task needed Docker. That is absurd for a package whose subject is housekeeping
that only appears to work. Error isolation, per-task cutoffs, the batch bound and
the always-log-success rule are properties of Go code. They are in
`janitor_test.go` now and run in fourteen seconds with no daemon; only the two
SQL proofs stay behind the tag.

**I wrapped Go commands in `timeout`.** On this shell that kills the wrapper and
not the process tree, so each timed-out run left an orphaned `go.exe` contending
for the build cache and made the next run slower. I spent a while measuring a
problem I was causing.

**The `BL-08` rewrite left duplicates.** Slicing the backlog between the first
`BL-08` heading and the next `BL-09` heading silently duplicated `BL-09` and kept
the stale `BL-08`. Caught by reading the headings back rather than trusting the
edit.

## The counting lesson

The original entry said three tables. It was written from a grep for `Prune` and
`Sweep`, which finds the cleanup code that exists and therefore cannot find the
two tables that had none.

**Looking for cleanup code with no caller finds less than looking for every
column named `expires_at`.** The second search is what found `user_tokens` and
`refresh_tokens`, and it is the one to run when a table is added.
