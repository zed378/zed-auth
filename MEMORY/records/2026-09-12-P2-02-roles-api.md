## The first project-scoped routes

Everything under `/v1` until now has been organization-scoped: the organization is in the path, `ORG_ADMIN` over it is the requirement, and the tenant scope follows. Roles are the first resource where the *project* is the unit of authority, which is why `P2-05` had to come first.

`PROJECT_OWNER` over the project in the path, which an `ORG_ADMIN` or `ORG_OWNER` of the containing organization also satisfies (`PG-32`). Nothing is taken away from an administrator who has access today.

## What the endpoint tests found that a unit test could not

`P2-05` proved the hierarchy as a pure function. These tests prove the hierarchy is what the routes actually consult — and the difference produced a real finding.

**A `PROJECT_OWNER` asking about another project in the same organization was answered `403`.** It should be `404`.

The visibility rule was written in `P1-16`, when every route was organization-scoped, and asked "does the caller hold anything over this organization?" — where "anything" includes *being a member of it*. A `PROJECT_OWNER`'s token belongs to the organization, so that was true for every project in it. And listing projects requires `ORG_ADMIN`, so the same caller cannot enumerate them. A `403` on one project id therefore answered *"does this project exist?"* for anybody willing to send one request per guess — `docs/SECURITY/02` §12's disclosure, in a narrow role that was supposed to be the safe one.

So visibility now splits by scope: on a project-scoped route it follows **grants** rather than membership — over the project, or over the organization containing it. An `ORG_ADMIN` still gets `403` for a project in their own organization, because they can list them and concealing one buys nothing.

The unit tests in `P2-05` could not have seen this. The difference only appears once a route has a project in it.

## A second bug, from the test that almost was not written

The role list is the only one in this API ordered by something other than creation time — roles are read as a reference table, and somebody looking for `billing-admin` should not have to know when it was created.

So its cursor carries a key. The first implementation put that key in the cursor's `ID` field, which looked equivalent and was not: `DecodeCursor` requires a **timestamp alongside an id**, so every second page was refused with "The page token is not valid."

Every other test passed. The bug lives entirely on the second page, and nothing else in the suite asked for one.

`Cursor` now expresses both forms explicitly — a time position `(After, ID)` or a key position — and refuses a token carrying both, because which one a reader honours would decide where the page starts. One type, one validator, and the second shape named rather than smuggled through a field meant for something else.

## Decisions

**`DELETE` is not raised to `ORG_OWNER`**, unlike projects and applications. Those raised it because deleting one is irreversible and silently breaks consumers. A role delete is already refused while any grant references it, so the destructive case cannot be reached by surprise — and an operator who cannot tidy up an unused role will leave it there instead, which is how a permission list becomes unreadable.

**The key is absent from `RoleUpdate` entirely**, rather than present and rejected. A field a caller can send and always be refused is a field somebody builds a form for.

**`permission_keys` replaces the whole set.** A partial update of an array is ambiguous — add, remove, or replace — and the audit event records what was *added and removed*, which needs a complete before and after.

**Grant counts are one query for the page.** The obvious implementation is a count per row, which is an N+1 against a table that grows with every user: the role list would get slower for every account the organization adds.

**The audit events live in the handler, not the store.** An audit row needs an actor and the store has no caller. `P1-14` found a lockout event that was never written because it was emitted where no organization was in scope; writing one from the store with a nil actor would be the same mistake deliberately.

The update event records the **difference** rather than a snapshot, so "who gave this role billing access" is one row to read instead of two rows and a comparison. The delete event keeps the permissions the role carried — after the row is gone, the audit log is the only record of what it could do, and that is exactly what an incident asks about.

**The third mutation was green the first time**, and that is the useful part. What `requireProject` actually prevents is a `200` with an empty list for a project that does not exist, which tells a console the project is real and simply has no roles. No test covered it until the mutation said so.
