## What closes here

`P2-04` put roles in the token, and a token is a snapshot. The gap between "this token says so" and "this is still true" is where a revoked administrator keeps their access until expiry.

`TestARevocationIsHonouredOnTheNextCheck` mints the caller's token **once**, before the revocation, and reuses it for both questions. The only way the second answer can differ is if the decision read live data. That is the whole premise of the endpoint, and it also closes the item `P2-03` had to leave unticked.

## The permission is `resource.type:action`, which was already decided

`P2-01` chose `resource:action` for permission keys, from `docs/PLAN/08`'s own examples. The contract's example asks to `approve` a `purchase_request`. So the permission is `purchase_request:approve`, derived rather than sent.

Making the caller send the permission separately would let the two disagree — a consumer sending `action: "delete"` with `permission: "read"` has written a bug this endpoint cannot see, and would answer confidently.

A malformed question is a **400, not a deny**. A deny would be technically correct — nobody holds a key that cannot exist — and would hide the caller's bug behind a plausible answer, from the one person able to fix it.

## The oracle, which is the real risk in this endpoint

An authorization endpoint is an excellent enumeration tool if you are not careful. It is cheap, it is called constantly so the traffic is unremarkable, and — deliberately — **it writes no audit rows**.

So a subject who does not exist and one who holds no matching role must produce responses that are identical **byte for byte**. Not merely the same `allowed`: the same `reasons`, the same `matched_policy`, the same status. Anything else answers "does this user exist in this organization?" to anybody holding a valid client token.

The distinction is recorded server-side, in the log, where an operator can see it and a caller cannot.

My first version of that test failed for an unrelated reason worth keeping: the fixture helper gave **every** role it created the `purchase_request:approve` permission, so the subject meant to be *unauthorized* was authorized. The helper now takes the permissions as a parameter.

## Failing closed, and why 503 rather than `200 {"allowed": false}`

`docs/PLAN/13` says availability of a decision is never a reason to weaken security posture. Nothing is allowed by a failure.

But `200 {"allowed": false}` would be a lie with consequences. It says *we checked and the answer is no* — so a caller may cache it, an operator watching the allow/deny ratio sees a policy change rather than an outage, and the error rate `docs/PLAN/13` wants alerting on stays flat while every decision in the fleet fails.

`503`, with the standard envelope and a message telling the caller to treat it as denied. That needed a new fault class — the API had never needed a 503 — and `UNAVAILABLE` is distinct from `INTERNAL` for a reason a caller can act on: `INTERNAL` says a bug happened here, `UNAVAILABLE` says a dependency did not answer.

**The fault injection had to be narrowed.** Closing the shared pool broke *authentication* — the middleware reads the caller's manager roles on every request — so the request failed with a 500 before reaching the code under test, and the test was asserting nothing about failing closed. Only the decision's own pool is closed now.

## `Member`: the role the table could not express

The policy table could say "an administrator" or say nothing, because the zero `Requirement` is unsatisfiable by design. Both are wrong here.

This endpoint is called by consumer applications about their own users, on every protected request they serve. Requiring `ORG_ADMIN` would mean **every service that checks a permission holds an administrative role over the organization** — the exact inversion of least privilege, and a far larger blast radius than the endpoint needs.

So `Member` exists: "holds a valid token for this organization", satisfied by the token's own tenant rather than by any grant, and sitting under every other role. It is not a `manager_roles` value and never appears in that table.

I wrote the policy entry as `ORG_ADMIN` first, with a comment explaining that `ORG_ADMIN` was not required — a contradiction that was only visible once written down.

**Adding a role silently un-exhausted an exhaustive test.** `TestTheHierarchyMatchesThePlan` iterates a list, and `Member` was not in it, so the test kept passing while covering five of six roles. Its list and table now include it, which is the only reason it is still what it claims to be.

## What bounds the endpoint

Both scopes come from the token. The organization is the caller's own, and the project is the one their **client** belongs to. Neither can be named in the request — given a free choice of project, a caller could map another organization's grants one question at a time.

## Not finished

**The latency targets are not measured.** `docs/PLAN/12` asks for p50 < 20ms, p95 < 80ms, p99 < 150ms, which are the tightest in the document. `scripts/loadtest` exists and can measure them, and it must run on the VM — which is unreachable this session. Left unticked.

`P2-07` adds caching, deliberately after this: a cache over a decision whose cost has not been measured is a cache tuned against a guess.

Metrics are wired to the two series `P0-11` reserved for this task — `authz_decisions_total` labelled by outcome and mode, and `authz_check_duration_seconds` — with failures counted as their own outcome rather than as denials.
