# P1-10 — RP-initiated logout

**Date**: 2026-09-10
**Branch**: `feat/P1-10-logout`
**Spec**: [`MEMORY/specs/P1-10-logout.md`](../specs/P1-10-logout.md)

---

## What this is

`GET` and `POST /oidc/logout` — OpenID Connect RP-Initiated Logout 1.0. Discovery now advertises it as `end_session_endpoint`, which completes the set a conforming relying party configures itself from.

With it, the session lifecycle closes: `P1-12` starts one, `P1-11` maintains it, and this ends it.

## The one decision this endpoint exists to get right

> **A `GET` logs somebody out only when the request proves it was initiated by a party that already holds a token for that very session.**

A `GET` is triggerable by any page on the internet — an `<img>`, a prefetch, a link in an email. Acting on a bare one is a cross-site request forgery whose payload is "log this person out". The `id_token_hint` is what turns an unauthenticated GET into an authenticated one, because only a party that completed the flow has one.

So the rule is: a hint that verifies (signature, `typ: JWT`, `iss`), whose `sid` **and** `sub` match the session the cookie resolves to. Everything else — no hint, an unverifiable hint, a hint for another session, a hint for another user, a hint with no `sid`, a matching hint but no cookie — gets the confirmation interstitial.

**A hint for somebody else's session logs nobody out.** Not its own subject, and not the cookie's owner. It falls through to the interstitial, which acts on the cookie's session and only with a click. That is tested from both directions, because "a crafted hint does not log out its target" and "a crafted hint does not log out the visitor either" are different failures.

`shouldActWithoutAsking` is eleven lines and is the whole security argument. Three mutations attack it and all three are caught.

## What is deliberately not checked: the hint's expiry

An ID token lives five minutes (`P1-07`). A user signing out an hour after logging in is the ordinary case, not the exception, so rejecting an expired hint would mean nearly every real logout falls back to a confirmation click.

The hint is **evidence of who initiated the request**, not a credential being honoured. What actually bounds it is that it must match the live session — so a stale hint for a session that has since ended proves nothing and gets the interstitial anyway, which is the correct outcome by a different route.

## Clearing the cookie is not logging out

Step 3 of the card says so, and it is worth restating because it is the failure that looks like success. A cookie the user copied, a proxy logged, or an attacker captured still works if the server-side row survives. The row is revoked; the cookie is cleared **as well**, never instead.

A mutation that clears the cookie without revoking is caught — not by a test on `revoked_at`, but by the integration test that replays the same cookie at `/oauth/authorize` and asserts it lands on the login page. That is the DoD item as written, and it would also catch a system that revokes the row and keeps honouring the cookie from cache.

The cache invalidation runs **after** the commit, through the function `session.Manager.Revoke` returns. `P1-11` built that ordering deliberately: invalidating first lets a concurrent reader repopulate from the pre-commit state.

## "Log out everywhere" is two things, and one of them is easy to forget

Every session **and** every refresh token. Without the second half a user who pressed the button still has live refresh tokens, and an application holding one mints a fresh access token minutes later — so the button ends the browser sessions and quietly leaves every integration signed in.

`RefreshStore.RevokeAllForUser` is the missing half, and the mutation that removes the call is caught by an integration test counting live rows.

The checkbox is **unchecked by default**. Signing out of one application should not silently end a user's session in every other one, and a default that did would be a surprise measured in other people's support tickets.

## The redirect target

Exact match against the client's registered `post_logout_redirect_uris`, and an unregistered value is refused with a **rendered page and no redirect at all**. This is the same branch `P1-06` calls the most important in its file: reporting the error by redirecting to the unvalidated address *is* the open-redirect vulnerability, delivered by the code meant to prevent it.

An unvalidated URI never reaches the `request` struct, so no later code path can redirect to one — the field is only ever set after the match succeeds. A mutation that redirects on refusal is caught; so is one that relaxes the match to a prefix, tested against six near-misses including a trailing slash, an appended query, a scheme change and a case change.

An unknown `client_id` and an unregistered address give the **identical** answer, so the endpoint cannot be used to find out which client ids exist.

## Where it lives, and the naming cost

In `internal/login`, not a new package. The confirmation interstitial needs everything the login page already has — CSRF, the hashed-CSP shell, the header discipline, the branding read — and a separate package would have to export all of it across a boundary to render one more page.

The cost is a package called `login` that also serves logout. That is stated in the package doc rather than hidden: it is "the browser pages this service serves". `writePage` was lifted out of the login handler's method into a package-level function at the same time, so both surfaces get their headers from one place rather than from a copy.

## On not using an opaque server-side reference

`P1-12` carries a pending authorization request by opaque id and is emphatic that echoing the parameter set through a hidden field would be wrong. This task does the opposite: the three parameters travel through the interstitial in hidden fields and are re-validated on the `POST`.

The difference is real rather than convenient. A pending authorization has seven parameters whose **validation order** is itself the security property — everything except `client_id` and `redirect_uri` must be reported by redirecting, so re-deriving the order is a second place to get it wrong. Logout has one parameter that matters and one function that validates it, called unconditionally on both paths. A hidden field the user can edit is a hidden field that same check rejects, and a test edits it to prove so.

## Gap raised

**`PG-20` — `docs/PLAN/05` treats RP-Initiated Logout and Back-Channel Logout as the same specification.** The sentence is:

> "Back-channel logout (RP-Initiated Logout) is a later phase; MVP needs per-app logout + a 'log out of all sessions' button."

They are two different OpenID Connect specifications. **RP-Initiated Logout 1.0** is the front-channel redirect this task implements. **Back-Channel Logout 1.0** is server-to-server: the provider POSTs a logout token to each relying party's registered `backchannel_logout_uri`, with no browser involved. Neither implies the other.

Read literally the sentence defers the endpoint the same document lists in its own core-endpoint table, and then asks for "per-app logout" in the MVP — so it contradicts itself unless the two are separated. `P1-10`'s card has it right (step 1 implements RP-initiated, step 7 defers back-channel); `DF-09` copied the plan's conflation and is narrowed to back-channel only.

Built per the card. `docs/PLAN/05` should be amended to name the two specifications separately.

## Verification

Seven mutations, each reverted, each confirming its test fails when the control is removed:

| Control removed | Test that failed |
|---|---|
| a GET acts without proving itself | `TestAGetThatCannotProveItselfNeverRevokes` |
| the hint no longer has to name this session | same |
| the redirect match becomes a prefix | `TestPostLogoutMatchingIsExact` |
| the cookie is cleared without revoking the row | `TestAfterLogoutTheSameCookieRequiresFullReauthentication` |
| "everywhere" leaves the refresh tokens alive | `TestSignOutEverywhereEndsEverySessionAndRevokesRefreshTokens` |
| the CSRF check is skipped | `TestTheConfirmationRequiresACSRFToken` |
| the refusal redirects to the unregistered address | `TestAnUnregisteredPostLogoutRedirectIsRefusedWithoutRedirecting` |

`internal/login` stays above its coverage floor at 82.1%.

## What is still missing

- **Back-channel logout.** `DF-09`, narrowed. Nothing here precludes it: the audit entry, the scope, and the session id are all already recorded, and a back-channel implementation adds a delivery mechanism rather than changing this one.
- **A "sign out" link in the console.** `PF-42` owns the logout screen; `P1-21` is what gives the console a session to end.
- **A metric with a consumer.** `auth_logout_total{outcome}` counts `asked` as well as `completed`, because a rise in `asked` means relying parties have stopped sending a usable `id_token_hint` and every user is getting a confirmation click they did not used to get. Nothing alerts on it yet.
