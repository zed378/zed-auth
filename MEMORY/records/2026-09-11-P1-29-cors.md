# P1-29 — Cross-Origin Access Policy

**Date**: 2026-09-11
**Branch**: `feat/P1-29-cors`
**Decision**: [ADR-020](../DECISIONS.md). Closes `PG-17`.

---

## Why this task exists

It was not on the board this morning.

`P1-27` built an end-to-end environment and pointed a real browser at the login flow for the first time. Nothing worked — and the reason was not a bug in the test.

**A public client cannot complete the Authorization Code flow without CORS.** The authorize step is a *navigation* and needs nothing. The code exchange is a `fetch` to `/oauth/token` from the application's own origin, and the browser refuses it before the request is sent. So:

- the demo SPA could not exchange its code at all, and
- the console could not exchange its code **or** make a single Management API call.

The console has therefore never been able to sign in from a browser in any deployment where it is not served from the service's own origin — which is every deployment `docs/PLAN/06` describes, including staging today (`console.zedth.my.id` against `auth.zedth.my.id`).

Every test that passed until then drove these flows with `curl`, which has no same-origin policy. That is the same sentence as the CSP bug `P1-27` found an hour earlier, and it is not a coincidence: **a test harness that cannot enforce browser rules cannot find browser bugs**, and a suite made entirely of such harnesses will report a green login flow that no person can use.

`PG-17` had forecast this in Phase 0 and written a rule for the interim: *no endpoint may add CORS headers to unblock a caller*, because a one-endpoint exception is how an instance-wide `*` arrives. That rule is why this was raised rather than decided — it is a data-model and API-contract change, which `AGENTS.md` rule 9 puts behind a deliberate process. Authorized before implementation.

## The split, and why one policy is wrong

| Endpoint | Policy | Credentials |
|---|---|---|
| `/.well-known/*`, `POST /oauth/token` | `Access-Control-Allow-Origin: *` | Never |
| `/oauth/userinfo`, `/v1/*` | The calling application's `allowed_origins` | Never |
| Everything else | No headers at all | — |

**The public set is public by construction.** The token endpoint hands nothing to a caller who cannot present a valid authorization code *and* the PKCE verifier that produced its challenge, and it reads no cookie. A page reading it learns nothing `curl` did not already offer. A per-application policy is not merely stricter here — it is impossible: the exchange happens before the client holds any token, so there is nothing to resolve an application from.

**Everything else is per application**, because `/oauth/userinfo` returns an email address and `/v1/*` returns an organization's users. `PG-17`'s specific objection to an instance-wide allowlist was that it would let any tenant's registered origin read any other tenant's data, and that objection is correct.

**Credentials are permitted nowhere**, including where they could be. `/v1/*` authenticates a bearer token and reads no cookie, so allowing credentials would create ambient authority for no purpose — and would force the service to make a larger claim about an origin than it needs to. The console was changed to `credentials: "omit"`; its SSO session cookie belongs to the silent-renewal *navigation*, which carries cookies regardless of what the API client says.

## Three decisions worth the words

**The `client_id` claim is read without verifying the signature.** Deliberately. A forged one buys nothing: the origin still has to appear in *that* application's list, so naming somebody else's application only makes the check fail, and naming your own is what an honest client does. The signature is verified microseconds later by the bearer middleware, which is what decides whether the request runs at all. Verifying twice would cost an RSA operation per request to answer a question whose wrong answer is "the browser hides a response the caller was entitled to". `TestForgingTheClientIdDoesNotWidenWhatAnOriginMayRead` is the assertion.

**A preflight is answered from the union of every application's origins.** A preflight carries no `Authorization` header — that is what a preflight *is* — so the specific application cannot be known. What that discloses is one bit about a value the asker already holds, and the actual request is still checked per application. The alternative is refusing every preflight, which means nothing works. A refused preflight answers `204` like an allowed one, because a `403` enumerates the registered origins one guess at a time.

**CORS sits outside the bearer guard, not inside it.** A console whose token has just expired has to be able to *read* its own `401` to know to renew; a `401` with no CORS headers is a fetch that rejects with no status at all, indistinguishable from an unreachable service. So when no usable token is present the preflight rule applies — the response is an error envelope with no personal data in it.

## What the tests assert, and what they cannot

Unit tests cover the header logic per endpoint, including every negative: another application's origin, a wildcard where personal data is served, credentials anywhere, a forged client id, `Vary: Origin` on refusals, and the status-code equality that keeps a preflight from enumerating.

Integration tests cover the column, the constraint, and both lookups **against a real database** — `PG-24`'s standing warning is that a migration reading correctly is not the same as a schema being correct, and the bootstrap lookup's signature changed in this task.

What none of them can test is a browser. That is `console/e2e/sso.spec.ts`, and the whole reason this task exists is that its absence hid two production bugs in one morning.

## Found while building it

- **PostgreSQL refuses a subquery in a `CHECK` constraint.** The shape check is an `IMMUTABLE` function instead. Caught by the integration test on its first run, which is the right place to catch it — the migration file read perfectly.
- **`CREATE OR REPLACE FUNCTION` cannot change a return type.** Adding `allowed_origins` to `application_by_client_id`'s `RETURNS TABLE` needs a `DROP` first. Same run, same lesson.
- Both migrations were edited in place rather than superseded, which `PG-24` normally warns against. They had only ever run in an ephemeral test container — never in staging — so there was no deployed database holding the old text. That is the condition under which editing is safe, and it is worth stating because the next person will have to decide the same thing.
