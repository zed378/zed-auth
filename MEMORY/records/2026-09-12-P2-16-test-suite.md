## "Prove the authorization model, not just exercise it"

The card's goal sentence is the whole task. Phase 2 arrived with a lot of tests — each
implementation task carried its own, each with a mutation run. What none of them could do
is make a statement about the model **as a whole**.

Three additions do that.

## The hierarchy, exhaustively — and against an independent oracle

`internal/management/hierarchy_exhaustive_test.go` enumerates every (held role, held
scope, required role, required scope, target): **6,300 combinations, 1,582 of them
allowed.**

The part that matters is not the count. It is that the expectation is **derived from
`docs/PLAN/08` Part C's prose**, in the order the document states its rules, which is
deliberately not the order `Authorize` evaluates them. A table that asked the
implementation what it does and then asserted it does that is a very long way of writing
`true`.

The dimensions include combinations the database should never hold — a `PROJECT_OWNER`
whose `scope_id` is an organization, an `INSTANCE_OWNER` scoped to a project — because
"cannot occur" is an assumption, and an authorization function that misbehaves on a row
that should not exist is one bad migration away from mattering.

Two guards keep it from passing vacuously: fewer than 1,000 combinations is a failure,
and an allow-rate of 0% or 100% is a failure on its own.

Three companions cover what a single-grant table cannot see:

- **Two grants give the union** — a rule that ANDed grants, or let a project-scoped grant
  widen an organization-scoped requirement, would pass every row of the main table.
- **Every outcome is explicable** — across the whole table, a refusal carries a reason and
  an allowance does not. A branch that forgets one is invisible until somebody is
  debugging a 403 at 3am.
- **Invisibility does not depend on the required role** — the 403/404 split must not let
  somebody probe which role a route wants.

That last one failed twice while being written, both times because the **test** was
wrong: first comparing across scopes (a project-scoped route naming no project is a
routing mistake, not a leak), then including a target inside the caller's own
organization (where `MEMBER` is satisfied by membership, correctly). Both are recorded in
the file, because the next person will have the same two ideas.

## Claim tampering

`internal/authz/tampering_integration_test.go`. Every test presents a token **validly
signed by this service's own key** whose claims say something the database does not.

That is not a forgery an outsider can produce. It is what happens if claim assembly is
ever wrong, if a token is minted through a path that skips a check, or if a key issues
something it should not have. The property under test is the one
`internal/management/store.go` opens by promising: roles are read from the database on
every request, never from the token. **A suite that only ever presents honest tokens
cannot tell that promise from a coincidence.**

Six tests: a forged `INSTANCE_OWNER` claim buys nothing; a forged project role claim does
not decide an authorization check; an edited `org_id` does not move the caller into
another tenant; an ID token is not an access token (same key, same audience, different
`typ`); a token with no subject is refused; and a tampered refusal is byte-identical to an
ordinary one, so nothing tells a prober which forgery got further.

The first carries a **positive control**: after the refusals, the real `manager_roles` row
is inserted and an ordinary token must now succeed. Without it, every assertion would also
pass against a route that was simply broken.

## Row level security at scale

`tests/security/rls_plans_test.go` seeds 400 tenants and asserts on **query plans**, not
on the clock. A timing assertion on a loaded CI machine is a flaky test that gets deleted;
a plan assertion is deterministic and names what went wrong.

The failure it guards against is one that breaks nothing: an RLS predicate the planner
cannot push into an index turns a keyed lookup into a sequential scan over every tenant's
rows. Correctness is untouched — the other tenants' rows are read and then discarded. The
symptom is a service that is fine at thirty organizations and unusable at three hundred,
by which time every test still passes.

Writing the "the detector can fail" self-test taught me something worth recording. The
first attempt used a query no index covers, and it **still** planned an index scan — because
the RLS predicate itself is `org_id = current_org_id()`, which is indexed, and steers the
planner onto an index even when the caller's own predicate cannot.

That is the property these tests assert, arrived at from the other direction. The
self-test now uses `manager_roles`, which carries no policy and no org column, where a
bare count has nothing to key on.

## What was already covered

The card's steps 2, 3 and 6 were largely done before this task, and re-doing them would
have been motion rather than work:

- **Integration**: `tests/security/full_flow_integration_test.go` already walks
  organization → project → application → user → login → token claims.
- **E2E**: `P2-11`…`P2-13` shipped 7 Playwright tests covering role creation and
  assignment, organization switching, and a user with no grant.
- **CI**: `make test-integration` and a separate `make test-security` already run the
  security suite as its own visible target.

- **Cross-org and enumeration**: `internal/authz` already had the nonexistent-versus-
  unauthorized subject test, the cross-organization check, and the dependency-failure
  denial; `tests/security` already had RLS enforcement independent of application
  filtering.

Saying so is part of the task: a test suite whose value is claimed rather than located is
one nobody can audit.
