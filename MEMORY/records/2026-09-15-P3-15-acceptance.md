## Deployed first, then accepted

Staging had run the `P1-28` build since 2026-09-11. Phases 2 and 3 had been accepted
against local stacks only. This phase was deployed before acceptance rather than after, in
the order `deploy/vm/deploy.sh` documents:

1. **Backup.** It had not run since 2026-09-11 (`P3-14`'s record covers the fix). Once
   fixed, a fresh dump was restored into a throwaway database and every row count matched.
2. **Migrations** as the owner role, in a one-off container from the new image, while the
   old build kept serving, up to version 34 (`20260914000034`).
3. **Roll out.** The auth service was recreated, then the console and public-site
   artifacts were rebuilt locally and extracted in place, because the bind mount is an
   inode.
4. **The MFA seal key** was generated on the host by `secrets.sh`. The compose files'
   instruction for it was wrong: `/run/secrets`, which neither file mounts. A key that is
   set but unreadable is fatal at startup by design, so following the documentation
   would have produced a service that refuses to start. Both comments are corrected.
5. **Smoke test** through the public hostnames. The new routes answer 401 (they exist and
   authenticate), the console serves the new bundle, and the new guides and changelog
   return 200.

## The three criteria, with evidence

`scripts/acceptance-phase3.sh` runs on the VM against the service's own port and walks each
criterion with a throwaway account. **19 checks, 0 failures**:

| Criterion | What was executed |
|---|---|
| TOTP end to end, including a lost device | Enrol through `/v1/me/mfa/totp` with a code computed from the secret. Show the password alone no longer signs in. Refuse a wrong code, then accept the right one: `amr ["mfa","otp","pwd"]`. Sign in with a recovery code typed in lower case: `amr ["mfa","pwd"]`. Refuse the same code a second time. |
| A rotated refresh token cannot be reused | Rotate, use the new token (so the old one cannot pass as a retry), present the old one: `invalid_grant`. The newest token then fails too, because the family is revoked. |

## The load test, and a bug the load test found

### Sign-in answered 500 on every deployment without a second factor

`docs/PLAN/12` sets targets for silent authorize and `/oauth/token`, and this phase put more
work on refresh. To attribute the cost, the refresh phase was run with MFA on and then with
the seal key removed. **The MFA-off run could not sign in at all:**
`sign-in did not produce a code: 500`.

`cmd/authservice` wired `MFA: factorFramework`. That `*mfa.Framework` is nil when no seal
key is configured, and a nil pointer stored in an interface is not a nil interface. The
login handler's `h.MFA == nil` guard saw a non-nil value, `Required` ran on a nil receiver,
and it panicked.

From `P3-03` (2026-09-12) until this task, a deployment the compose files describe as
legitimate ("its absence is a real deployment rather than a broken one") could not sign
anybody in. Nothing covered that configuration:

- the E2E stack has set a seal key since `P3-10`;
- staging ran a Phase 1 build;
- every login integration test either set a framework or left the field as a true nil.

The fix has two layers:

- **At the call site:** `challenger()` returns a nil interface.
- **In the method:** a nil `Framework` requires nothing.

`TestNoFrameworkIsANilChallenger` guards the wiring. A login integration test hands the
handler the exact typed nil, and it panics with the method guard removed. The fixed build
was then run on staging with the seal key removed (verified from the container's
environment and its log line), and signed in.

### What refresh costs now

Each leg was verified from the container, three runs each, 20 workers:

| | p50 | p95 | p99 |
|---|---|---|---|
| `/oauth/token` refresh, MFA on | 57.7–63.0ms | 141–152ms | 192–220ms |
| `/oauth/token` refresh, MFA off | 58.6–63.1ms | 149–161ms | 221–234ms |
| Phase 1 (`P1-28`), same harness | 46ms | 133ms | — |
| `docs/PLAN/12` target | 50ms | 200ms | 400ms |

**The MFA mandate check `P3-14` added costs nothing measurable.** Folding it into the
rotation transaction was considered, and dropped once measured. The refresh p50 moved from
46ms to about 60ms across Phase 3. That comes from rotation and reuse detection (`P3-06`):
a lineage lookup, a liveness check, and a rotation transaction on every refresh. It now
misses the p50 target in isolation. Under mixed load it misses p50 and p95 (109ms and 264ms
against 50ms and 200ms), as Phase 1 already did at 72.7ms and 209ms.

This is **accepted and scheduled, not fixed**. It runs on a 4-core VM shared with 39
containers, with one replica and no read replica. `docs/PLAN/12`'s remedies are Phase 5's.
About 22 database round trips per refresh is the place to start, and the audit and roles
transactions are the obvious candidates to share one.

Silent authorize (p50 14.7ms, p95 107ms), userinfo and management are within target.

### The second factor on an interactive sign-in

`docs/PLAN/12` sets no target for a person typing, so this is reported rather than judged.
Over six complete sign-ins: the password step (argon2id, then the challenge page) had a
median of 106ms, and the TOTP step (verify, record the counter, open the session, redirect)
a median of 13.6ms. The sample is small because a code works once per 30-second step.

## The Phase 4 threat review

[Recorded separately](2026-09-15-P3-15-phase-4-threat-review.md): 14 findings. Its pattern
is Phase 3's, one level up: **every Phase 4 card adds a way to issue or change access that
bypasses the one login flow the policy checks were built around.** Phase 3 had just shown
what that costs, with `P3-07`'s A-2.

Two findings need a decision before Phase 4 work starts, rather than a card edit:

- **T4-1. Cross-organization sign-in is not designed.** Today's code refuses a session
  from another organization, and looks the password up within the application's own
  organization. `docs/PLAN/08` Part C says nothing about whose MFA mandate or allowed
  sign-in methods apply to a partner's user. As written, delegation would be a way around
  the granting organization's MFA mandate.
- **T4-2. Subset validation is checked where grants are written, and every reader ignores
  it.** Token claims and `/v1/authz/check` read `user_grants` and never `project_grants`.

Both were checked against the code before being accepted.
