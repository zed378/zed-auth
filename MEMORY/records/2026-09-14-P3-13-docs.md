## A required second factor that was never required

The admin guide has to describe the grace period, so the grace period had to be read
rather than remembered. `authn.RequireMFA` treats a mandate with no
`mfa_required_since` as **inside the grace**, which its comment justifies: an
organization upgrading with the flag already set gets a grace "starting now". But
nothing ever wrote the timestamp afterwards. `StampMandate` runs only on a PATCH that
turns the mandate from off to on, so an organization that was already on never got one.
Its grace started now on every sign-in, which means it never ended.

Two ways in, and both were reachable:

- **An organization that set `mfa_required` during Phase 2.** The console offered the
  switch then, labelled "not enforced yet".
- **An organization created with `mfa_required: true`.** `CreateOrganization` never
  called `StampMandate`.

In both cases the policy said MFA was required and nobody was ever asked for it. No
error, no log line, and the impact endpoint reported `grace_ends_at: null`, which reads
as "not enabled".

Fixed in both places:

- **Creation stamps**, and writes `organization.mfa_required.enabled` like the update
  path does, so "who turned MFA on" does not depend on how the organization came to have
  it.
- **Migration 034 stamps every unstamped mandate** at migration time. The grace starts on
  upgrade, not when the flag was set, because nobody was told there was a deadline. The
  migration is data-only and idempotent. Its down migration does nothing, since removing
  the stamps would restore the bug, not the schema. The stamp is written as RFC 3339 with
  an explicit `Z`. Go refuses a timestamp without a zone, and an unparseable stamp reads
  as no stamp, which is the same bug again.

`TestTheBackfillStampsOnlyUnstampedMandates` runs the embedded migration file twice
against seeded rows. The unstamped row gets a deadline the service can parse. The
stamped row keeps its date, which is what fails when the `NOT settings ? ...` guard is
removed. The unmandated row is untouched.

## The console said the switch did nothing

`PoliciesPage` still carried its Phase 2 copy: a **"Not enforced yet"** badge and
**"Setting this changes nothing today. It will take effect when multi-factor enrolment
ships in Phase 3."** Phase 3 enforcement shipped in `P3-07`, and the screen went on
saying this through `P3-12`.

This is the Phase 2 lie reversed, and it is the more dangerous direction. An
administrator told a switch is inert has no reason to warn anybody before flipping it.
Fourteen days later, everybody without a factor is sent into enrolment at sign-in.
`policies.test.tsx` had a test named *"never presents itself as enforced"* that asserted
the false copy.

The section now says what the mandate does. It uses `GET .../mfa-impact`, which `P3-07`
built for exactly this and nothing had called, to show how many active members have no
factor. Switching the mandate on joins the existing reduces-access confirmation, which
names that count and the grace length. The grace length comes from the service: a new
`grace_period_days` field on `MfaImpact`, so the console never holds its own copy of
"14".

Also in the console: **Projects, Users, Policies and Audit Log carried a "P1" nav badge
with the tooltip "Arrives in phase P1"**, on screens that exist. The Settings placeholder
said "built in phase 1". Organization settings (branding) has a specification and **no
roadmap task**: `PG-16` decided where branding is stored, not when the screen is built.
It now reads "not scheduled". A shell test asserts that exactly the two unbuilt
destinations carry a badge.

## The grace warning nobody saw

`P3-07` wrote `MsgGraceWarning` for people inside the grace period and deferred showing
it to `P3-10`/`P3-12`. Neither showed it, and the constant has no caller. A member
learned the mandate existed at the sign-in that would no longer let them through.

`GET /v1/me/mfa` now returns `grace_ends_at`. **Your account** shows a notice to a
member with no factor: the deadline, or that the deadline has passed. It is hidden when
the deployment cannot enrol anybody, so it never tells somebody to do something the
page cannot offer. The unused constant is left in place. The notice's copy is the
console's, and the constant's comment is accurate about why it exists.

## The guides

- **Two-step verification** (end users): enrol an app or a passkey, recovery codes, the
  lost-device path with and without codes, the mandate from a member's side, and "This
  wasn't me". The lost-device steps follow `deploy/RUNBOOK-mfa-recovery.md`'s paths B and
  C, and the Definition of Done asks for exactly that match.
- **Step-up with `amr`** (integrators): the four values, the four combinations, why a
  recovery code is `mfa` and not `otp`, and a worked payout check. It is explicit about
  three things a reader would otherwise assume: `amr` is in the ID token only, a refresh
  issues no ID token, and `acr_values` is ignored, so a check can require `hwk` and still
  get `otp` back.
- **Refresh token rotation** (integrators): the lifetimes, both retry conditions, and the
  identical `invalid_grant`. It traces the concurrency case through the code rather than
  guessing. Two racing refreshes within the window do **not** kill the family: the second
  counts as a retry, revokes the first's successor, and the first client fails later with
  an ordinary refusal. If the first successor has already been used, the family dies. A
  table maps `seconds_after_rotation` to the likely client bug.
- **Require MFA** (administrators): the per-member effect, the grace rules and why they
  cannot be gamed, impact first, the audit events, and the administrator reset with the
  runbook's verification requirement.

Two drafting errors were caught by checking against code before publishing. The step-up
guide pointed at `/oauth2/authorize`; the router serves `/oauth/authorize`. The rotation
guide said a retry "works once"; the conditional `UPDATE` in `Rotate` admits a retry of a
retry while the new successor is untouched. Both are corrected, and a test now pins the
authorize path.

## Drift, tested rather than read

`backend/internal/docsdrift` is a test-only package, because the facts come from `mfa`,
`oauth/token`, `authn`, `audit` and `management` at once and none of those can import the
others. It asserts:

- the `amr` table rows are exactly `mfa.AuthMethods(...)`/`AuthMethodsWithRecovery(...)`
  rendered, and the vocabulary table lists exactly the four emitted values;
- `RotationGrace`, the three token lifetimes and the family lifetime, the reuse event
  name, and the refusal string, read from `handler.go`;
- the recovery code count, the low-water mark, the recent-authentication window, the
  clock skew and the per-user attempt bound;
- the grace length, the six audit event names, and the role each admin call needs, read
  from `management.Policy`;
- step 6: any docs section that mentions SAML, social sign-in or Project Grants must name
  Phase 4.

Mutations: the retry window changed to 60 seconds, the recovery-code row given `otp`, the
grace changed to seven days, and the Phase 4 labels removed from the quickstart. Each
turned the test red, and each was restored. The first draft of the test had two bugs of
its own. The vocabulary regex matched the claims table (it reported `amr` as an emitted
`amr` value), and the Phase 4 check worked per paragraph, where the concept pages label a
phase once per section. Both were fixed before the test was trusted.

## A red gate that showed only green lines

The first gate run for this task failed on "coverage floors". Its report was a table of
sixteen passing packages. `scripts/check.sh` ran the coverage script **twice**: once
silently to decide pass or fail, and again to print. The first run had a failure. The
second, printed run passed. So the report showed a different run from the one that
failed.

Re-running afterwards found nothing: two loops over every floored package had no test
failures, and `internal/login` measured a steady 80.4% four times. Whatever failed is a
flake, and it cannot be named now, because the script had also thrown away the test
output (`>/dev/null`) and printed only "tests failed".

Both are fixed. The gate runs coverage once and prints that run's output. The coverage
script now prints the failing tests' lines and file positions. This was proved with a
package whose `init` panics: the report names the package and shows `panic: mutant`. The
next time the flake happens, it will say what it is.
