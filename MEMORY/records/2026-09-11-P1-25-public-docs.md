# P1-25 — Public Docs: Real Quickstart and Generated API Reference

**Date**: 2026-09-11
**Branch**: `feat/P1-25-public-docs`
**Spec**: none — the card is `Spec required: No`.

---

## What this is

`P0-19` shipped the public site with a quickstart that opened with a `danger` admonition saying the guide did not exist. Phase 1 made it possible to write. This replaces it, republishes the generated API reference, and brings the rest of the site's claims up to what actually shipped.

The card's step 2 is the only one that matters: **verify the quickstart by following it from scratch against staging.** A quickstart that has never been executed is a hypothesis, and it is the first thing every evaluator tries.

## The quickstart was executed, not proofread

`scratchpad/p125-quickstart.sh` runs the literal commands from the published page against `https://auth.zedth.my.id` over real TLS, and asserts that every response shape the page *shows* is the shape the service returns — **field names included**, because a wrong field name is the failure a reader cannot debug from the page.

**52 assertions passed. One failed, and it was the page's fault.**

The page showed `refresh_token` in the token response. The service does not issue one unless `offline_access` is in the requested scope — registering the `refresh_token` grant type makes it *permitted*, not automatic. Written from the specification, the page was wrong; executed, it could not stay wrong.

Two more corrections came out of the same run, both invented from reading rather than running:

- **An `error_description` I made up.** The real wording is "the authorization code is not valid", and it is deliberately the same for an unknown code, a spent one, an expired one and a mismatched `redirect_uri`.
- **A `request_id` inside the error envelope.** The envelope is `additionalProperties: false` and has no such field. The correlation id is the `X-Request-Id` response header, and the run captured a real one to print.

That is three factual errors in a page written by someone who has read this codebase for days, in the parts a reader would copy. The card asks for the quickstart to be *followed*, not reviewed, and this is why.

The run also checks claims the page makes about *behaviour*, not just shape: a trailing slash is refused as a different redirect URI, `code_challenge_method=plain` is refused, a spent code is `invalid_grant`, the client secret is never returned a second time, the ID token's `aud` is the client and the access token's is the issuer, and the access token carries `typ: at+jwt` while the ID token carries `JWT`.

## What the run could not do

The DoD says "**someone who has never seen the project** completes the quickstart successfully against staging". That person does not exist in this session, and executing the commands myself is not the same test — I know what each one is for, so I cannot detect a step that is *unclear* rather than *wrong*.

What was verified is the strictly weaker claim: every command on the page runs, in order, from a clean shell, and every response matches what the page says it will be. The unclear-step half of that DoD item is left open rather than ticked.

## The gap the quickstart could not write around

**A new deployment cannot be bootstrapped without database access**, recorded as `PG-26`.

Every step works — once you already have an organization, a project, an administrator and one application. Getting the first of each does not work through any published surface: `POST /v1/organizations` needs `INSTANCE_OWNER` and nothing creates the first one; registering the first application needs a token that only an already-registered application can obtain; and the console is itself an application that has to be registered before anyone can log into it.

Every environment so far was seeded with `INSERT` statements, which is why this had never blocked anything. It is not a gap in the API contract — the endpoints are right. It is a missing operator path, and it is the first wall a stranger hits.

The page says so plainly in a `warning` admonition and points at `PG-26`, rather than opening with a step a reader cannot perform.

## The capability audit, now running in both directions

Phase 1 shipping made two landing-page cards wrong. "Single sign-on" and "A complete REST API" had been labelled *Phase 1 — planned* since `P0-19`.

`check-claims.mjs` already caught a capability claimed **before** it existed. It had no idea about the reverse, and the reverse is the one that happens by itself: nobody edits a page to introduce "still says planned" — it appears on the day a task is marked done, in a file nobody opened.

Both directions are now checked:

- A shipped card must carry `Shipped — Phase 1` and must not also carry a bare phase label.
- A planned card must carry its phase and must not say "Shipped".
- A card marked shipped whose tasks are not all `DONE` fails the build. So does one still labelled with a phase whose tasks all are.

**Single sign-on's task list gained `P1-26`**, which is the fourth revision of that list and the first to add a task that is not an endpoint. `P1-06` issues codes, `P1-07` exchanges them, `P1-12` is where a password is typed, `P1-18` registers applications, `P1-19` creates users — and `P1-26` is the one that put two applications behind one login and proved it. Until something had done that, "single sign-on" described endpoints rather than a capability. The list has been extended three times for exactly this reason, each time because *implemented* was mistaken for *usable*.

### The audit had been silently wrong the whole time

`statusOf` matched `/\*\*DONE\*\*/` against the whole row. The board bolds a status only when the row carries a caveat worth drawing the eye to; **most completed tasks are a plain `DONE`**. So the check read every one of them as unfinished.

In the direction it was originally written that failure is invisible — everything looks less shipped than it is, which only ever suppresses a complaint. It surfaced the instant the check gained its other direction and a capability had to *prove* it had shipped: the audit reported that `P1-15` through `P1-20` were not done, on a board where all six say `DONE`.

It now parses the status **column** rather than searching the line, which also means a status of "not DONE", or a note mentioning the word, cannot be mistaken for the status itself.

**A check that fails safe in one direction and is silently wrong in the other is worth distrusting on sight.** This one passed every build for three days while reading the roadmap incorrectly.

### Proven able to fail

Six mutations, six killed (`scratchpad/mutate-p125.sh`): a shipped card relabelled as planned, the status sentence rewritten, the "no hosted signup" qualifier removed, a card renamed out from under the manifest, a task moved back to `WIP`, and a claimed task vanishing from the board.

The card-rename mutation "survived" twice before it was right — both times because the mutation was bad, not the check. `Single sign-on` appears in the status sentence *before* it appears as a card title, so replacing the first occurrence left the card intact and the audit correctly passed. The mutation now targets `site-card__title">Single sign-on`. **A survivor is a claim about the test, and the first thing to check is the mutation.**

## The archived docs were publishing a false page

`versions.json` carries a `1.0` snapshot, taken during Phase 0 to prove the versioning pipeline worked before there was a release to version. It is badged "1.0 · placeholder" with an unmaintained banner — and it still contained the Phase 0 quickstart saying **"This guide does not exist yet"**, served at `/docs/1.0/quickstart`, reachable from the version dropdown.

That is not a neutral artifact. It is a published page making a claim about the product, and nobody re-reads it, because it is archived by definition.

Re-snapshotted from the current docs. The config comment now says to retake it whenever the current docs change materially, or delete it — the original comment only said to delete it "when a real release replaces it", which is a condition that does not fire on the day the page becomes wrong.

## Found while deploying

**I took the public site down for about four minutes.** The site container was restarted without sourcing `/home/infra/auth-state/.env`, so `AUTH_SITE_DIST` was unset and compose fell back to its default — `/home/infra/auth/public-site/build`, which does not exist on the VM. nginx mounted an empty directory and answered `403` on `/` and `404` everywhere else, while the freshly extracted files sat correctly on disk.

It reads exactly like the bind-mount inode trap that `deploy/console/docker-compose.yml` has a header about, and it is a different bug with the same symptom. Fixed by sourcing the env file and `--force-recreate`, and confirmed by reading the container's actual mounts rather than trusting the restart.

**The site was redirecting HTTPS visitors to HTTP.** Docusaurus builds a directory per route, so `/about` is a 301 to `/about/` — and nginx built that `Location` absolutely, from what it sees: `http://$host`, no port, no TLS. Behind a tunnel that terminates TLS at the edge, every route typed without a trailing slash answered an HTTPS request with an HTTP redirect.

Cloudflare's edge and any browser holding the HSTS entry hide it, which is why it survived since `P0-19`. The request that is *not* covered is a first visit from a browser that has never seen the host — which is the visit a marketing site exists for. One line: `absolute_redirect off`. nginx cannot know the public scheme, port or path prefix, so it should not try to reconstruct them.

## The API reference

Regenerated from `openapi/openapi.yaml` and **byte-identical** to what was already committed — it had been kept current as each endpoint landed. That is the answer to the DoD item rather than an absence of work: the reference covers all 35 operations because the server's own interfaces are generated from the same file, so an endpoint cannot exist without being in it (ADR-013).

Never hand-written, per `CLAUDE.md`.

## Smaller decisions

- **The changelog entry carries a "Known limits" section**, and it is the part of the entry that matters: no hosted signup, roles not in tokens, refresh tokens that do not rotate, one VM against a plan that requires more. A release note listing only additions is a sales page.
- **The landing CTA is now "Get started" pointing at the quickstart.** `docs/UI-UX/21`'s blueprint always said it should be; `P0-19` pointed it at the docs instead because a "Get Started" button leading to "not available yet" costs more trust than it wins. The condition it was waiting on is now met.
- **"Shipped" is qualified on the page itself.** "There is no hosted signup: you run it yourself, from source" is in the status sentence, and `check-claims.mjs` fails the build if it disappears — with two cards marked shipped, that clause is what keeps "shipped" from reading as an invitation to sign up.
- **Guides stays nearly empty on purpose.** One row points at the quickstart; the rest name the phase *and*, where it is more specific than a phase, the actual blocker — roles do not exist, and provisioning from CI needs `PG-26`.
