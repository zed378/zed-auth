## Evidence, not ticks

`scripts/acceptance-phase2.sh` checks `docs/PLAN/17`'s four criteria against a
running service and **prints what it found** — the actual grant, the actual
decision, the actual refusal.

That shape is deliberate. Take criterion 1: *a role assigned in Project A
appears in the token claim, scoped to Project A only.* The second half is
satisfied by a user with no grants anywhere, so a script that checked only
"absent from B" would pass against a completely broken system. Every negative
half here is credited only when the positive half also held, and the script says
so in a comment where somebody might otherwise simplify it.

**19 checks, 0 failures.**

## The first run failed four, and all four were the harness

Worth recording because both are mistakes somebody else will make.

**`/v1/authz/check` denied a permission the user held.** The endpoint takes its
organization and project from the **caller's** token and offers nowhere in the
request to name either — that is what stops a caller asking about a tenant that
is not theirs. The script asked with the console administrator's token, whose
project is the console's, so it asked the right question about the wrong
project. It now registers an `api` application in the project under test and
uses a client-credentials token, which is what a consumer service would have.

**`PATCH /v1/organizations/{org_id}` "did not persist".** It answered 403 — the
bootstrap administrator holds `ORG_ADMIN` and changing an organization's policy
requires `ORG_OWNER` — and the script discarded the status code and reported the
unchanged value as a failure. The refusal is correct and is now asserted as
such.

That second one is the first time [`PG-31`](../../TASKS/BACKLOG.md) has cost
anything concrete: **no API grants a manager role**, so no script can promote
itself to perform that write. The enforcement half of criterion 3 is therefore
proven by `P2-10`'s integration tests — which hold two organizations at
different session lifetimes and measure the resulting expiry — and the
acceptance script names that file rather than claiming to have checked something
it cannot reach.

Getting there took two findings.

### The endpoint shared the Management API's rate limit

The first run refused **19,658 of 40,515 requests**.

`ratelimit.PerClient` is 600 a minute, and its own comment says what it was
sized for: "far above any console session and comfortably above a provisioning
script walking a few thousand users at a page at a time".

`/v1/authz/check` is neither of those things. `docs/PLAN/12` calls it "called
frequently at runtime by resource servers", and `P2-15`'s guide tells consumers
to call it on every action that cannot be undone. Ten a second per client is a
ceiling one busy consumer reaches with a handful of users, and the 429 lands on
its hot path rather than on an administrator's tooling.

Fixed with `PerClientAuthz` at 6,000 a minute and three things that make a
second bound mean anything:

- **its own counter namespace** — two quotas sharing a key share an allowance,
  so the looser one is spent by the traffic the tighter one governs, which is
  the same as not having two;
- **a `HotRoutes` table** in the middleware, readable in one screen like
  `Policy`, with a test asserting every route in it exists;
- **a test that every ordinary management route stays on the tighter bound**. A
  fix that quietly widened the whole API would be worse than the problem.

The number is justified rather than picked: what a stolen credential could do
with the volume between 600 and 6,000 here is close to nothing — the endpoint
answers one action at a time, within the caller's own project, and is
deliberately unhelpful as an oracle — while the availability cost of the lower
bound is a consumer's users seeing failures.

### Then the measurement was wrong

At 724 rps against a 6,000/minute bound, a third of the samples were the
limiter's fast rejection path, and percentiles blended from two code paths
describe neither.

The harness already knew this. Its management phase says "measuring an endpoint
past its own documented bound measures the limiter" and paces accordingly; the
authz phase did not. It does now, at a rate `run-authz.sh` reads out of
`ratelimit.PerClientAuthz` with `sed` — one source of truth, at the cost of a
grep, and it exits rather than guessing if it cannot find the constant.

## A load test that runs where the VM is not

`run.sh` requires `~/auth-state/.env` and the staging compose file. This phase
spent days unable to measure anything because the VM was unreachable.

`run-authz.sh` seeds **entirely through the Management API** — project, role,
user, grant, service client — so it runs against any deployment it can get a
token for. It also smoke-checks that the fixture decides *allow* before
measuring, because a phase that measures the denial path is measuring a shorter
one, and finding that out from a latency number rather than a sentence wastes a
run.

## The Phase 3 threat review

[Recorded separately.](2026-09-12-P2-17-phase-3-threat-review.md) No new
category of risk — Phase 3 is the first phase where every card is security work
and `docs/SECURITY/02` already covers it — but ten findings, five of which are
one observation applied to different cards: **every mechanism Phase 3 adds
arrives with a recovery path, and the recovery path is the new attack surface.**

The one that needs acting on before Phase 3 starts is T3-9. `P2-10` stored
`mfa_required` and enforced nothing, deliberately. The moment `P3-07` delivers
enforcement, every organization that set the flag optimistically starts refusing
logins from users with no factor. That needs a transition designed, not
discovered.
