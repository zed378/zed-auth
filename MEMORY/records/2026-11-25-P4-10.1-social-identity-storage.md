## What Changed and Why

Migration `20261125000047` activates the planned `user_identities` table. A unique `(provider, provider_subject)` identifies an existing local user. The subject is compared exactly, with deterministic `C` collation and a 1–255-byte bound; it is never normalized or matched against email. The table holds no provider token, secret, or email field.

`internal/social` provides the three provider values, input validation, and a read-only `Store.BySubject` operation. Unknown subjects and links belonging to another tenant both return `ErrNotFound`. A lookup never creates or links a user, following ADR-030.

## Database Security

- RLS derives tenant ownership from the referenced user. There is no second organization column that can disagree with that user's organization.
- Both reads and writes require the referenced user to belong to `current_org_id()`. An unfiltered application query sees only its tenant's links; missing tenant context and instance scope see none.
- The runtime role has no UPDATE permission, including the UPDATE privilege that deployment defaults would otherwise grant. An existing binding cannot be reassigned in place.
- Database uniqueness arbitrates concurrent attempts to bind the same provider subject, including attempts from different organizations.
- Deleting a user cascades to its links. An index on `user_id` supports ownership checks and deletion.

The schema permits INSERT and DELETE for P4-11's future authenticated, audited linking flow. This subtask adds no production write method or HTTP endpoint, so it introduces no unaudited linking action.

### Full Integration Run

The first full run failed `ratelimit.TestConcurrentRequestsCannotExceedTheLimit` (22 of 60 concurrent requests allowed instead of 20) and 11 user tests after their PostgreSQL connection started returning EOF/refused errors. Both packages passed when rerun serially without any changes to their code or tests. The failures did not reproduce on that rerun; their root causes are not established. The failed PostgreSQL container was no longer available to inspect after the full run.

RTK reported four skipped entries: three command packages with no tests and the pre-existing security test `TestTrustingProxyHeadersDoesNotExtendToTheTenant`. The new social tests were not skipped. The original full-suite result is retained rather than described as a green run.

## Scope and Remaining Work

P4-10 remains WIP. P4-10.2 covers provider configuration, secret references, callback state/PKCE/nonce, and provider adapters. P4-10.3 covers policy checks, callback/session/MFA/audit wiring, hosted login UI, and end-to-end acceptance. Authenticated linking and last-login-method protection remain P4-11. No social provider is advertised or enabled by this storage subtask.

No API surface or generated client changes are needed for the internal repository. End-to-end provider flow and token replay tests belong to the remaining callback work; they are not claimed as covered here. No reference documents under `docs/PLAN`, `docs/UI-UX`, or `docs/SECURITY` were changed.

## Decisions and Rollback

This follows ADR-028 and ADR-030 without introducing another protocol or provisioning decision. Tenant ownership is inherited through the planned user FK. The down migration removes only the new table; no live deployment was migrated during this work. Dropping the table destroys its links and should be reserved for an intentional rollback, not a way to disable social sign-in.
