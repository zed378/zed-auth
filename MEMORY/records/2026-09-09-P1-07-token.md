## What Changed

`internal/oauth/token` implements the token endpoint: three grants, client authentication by Basic or form post, PKCE verification, signed ID and access tokens, and opaque refresh tokens stored as hashes.

**The flow closes here.** `P1-06` has been issuing codes that nothing could redeem; `P1-02`, `P1-05` and `P1-11` were packages with no callers. A consumer application can now complete a login end to end, and `P1-04`'s discovery document advertises both endpoints a conforming client needs — which is the first moment its opening DoD item can honestly be ticked.

## Why

`docs/PLAN/12` calls this "the highest call volume, most latency-sensitive" endpoint in the system: every consumer's login latency is this endpoint's latency, and so is every silent renewal.

## How

**The three token types are deliberately different things**, and the separation is carried by two fields rather than by convention:

| Token | Form | `typ` | `aud` |
|---|---|---|---|
| ID token | JWT | `JWT` | the `client_id` |
| Access token | JWT | `at+jwt` (RFC 9068) | the resource |
| Refresh token | **opaque random** | — | — |

An ID token is an assertion *about* the user, addressed to the client that asked; an access token is a capability *at* a resource server. Conflating them is the token-substitution abuse case, and a resource server that checks either field refuses the swap.

**The refresh token is opaque rather than a JWT for two reasons, and the second is the one worth writing down.** It must be revocable, so it must be looked up — which a stateless JWT would defeat. But `P1-03` also found that sixteen distinct base64url encodings of one RSA signature all verify, so a JWT's string form is non-canonical and reuse detection keyed on it can be defeated by mutating one character. `P3-06` builds reuse detection on this foundation; an opaque value has exactly one representation and its SHA-256 is canonical, so the trap cannot be walked into.

**The code is consumed before the client, redirect URI or verifier is checked.** A wrong guess burns it. Leaving it alive through a failed check would turn a single-use credential into an oracle a verifier could be brute-forced against, one request at a time, with the code valid throughout.

**Every redemption failure returns the same `invalid_grant`.** An error distinguishing "unknown code" from "wrong redirect_uri" tells an attacker holding a code that the code is real.

**A confidential client presenting no secret is `invalid_client`, never treated as public.** That downgrade is the client-authentication bypass, and it is the kind that looks like leniency until somebody notices a `web` client's code can be redeemed by anyone who saw it.

ADR-016's choice of SHA-256 over Argon2id was made for this path specifically, and it is spent here: client secrets are verified on every request.

## Decisions Made

| Decision | Rationale |
|---|---|
| Refresh tokens are opaque, not JWTs | Revocability needs a lookup; and `P1-03`'s malleability finding makes a JWT string a poor key for `P3-06`'s reuse detection |
| Access token `typ: at+jwt`, ID token `typ: JWT`, different `aud` | Two tokens that differ only in claims are two tokens somebody eventually swaps |
| The code is consumed before later checks | Otherwise a live code is an oracle to brute-force a verifier against |
| One `invalid_grant` for every redemption failure | Any distinction confirms the code is real |
| A confidential client is never downgraded to public | The client-authentication bypass |
| No ID token on a refresh | Nothing was authenticated just now; asserting otherwise would be a false statement with a fresh timestamp |
| No refresh token for `client_credentials` | The client can authenticate again whenever it likes, so a refresh token is a second, longer-lived credential for nothing |
| Access token 10 minutes | The middle of `docs/PLAN/09`'s 5–15. Shorter multiplies traffic on the most latency-sensitive endpoint; longer widens the window for a token that cannot be revoked |
| Refresh token 14 days | Deliberately short *because* Phase 1 does not rotate. `P3-06` can lengthen it once theft becomes detectable |
| The role namespace is present and empty | A consumer reading it today keeps working when `P2-04` populates it, and one that would have crashed on a missing key never gets written |

### PG-15 — `refresh_tokens` had no scope column

`docs/PLAN/04` § `refresh_tokens` lists eleven columns and none records the scope the token was issued for. A refresh therefore had nothing to reproduce: it could carry no scope, or re-derive one from the client's registration — and those are different things. Scope is what the **user** consented to at the authorization endpoint; `grant_types` is only what the client may ask for.

The rule needing it is that a refresh may narrow scope and never widen it. Widening would make the refresh token more powerful than the consent that created it, and narrowing needs an original to narrow from. Closed by an additive `scope text[] NOT NULL DEFAULT '{}'`.

## Deviations from the Plan

`docs/PLAN/04` should be amended for `PG-15`, through the deliberate plan-change process.

The codegen exclusion extends to `token`. The line is now stated explicitly in `oapi-codegen.yaml`: the OAuth protocol endpoints (`/oauth/*`) are shaped by RFCs written for browsers and form posts and need the raw request — `/oauth/token` for the `Authorization` header that `client_secret_basic` puts credentials in, `/oauth/authorize` for ordered validation and duplicate detection. The management API (`/v1/*`) is REST and will be generated.

Both endpoints stay in `openapi.yaml`, so both are documented, generated into the public API reference, and checked by `openapi-shipped-paths.py`.

## Definition of Done Verification

- [x] Each supported grant works end-to-end against an integration test with a real database.
- [x] `password` and `implicit` are rejected with the correct OAuth error — by name, with the description pointing at the supported flow.
- [x] A wrong `code_verifier` is rejected, and the code does not survive the attempt.
- [x] Concurrent redemption yields exactly one success, verified by a parallel test.
- [x] Tokens carry the exact claim set, and `aud` and `iss` are correct for the requesting client — asserted after verifying against the published JWKS, not on the struct.
- [x] No refresh token is stored in plaintext, verified by reading the whole row as text.
- [ ] **The endpoint meets `docs/PLAN/12`'s latency targets under the load test.** Deferred to `P1-27`, which owns it. What ships here is the histogram, bucketed on the targets so a quantile query answers "did we meet it" without interpolating.

## What Did Not Work

**`AuthenticateClient` checked that a secret was presented and never verified it.** Caught while cleaning up a leftover parameter in its signature — a function that returned nil for any secret at all, which every test at the time would have passed because none of them presented a wrong one. The tests that exist now would catch it, and they exist because the bug prompted them.

**Three more RLS bootstrap problems.** The refresh-token lookup and the session-liveness check both need to run before a tenant is known, and both hit the wall `P1-11` found: `org_id = current_org_id()` matches nothing with no tenant set. Two more `SECURITY DEFINER` functions, each narrowed to its own question — `session_live` returns no columns at all, only whether a row exists.

The client-credentials read was the interesting one, because it did **not** need a function. `ByClientID` has already established the organization by the time a secret is wanted, so `CredentialsFor` takes the resolved application and reads on the normal tenant-scoped path. That is why the bootstrap function can return no secret columns at all.

**gosec flagged the token response**, correctly by its own logic: a marshalled field named `access_token` matches its secret pattern. Suppressed with a note saying what makes the suppression true — this struct is written to exactly one place, is never logged, audited or stored, and the audit event beside it carries the client, grant and scope and no token. If it ever reaches a log line, the suppression stops being true and the rule was right.

**Both coverage floors tripped.** `internal/oauth/client` fell to 79.8% when `CredentialsFor` arrived untested and `token` sat at 79.2%. The floors caught both rather than a reviewer noticing.

## Follow-Ups and Open Questions

- **`P1-04`'s first DoD item can now be ticked** — discovery advertises both endpoints, so a conforming client can configure itself. Worth revisiting that card.
- `P1-12` still owns the login page, so a user *without* a session cannot get a code yet. The endpoint is complete; the flow needs one more piece to be usable by a human.
- **Phase 1 does not rotate refresh tokens.** A stolen one is replayable until it expires or its session is revoked. `P3-06` owns rotation and reuse detection; the columns and `RevokeFamily` are already here so that phase adds a trigger rather than a mechanism.
- `P1-08` (userinfo) and `P1-09` (introspection, revocation) consume the access token.
- `docs/PLAN/04` needs amending for `PG-15`.

## What to Watch

**Anything that makes the refresh token a JWT.** It would reopen `P1-03`'s malleability trap for `P3-06`'s reuse detection, and the failure would be silent — reuse detection that can be defeated by changing one character still passes every test written against well-formed tokens.

**Anything that stops consuming the code before the checks.** It would look like a kindness — letting a client retry a typo'd verifier — and would turn the code into a brute-force oracle. The test asserting the code is gone after a failed verifier is what stands in the way.

**`auth_token_errors_total{grant,error}`.** "Token requests are failing" is not actionable; `invalid_client` on `client_credentials` names a misconfigured service account, and `invalid_grant` on `authorization_code` after a consumer deploy names a broken redirect URI.

**The `no-store` header.** It is asserted on both the success and error paths, because a cached token response is a token handed to whoever asks the cache next — and an error response still says whether a client id is valid.
