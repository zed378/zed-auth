## The suite was never green in CI, because CI never ran

The last item on the Definition of Done is "the suite is green in CI". Checking it meant
opening GitHub's run history for the first time in a long while. There had been **112 runs
and no successes**.

Ninety-four of them were named after the file path rather than the workflow. That is how
GitHub reports a workflow file it cannot parse. `.github/workflows/ci.yml` had a `run:`
key indented two spaces deeper than its step, added at `P1-03`. From then on, no job ran
on any push. Every record since that said a suite was "green" meant the local gate, and
nothing had noticed the difference.

The eighteen runs before the file broke were failing too, on two jobs. The integration
tests failed for unknown reasons. The compose validation failed because the VM compose
file had since gained required variables that the CI step did not supply. That second
failure was reproduced locally and fixed. It had been failing on placeholders since
Phase 1, hidden first by nobody reading the red runs and then by the parse error.

Three changes:

- **The file parses and passes actionlint.** Only three advisory shellcheck notes remain.
- **The compose step validates every compose file the project deploys**, with every
  required variable supplied, and was reproduced passing locally.
- **`scripts/check.sh` runs actionlint.** The gate re-implements CI's steps rather than
  reading CI's file, and that is why it could not see the break. The new check passes on
  the fixed file and fails on the old one.

## An abuse case the specification named and nothing implemented

The inventory mapped every Phase 3 abuse case to the test that covers it, and one mapped
to no code at all. `P3-07`'s specification lists **A-2, "keep using a token issued before
the policy"**, with the control **"the refresh grant re-reads the policy"**. Nothing on
the refresh path read the mandate. So a user with no factor, past the grace deadline, kept
refreshing a token family for its full 90 days. The silent authorize path had the same
hole: a live browser session kept receiving codes with no interaction. The mandate applied
only to people who happened to type a password.

`authn.MandateCheck` applies `RequireMFA`'s rule on both paths. It is the same rule the
login page uses, so the paths cannot disagree about who is past the grace:

- **A refresh** is refused with `invalid_grant`, the same as any dead token. The client
  sends the user to sign in, and signing in routes them into enrolment.
- **A silent authorize** treats the session as absent.
- **A mandate that cannot be read refuses**, because failing open would let one query's
  outage switch the policy off.
- **A build that cannot enrol anybody refuses nothing**, which is the same non-lockout
  answer the login page gives.
- **A factor type the build cannot challenge is not a factor**, as on the login path.

The tests turn red when the refusal is removed and when the factor-type filter is removed.

## Staging had no backups for four days, again

Deploying this phase to staging starts with a backup, so the backup was checked first.
`/home/infra/auth-state/backups` did not exist, and the unit had failed every night since
2026-09-11 with `226/NAMESPACE`. That is the same failure `BL-01` records from 2026-09-09,
by a different route.

On 2026-09-11 `~/auth-state` was deleted and restored. The restore rebuilt `.env` from
`docker inspect`, which recovers what the *containers* receive and nothing else, so the
backup-only `AUTH_BACKUP_DEST` was gone. It also never recreated `backups/`. The three
verified dumps from 9–11 September went with the old directory.

The fix is in the unit, so the two settings cannot come apart a third time:

- **`AUTH_BACKUP_DEST` is set in the unit**, beside the `ReadWritePaths` it must equal.
- **`ExecStartPre=+install -d …`** creates the directory.
- **`ReadWritePaths=-…`**: the `-` is the part that works. The first attempt used `+`
  alone and still failed with 226, because systemd builds the namespace for every Exec
  command, including a `+` one. That was verified on the VM, not assumed.

To test it, the directory was deleted and the unit started. It created the directory, took
the dump, restored it into a throwaway database, and matched 20 tables' row counts.
